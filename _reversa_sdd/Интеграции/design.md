## Слоистая архитектура

```
Каналы:   Сайт      План обмена 1С      Банк/Бух       HTTP заселения     Мессенджеры          Эквайринг
            │             │                 │                │                 │                    │
         ОбменСайт   ОбменГостиницы/   ОбменВыписка/    HTTP_Модуль/     МесенджерСервер       PayKeeperКлиентСервер
        (HTTPS GET   ОбменТест         ОбменБухгалтерияНДС ОбменHTTP      (диспетчер)            │
         JSON)       (XML+FTP)         (XML+FTP)        (HTTPS GET JSON)    │                  PayKeeperСервер (оркестрация)
            │             │                                          ┌──────┴──────┐            │
         ФТПСервер ←──── общий FTP-транспорт ─────────────┐    WhatsAppСервер  TelegramСервер   PayKeeper (REST-клиент)
         (порт 21, пассивный, таймаут 5с)                 │       │              │             HTTPS:443 OpenSSL, token-сессия
                                                          │  GREEN_WhatsApp  Обработка.GREEN_Telegram
                                                          │  (REST api.green-api.com)
                                                  ОбменКартинкаСервер (COM V83)
```

Три принципа дизайна, подтверждённые кодом:
1. **Диспетчер → адаптер → REST-клиент** для мессенджеров: бизнес-код не знает о Green API, обращается только к `МесенджерСервер`. 🟢
2. **Единый FTP-транспорт** (`ФТПСервер`) переиспользуется планами обмена и выгрузками. 🟢
3. **Единый формат структуры-ответа** транспорта: `{Ошибка:Булево, КодОшибки:Число, Описание/ОписаниеОшибки:Строка, Данные/ДанныеJSON}`. 🟢

## Основной поток — узловой обмен (RF-01) 🟢

1. `ВыполнитьОбменДанными()` открывает выборку `ПланыОбмена.ОбменГостиницы.Выбрать()`.
2. Для каждого узла: если `Узел = ЭтотУзел` → пропуск (BR-02).
3. `ПрочитатьСообщениеСИзменениями()`: забрать файл с FTP, `ЧтениеXML` + `СоздатьЧтениеСообщения()`, цикл `ВозможностьЧтенияДанныхXML/ПрочитатьДанныеXML`, регистрация добавленных/заменённых/удалённых. Коды ошибок 1/30 → «нет сообщения», не фатально (BR-01).
4. `ЗаписатьСообщениеСИзменениями()`: `ПолучитьИмяВременногоФайла('xml')` → `ЗаписьXML.ОткрытьФайл` → `СоздатьЗаписьСообщения().НачатьЗапись(ЗаписьXML, Приёмник.Ссылка)` → регистрация пространств имён xsd/xsi/v8 → цикл `ВыбратьИзменения(Получатель, НомерСообщения)` с `ЗаписатьДанныеXML()` на каждую порцию → `ЗакончитьЗапись()`.
5. `ФТПСервер.ПолучитьДанныеУзлаОбмена(Приёмник.Код)` → `ПолучитьИмяФайлаОбменаФТП(...)` → `ФТПСервер.ЗаписатьФТПФайл(...)`.
6. Удалить временный файл (всегда, в т. ч. при ошибке FTP).
- Источник: `CommonModules/ОбменГостиницы/Module.bsl:24-136`, схема — `flowcharts/Интеграции-ПланОбмена.md`.

## Основной поток — диспетчер мессенджеров (RF-04, RF-05) 🟢

1. Бизнес-код (например `РассылкаWhatsApp`) вызывает `ОтправитьДанные_Месенджер(ТипОтправки, Телефон, Текст, ИмяФайла, Ссылка)`.
2. Диспетчер нормализует телефон `GREEN_WhatsApp.ТелефонGREEN()` (BR-05).
3. Для каждого включённого канала (по константам `СообщенияЧерез*`) вызывает соответствующий адаптер: `WhatsAppСервер.Отправить*GreenWhatsApp()` и/или `TelegramСервер.Отправить*GreenTelegram()`.
4. Адаптер оборачивает вызов REST-клиента в `Попытка` и возвращает `{Ошибка, КодОшибки, Описание}`.
5. REST-клиент `GREEN_WhatsApp`: формирует URL `waInstance<Инстанс>/<Метод>/<Токен>` (инстанс/токен из констант), `chatId='<номер>@c.us'`, тело JSON, POST через `HTTPСоединение(..., ЗащищенноеСоединениеOpenSSL)`; 200 → `ЧтениеJSON`, иначе `ВызватьИсключение` (статус+тело).
- Источник: `МесенджерСервер`, `WhatsAppСервер`, `GREEN_WhatsApp/Module.bsl`; схема — `flowcharts/Интеграции-РассылкаWhatsApp.md`.

## Основной поток — PayKeeper (RF-08, RF-09) 🟢

1. `ПолучитьИОбработатьСписокПлатежей()` → `PayKeeperКлиентСервер.СписокПлатежейPayKeeper()`.
2. При запросе `ОбновитьТокен(Соединение)`: если токен пуст/истёк → GET `/info/settings/token/`, прочитать `token`, `ВремяИстечения = ТекущаяДата()+1200` (BR-08).
3. `ВыполнитьЗапрос`: `HTTPСоединение(Адрес, 443, Имя, Пароль, , , ЗащищенноеСоединениеOpenSSL)`, `Content-Type: application/x-www-form-urlencoded`, тело `"token="+Токен+ТелоЗапроса`.
4. Детект HTML-страницы ошибки → извлечь текст (BR-11); иначе `ПрочитатьJSON`.
5. По каждому платежу — маппинг полей (`id→ИД_Платежа, clientid→Плательщик, orderid→НомерСчета, pay_amount→Сумма, status→Статус, success_datetime→ДатаОплаты`) → `ОбновитьPayKeeperПлатежи()` (upsert по `ИД_Платежа`, сохранить `ГУИД/ДатаСоздания`, BR-09).
6. Если `Статус='success'` → `СвязатьPayKeeperПлатежи()` (привязка к документу долга, BR-10).
- Источник: `PayKeeper/Module.bsl`, `PayKeeperСервер/Module.bsl`; схема — `flowcharts/Интеграции-PayKeeper.md`.

## Альтернативные потоки

- **Нет нового сообщения обмена (код 1/30):** результат с ошибкой добавляется в массив, цикл продолжается. 🟢
- **Недоступен сайт/HTTP-сервис:** исключение оборачивается в структуру `{Ошибка=Истина, Данные=Массив(), Описание=ОписаниеОшибки()}`. 🟢
- **Телефон без WhatsApp/Telegram:** КодОшибки 100 в результате. 🟢
- **Истёкший токен PayKeeper:** прозрачное обновление перед запросом; при невозможности — `ВызватьИсключение`. 🟢
- **HTML-страница блокировки хостинга PayKeeper:** извлечение текста ошибки вместо JSON. 🟢
- **Сбой FTP при записи плана обмена:** ошибка сообщается, временный файл всё равно удаляется. 🟢
- **COM-соединение с планшетом недоступно:** до 3 повторов через `Перейти ~Соединение`; пустые `Попытка` без логирования (антипаттерн). 🟡

## Зависимости

- `ФТПСервер` — общий транспорт FTP для планов обмена и выгрузок (`ОбменГостиницы`, `ОбменБухгалтерияНДС`). 🟢
- Инфраструктура сообщений плана обмена 1С (`СоздатьЗаписьСообщения`, `ВыбратьИзменения`) — ядро узлового обмена. 🟢
- Green API (`api.green-api.com`, `media.green-api.com`) — облачный шлюз WhatsApp/Telegram/MAX. 🟢
- `Обработка.GREEN_Telegram` — внешняя обработка-движок для Telegram (вызывается из `TelegramСервер`). 🟢
- PayKeeper (HTTPS:443) — эквайринг и СБП. 🟢
- `ОбщийФункционалКлиентСервер.ПолучитьЧисло/ПолучитьДату` — парсеры при маппинге JSON. 🟢
- `V83.COMConnector` — COM-доступ к файловой базе планшета. 🟡
- Модуль «Финансы» — документ «Выписка» (сериализуется здесь), документы долга/оплаты (привязка PayKeeper). 🟢
- Модуль «Бронирование» — конвертация полученных бронирований сайта в `Document.ЗаявкаСайт`. 🟢

## Выявленные дизайн-решения

| Решение | Свидетельство в коде | Доверие |
|---------|---------------------|-----------|
| Адаптерный слой над Green API (диспетчер не знает протокола) | `МесенджерСервер`→`WhatsAppСервер`/`TelegramСервер` | 🟢 (ADR 0009) |
| Узловой обмен через штатный механизм 1С + файловый XML на FTP | `ОбменГостиницы`, планы обмена | 🟢 (ADR 0009) |
| Токены/адреса в константах, а не в коде | `GREENApiToken_*`, `Сервер*HTTP` | 🟢 |
| Token-сессия PayKeeper с TTL и ленивым обновлением | `PayKeeper.ОбновитьТокен` | 🟢 |
| Идемпотентность через регистры сведений | РС `РассылкаWhatsApp`, РС `PayKeeperПлатежи` | 🟢 |
| Единая структура-ответ транспорта `{Ошибка,КодОшибки,Описание,Данные}` | повсеместно | 🟢 |
| COM-интеграция с отдельными базами (картинки/горничные) | `ОбменКартинкаСервер` | 🟡 (ADR 0005) |
| Ручная сборка multipart/form-data для файлов Green API | `GREEN_WhatsApp` (`ПараметрFormData`/`ФайлFormData`) | 🟢 |

## Внутреннее состояние

- **Планы обмена** (`ExchangePlan`): стандартные реквизиты узла `Code/Description/SentNo/ReceivedNo/ThisNode/DeletionMark`; `thisNode` UUID предопределённого узла (`ОбменГостиницы` = `2a0723ee-…`, `ВГ_ВыпискаГостиницы` = `bdb53db4-…`, `ОбменТест` = `202c2b76-…`). `ВГ_ВыпискаГостиницы` доп. реквизит `Организация` (String). 🟢
- **РС `PayKeeperПлатежи`** (измерение `ИД_Платежа`): `ГУИД, Плательщик, НомерСчета, Сумма, Статус, ДатаСоздания, ДатаОплаты`. 🟢
- **РС `РассылкаWhatsApp`** (ключ Клиент+ДатаРассылки+ТипРассылки): факт рассылки для идемпотентности. 🟢
- **Структура соединения PayKeeper** (in-memory): `{Параметры{Адрес,Имя,Пароль}, Токен{Идентификатор,ВремяИстечения}, Ошибка, Описание}`; кэш COM-соединения планшета — во временном хранилище через параметр сеанса. 🟢

## Наблюдаемость

- Ошибки рассылки накапливаются в файл и отправляются на e-mail `postnikov_sn@invina.ru` (🟡 хардкод адреса, `РассылкаWhatsApp:33`).
- Ошибки FTP сообщаются через `Сообщить(...)` в потоке обмена. 🟢
- COM-обмен картинками: 🟡 пустые `Попытка` без логирования — наблюдаемость отсутствует.
- 🔴 Системного журналирования ошибок интеграций (`ЗаписьЖурналаРегистрации`) в разобранных модулях не обнаружено — требует подтверждения.

- 🔴 Боевые секреты в комментариях исходников: FTP (`212.176.32.173 / INVINA\streg / mnbvcxz*279`, `ФТПСервер:199-202`), Telegram ApiToken Green API (`TelegramСервер:4,20,59,120`), COM `Pwd="123"` (`ОбменКартинкаСервер:8,16`). См. `questions.md`.

- 🟡 Дубли/тестовые объекты: `Обмен_ТЕСТ`, `ОбменГостинницы` (опечатка), `GREEN_Тест`, план `ОбменТест`, методы `*_1` в `ОбменГостиницы`.
- 🟡 `HttpBridgeКлиент` (378 строк) и обработки `GreenAPI`/`GREEN_MAX` не разобраны детально.
