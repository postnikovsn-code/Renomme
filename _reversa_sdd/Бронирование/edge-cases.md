# Бронирование — Крайние случаи

> Крайние случаи модуля «Бронирование», выведенные из кода. Каждый описывает условие, поведение легаси и ожидаемое поведение реконструкции. Уверенность: 🟢/🟡/🔴.

## EC-01. Конфликт занятости номера (пересечение резервов)

- **Условие:** на запрашиваемый почасовой интервал номера уже существует запись `ЗанятостьНомеров` от другого регистратора (`Регистратор <> ТекущийРегистратор`).
- **Поведение легаси:** `ЗанятостьНомераПроверить` возвращает `Результат = Истина`; `ОбработкаПроведения` выдаёт «Номер занят… ЗАПИСЬ ОТМЕНЯЕТСЯ» и ставит `Отказ = Истина`. Движения не формируются. 🟢
- **Ожидаемо:** проведение отменяется, существующий резерв не повреждается. Граничный час: выезд исключает последний час (`Конец−1`), т.е. бронь, выезжающая в 12:00, и бронь, заезжающая в 12:00, на один номер НЕ конфликтуют. 🟢
- Источник: `ObjectModule.bsl:13-18`; `ДокументыСервер.ЗанятостьНомераПроверить:264-311`.

## EC-02. Дубль при конвертации заявки сайта

- **Условие:** пользователь повторно выполняет «СоздатьЗаявкуНаБронирование» для `ЗаявкаСайт`, по которой уже есть проведённая `ЗаявкаНаБронирование` (`ЗаявкаСайт = ТекущаяСсылка`).
- **Поведение легаси:** `ЕстьЗаявкаНаБронирование()` находит существующую бронь → выводится предупреждение, новая бронь не создаётся. 🟢
- **Ожидаемо:** идемпотентность конвертации: одна заявка сайта → не более одной брони. 🟢
- Источник: `Documents/ЗаявкаСайт/Forms/ФормаДокумента/Module.bsl:50-64`.

## EC-03. Неоднозначное сопоставление клиента из заявки сайта

- **Условие:** по ФИО/телефону из заявки сайта найдено несколько клиентов (`ТипСовпадения = 2`) или ни одного (`= 1`).
- **Поведение легаси:** при неоднозначности/отсутствии пользователю предлагается выбрать существующего или создать нового клиента вручную. 🟡
- **Ожидаемо:** автоматическое связывание только при однозначном совпадении; иначе — интерактивное решение. 🟡
- Источник: `Documents/ЗаявкаНаБронирование/Forms/ФормаДокумента/Module.bsl:459`.

## EC-04. Потеря копейки при делении счёта (нечётная сумма)

- **Условие:** `РазделитьСчет И ЕстьКлиент2`, сумма счёта нечётна (например 1001).
- **Поведение легаси:** первому гостю `1001/2 + 0.001 = 500.501`, второму `1001 − 500.501 = 500.499`; сумма частей = 1001 (копейка не теряется). 🟢
- **Ожидаемо:** инвариант «сумма частей = целому» при любых суммах; ±0.001 нельзя убирать. 🟢
- Источник: `ЗаявкаСервер.УстановитьЦенаСуммаДляРазделитьСчет:432-446`.

## EC-05. Бронь по тарифу «БонШанс» — непересечение с другими БонШанс

- **Условие:** бронь `БонШанс = Истина` на номер, где уже есть другая бронь `БонШанс` на тот же час.
- **Поведение легаси:** в запрос занятости добавляется `И БонШанс = ЛОЖЬ` ⇒ БонШанс-резервы не учитываются как конфликт ⇒ номер считается доступным. 🟡
- **Ожидаемо:** БонШанс-брони могут накладываться друг на друга, но конфликтуют с обычными резервами. Подтвердить бизнес-смысл оверселла по БонШанс. 🟡
- Источник: `ДокументыСервер.ЗанятостьНомераПроверить`; `flowcharts/Бронирование-ЗанятостьНомераПроверить.md`.

## EC-06. Суточная/вырожденная бронь (РезервС = РезервПо)

- **Условие:** даты начала и конца резерва совпадают, либо расчётный конец оказался раньше начала.
- **Поведение легаси:** окно расширяется до +24ч; при вырожденном интервале принудительно ставится 13:00–18:00; `ТемпПо = ТемпПо − 1`. 🟡
- **Ожидаемо:** однодневный «дневной отдых» резервирует корректное окно, проведение не падает на пустом интервале. Магические часы требуют подтверждения. 🟡
- Источник: `ObjectModule.bsl:23-40`.

## EC-07. Отключённый код запроса к MS SQL

- **Условие:** вызов `ВыполнитьЗапросСайт` (исторический прямой запрос к внешней MS SQL).
- **Поведение легаси:** функция возвращает `Неопределено` в первой строке (фактически отключена), но содержит хардкод строки подключения с паролем (`Password=bf02a805`). 🔴
- **Ожидаемо:** НЕ воспроизводить; интеграция с внешним каналом идёт через `ЗаявкаСайт` (обмен), а не прямой SQL. См. `questions.md`. 🔴
- Источник: `ObjectModule.bsl:402-443`.
