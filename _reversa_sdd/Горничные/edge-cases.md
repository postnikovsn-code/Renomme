## EC-01. Отпуск пересекает границы расчётного периода

**Контекст.** Зарплата считается за период `ДН..ДК` (обычно календарный месяц). У горничной в ТЧ `Отпуска` могут быть строки, чьи интервалы по-разному соотносятся с `ДН..ДК`: целиком внутри, целиком охватывают период, заходят слева (начались до `ДН`, кончаются внутри), заходят справа (начались внутри, кончаются после `ДК`). От числа «дней отпуска внутри периода» зависят и оклад (`РасчётныеДни = ДнейПериода − ДниОтпуска`), и отпускные, и надбавка за стаж (считается на `РасчётныеДни`).

**Текущее поведение легаси.** `КоличествоРасчетныхДней`/`СуммаОклад` обрабатывают пересечение **4 ветвями** (отпуск внутри / охватывает период / пересекает начало / пересекает конец) и вычисляют пересечённые дни отпуска; затем `Оклад_И = Окр(Оклад × (ДнейПериода − ДниОтпуска) / ДнейВМесяце)`, где `ДнейВМесяце = День(КонецМесяца(МесяцРасчета))`. Отпускные: `Окр(ДнейОтпускаВпериоде × Горничная.Отпуск / Горничная.ВсегоДнейОтпуска)`. 🟢

**Ожидаемое.** Любая из 4 конфигураций пересечения даёт корректное число дней отпуска внутри `ДН..ДК` (без двойного учёта и без отрицательных дней); при `ДниОтпуска ≥ ДнейПериода` оклад → 0, не уходит в минус; при `Горничная.ВсегоДнейОтпуска = 0` деление на ноль в отпускных не происходит (нужна явная защита). 🟡

**Легаси.** `ПСН_РЕНОМЕ__АУДИТ/src/Documents/ГорничныеЗарплата/Forms/ФормаДокумента/Module.bsl` — `СуммаОклад`/`КоличествоРасчетныхДней` (927-977), `СуммаОтпуск` (отпускные); `code-analysis.md` §2.2, §2.4.

**Доверие:** 🟢 (4 ветви подтверждены) / 🟡 (защита от деления на ноль в отпускных не прочитана построчно — кандидат на проверку).

## EC-02. COM-база горничных недоступна при обмене

**Контекст.** Все процедуры загрузки/выгрузки идут через синхронное COM-соединение `V83.COMConnector` к отдельной файловой базе «Горничные». Сценарии недоступности: путь `Константа.Папка_Горничные` не задан; файловая база занята/недоступна; служба/диск отвалились; соединение из кэша «протухло».

**Текущее поведение легаси.** `Соединение()` (1-46):
- Если `Папка_Горничные` пуст → `Сообщить("Не настроена папка Горничные")` и возврат `Неопределено` (14-18). 🟢
- Если `COMConnector.Connect(...)` бросает исключение → `Сообщить("Ошибка подключения к БД Горничные...")` и возврат `Неопределено` (25-30). 🟢
- Кэш-соединение проверяется «пингом» `Соединение.ОбменГорничныеСервер.ПроверкаСоединения()`; при ошибке адрес во временном хранилище сбрасывается, счётчик попыток +1 и `Перейти ~Соединение` — до 3 повторов, далее возврат `Неопределено` (4-5, 37-45). 🟢
- Вызывающие процедуры (`Загрузить*`) при `Соединение() = Неопределено` выводят сообщение «Нет связи…» и выходят без изменения данных. 🟢
- Сама COM-выгрузка ТЗ обёрнута в `Попытка` с **подавлением** ошибки (пустой/молчащий `Исключение`) — сбой выгрузки может пройти незаметно (загрузка отработает по пустой ТЗ). 🟡

**Ожидаемое.** При недоступности COM ни один документ/справочник «ОТЕЛЬ» не изменяется; оператор получает явное сообщение; повтор до 3 раз с переподключением; расчёт зарплаты, запущенный с дозагрузкой, не должен падать — продолжает по уже имеющимся данным. Подавление ошибок выгрузки (🟡) маскирует частичный сбой обмена — желательно журналировать.

**Легаси.** `ПСН_РЕНОМЕ__АУДИТ/src/CommonModules/ОбменГорничныеСервер/Module.bsl` — `Соединение()` (1-46), точки выхода в `ЗагрузитьОбслуживаниеНомеров` (120-128), подавление при выгрузке ТЗ (130-136).

**Доверие:** 🟢 (ретраи, выходы, кэш) / 🟡 (молчаливое подавление ошибок выгрузки).

## EC-03. Ручная корректировка значений зарплаты (модель И/Р/Э/Есть)

**Контекст.** Оператор может вручную править рассчитанные суммы и количества на форме зарплаты. Каждый показатель имеет 4 представления: `_И` (исходное, рассчитано системой), `_Р` (ручная дельта/значение), `_Э` (эффективное, идёт в итог), `_Есть` (флаг «значение заменено целиком вручную»). Два разных типа показателей ведут себя по-разному: фиксированные суммы (оклад, надбавки) — «замена»; количества уборок — «аддитивная корректировка».

**Текущее поведение легаси.**
- Сведение (`ОбновитьСтрокаСуммы`, 1021-1094): для сумм `Поле_Э = ?(Поле_Есть, Поле_Р, Поле_И)`; для количеств `Кол_Э = Кол_И + Кол_Р`, затем `Сумма = Кол_Э × Цена`. 🟢
- Ручной ввод в `_Э` (`...ПриИзменении`): для «замены» пишется `_Р = _Э` и `_Есть = Истина`; для «количества» `_Р = _Э − _И` (сохраняется именно дельта). 🟢
- При повторном пересчёте `_И` обновляется системой, а `_Р/_Есть` сохраняются → ручная правка переживает пересчёт. 🟡

**Ожидаемое.** Повторный запуск расчёта не затирает ручные правки: для «замены» итог берёт `_Р`; для «количества» к новому `_И` прибавляется ранее введённая дельта `_Р`. Сброс правки = очистка `_Р` и `_Есть`. При `_Есть=Ложь` и `_Р=0` поведение тождественно «как рассчитала система».

**Легаси.** `ПСН_РЕНОМЕ__АУДИТ/src/Documents/ГорничныеЗарплата/Forms/ФормаДокумента/Module.bsl` — `ОбновитьСтрокаСуммы` (1021-1094), обработчики `..._ПриИзменении`; `code-analysis.md` §2.1.

**Доверие:** 🟢 (формулы сведения и записи дельты) / 🟡 (сохранность правок между пересчётами выведена, не трассирована построчно для всех полей).

## EC-04. Эхо двусторонней синхронизации (`ОбменДанными.Загрузка`)

**Контекст.** Справочник `Горничные` (и помещения/минибар/комплектации) синхронизируется в обе стороны: «ОТЕЛЬ» → БД горничных при записи карточки, и БД горничных → «ОТЕЛЬ» через входящие COM-вызовы. Без защиты входящая запись сразу спровоцировала бы обратную выгрузку, та — новую входящую, и т.д. (бесконечный цикл «эха»).

**Текущее поведение легаси.**
- Входящие процедуры (`ОбновитьГорничныеОтель`/`...Помещения...`/`...НоменклатураМиниБара...`/`...Комплектация...`) пишут объект с флагом `ОбменДанными.Загрузка = Истина` (722, 749, 776, 802). 🟢
- `Catalog.Горничные.ObjectModule.ПередЗаписью`: если `ОбменДанными.Загрузка = Истина` (или новый объект) → `ПроверкаОбмена = Ложь`, обратная выгрузка не планируется (6, 33). 🟢
- `ПриЗаписи`: выгрузка `ОбновитьГорничнаяГорничные(ЭтотОбъект)` выполняется только при `ПроверкаОбмена = Истина`. 🟢

**Ожидаемое.** Запись, пришедшая из обмена, фиксируется в «ОТЕЛЬ» и **не** выгружается обратно — цикл разорван за один проход. Локальная (ручная) запись карточки выгружается в БД горничных (при выполнении прочих условий, см. EC-05/правила). 🟢

**Легаси.** `ПСН_РЕНОМЕ__АУДИТ/src/Catalogs/Горничные/ObjectModule.bsl` (6, 33); входящие процедуры в `ПСН_РЕНОМЕ__АУДИТ/src/CommonModules/ОбменГорничныеСервер/Module.bsl` (722, 749, 776, 802).

**Доверие:** 🟢.

## EC-05. Баг `КоличествоЧасовНаКлиенте` — `* 8` вместо `ДлинаСмены`

**Контекст.** Количество отработанных часов = число смен × длина смены горничной. Есть два расчёта: серверный `КоличествоЧасов` (использует реквизит `Горничная.ДлинаСмены`) и клиентский `КоличествоЧасовНаКлиенте`, который должен делать то же.

**Текущее поведение легаси.** Клиентская функция **читает** `ДлинаСмены` (`ОбщийФункционалСервер.ЗначениеРеквизитаНаСервере(Строка.Горничная, "ДлинаСмены")`), проверяет `Если ДлинаСмены = 0 Тогда Возврат 0`, но затем **игнорирует её** и считает `КоличествоЧасов = КоличествоСмен * 8` — захардкоженная «8» вместо прочитанной `ДлинаСмены`. Серверный вариант использует `ДлинаСмены` корректно. Для горничных с `ДлинаСмены ≠ 8` клиент и сервер дают **разные** часы. 🔴

**Ожидаемое.** Клиентский расчёт должен совпадать с серверным: `КоличествоЧасов = КоличествоСмен × ДлинаСмены` (а не `× 8`). При `ДлинаСмены = 0` → 0 (этот guard уже есть и корректен). 🟢 (ожидаемое поведение)

**Легаси.** `ПСН_РЕНОМЕ__АУДИТ/src/Documents/ГорничныеЗарплата/Forms/ФормаДокумента/Module.bsl` — `КоличествоЧасовНаКлиенте` (846-853): строка 848 читает `ДлинаСмены`, строка 851 `КоличествоЧасов = КоличествоСмен * 8`; ср. серверный `КоличествоЧасов`/`Возврат` (≈843). `code-analysis.md` §2.5.

**Доверие:** 🔴 (подтверждённый баг; см. `questions.md` — нужна валидация: верна ли `ДлинаСмены` как единственный источник, либо «8» — намеренный дефолт для части профилей).

## EC-06. Документ уборки с `РучноеИзменение = Истина` при повторной загрузке

**Контекст.** Факты уборки загружаются из БД горничных и могут перезагружаться многократно за тот же период (идемпотентность по бизнес-ключу). Если оператор вручную поправил загруженный документ, повторная загрузка не должна затереть правку.

**Текущее поведение легаси.** При поиске существующего документа по ключу (ДатаОбслуживания + НомерОбслуживания_пп + НомерГорничные): если найденный документ имеет `РучноеИзменение = Истина` → `Продолжить` (строка пропускается, документ не трогается) (214). 🟢

**Ожидаемое.** Документ с `РучноеИзменение = Истина` сохраняется без изменений при любой повторной загрузке; новые (не правленные вручную) факты создаются/обновляются как обычно. 🟢

**Легаси.** `ПСН_РЕНОМЕ__АУДИТ/src/CommonModules/ОбменГорничныеСервер/Module.bsl` — `ЗагрузитьОбслуживаниеНомеров` (214); те же правила для `...Помещения` (`code-analysis.md` §2.9).

**Доверие:** 🟢.

## EC-07. Не найден номер / номенклатура / цена при загрузке (вспомогательный)

**Контекст.** При загрузке уборки строка ссылается на номер (через `НомерГорничные`) и позиции минибара (по коду). Эти сущности могут отсутствовать в «ОТЕЛЬ».

**Текущее поведение легаси.**
- Номер не найден в `НомернойФонд`/`ГорничныеНомера` → строка пропускается с сообщением (193-209). 🟢
- При создании задания (`СоздатьЗаявку`), если у номера не заполнен `НомерГорничные` → сообщение и задание не создаётся (54-62). 🟢
- Минибар: `НоменклатураМиниБара.НайтиПоКоду`; при ненайденной цене — 0 с сообщением (288-299). 🟢
- Горничная не найдена по наименованию → **авто-создаётся** (264-275). 🟢

**Ожидаемое.** Ненайденные номера/номенклатура не срывают всю загрузку — обрабатывается построчно с сообщением; горничная создаётся автоматически (риск дублей при расхождении наименований — см. `questions.md`). 🟡

**Легаси.** `ПСН_РЕНОМЕ__АУДИТ/src/CommonModules/ОбменГорничныеСервер/Module.bsl` (54-62, 193-209, 264-275, 288-299).

**Доверие:** 🟢 (поведение) / 🟡 (риск дублей горничных при авто-создании по наименованию).
