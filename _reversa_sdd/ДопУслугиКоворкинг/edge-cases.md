# Доп. услуги и коворкинг — Крайние случаи

> Файл `edge-cases.md` (doc_level=detalhado). Крайние случаи, выведенные из легаси-кода и flowcharts. Шкала: 🟢 подтверждено / 🟡 выведено / 🔴 пробел.

## EC-01 — Конфликт со счётом приоритетнее конфликта с заявкой 🟢

**Контекст.** Заявка резервирует «черновой» период, счёт — фактический. Двухпроходная проверка (`ЗанятостьНомераКоворкингПроверить`, `КоворкингСервер:111-178`): 1-й проход ищет пересечение со *счетами* других заявок (пропуская записи-заявки), 2-й — среди заявок.

**Сценарий.** Рабочее место имеет в периоде 02.06 одновременно черновой резерв заявки B и фактический резерв счёта заявки C. Новая заявка A пересекается по 02.06.

**Ожидаемое поведение.** Конфликт фиксируется со СЧЁТОМ (заявка C) в 1-м проходе — `Регистратор` = счёт C; проведение A отклоняется (`Отказ=Истина`), даже если по заявке B тоже есть пересечение. Заявка исключает счета собственной заявки; счёт исключает себя и родительскую заявку.

**Риск/проверка.** Если изменить порядок проходов или забыть исключения собственных документов — ложные конфликты при перепроведении. Тест: TT-02.

## EC-02 — Несовпадение долга при списании допуслуг (СуммаДолг ≠ СуммаСчетДолг) 🟢

**Контекст.** Предохранитель DK-06 (`СписаниеДопУслуг/Forms/ФормаДокумента/Module.bsl`; flowchart `…-СписаниеДопУслуг.md`): списание создаётся только если долг по `ЗаявкаНаБронирование.ДопУслуги` (`ВСчет=Истина`) совпадает с долгом в `СчетаДетальноДолги` (`Услуга=Истина`).

**Сценарий.** Долг допуслуг по брони = 1500, а долг в счетах брони = 1200 (рассинхронизация, например после ручной правки счёта).

**Ожидаемое поведение.** Строка попадает в ТЧ `Ошибки` с текстом «долг доп.услуг <> долг в счетах»; документ оплаты-списания (`ПрочиеОплаты`) НЕ создаётся; распределения по долгам брони нет. Дополнительно: если `СуммаДолг=СуммаОплатыДолг` (нечего списывать) — строка просто пропускается (`Продолжить`).

**Риск/проверка.** Без предохранителя — двойное закрытие/некорректное распределение долга. Тест: TT-07.

## EC-03 — Разрыв в цепочке счетов / выход за период заявки 🟢

**Контекст.** Счета заявки идут непрерывной цепочкой: `СледующийСчетДатаС = МАКС(ДатаПо непомеченных счетов)+1 день` (DK-03, `КоворкингСервер:326-345`). Для посуточного — стоп, если `СледующийСчетДатаС > Заявка.ДатаПо`.

**Сценарий A (стоп цепочки).** Заявка ДЕНЬ с `ДатаПо=20.06`; последний счёт закрывает 20.06. Оператор формирует следующий счёт.
**Ожидаемое.** `СледующийСчетДатаС (21.06) > Заявка.ДатаПо (20.06)` → предупреждение, счёт не создаётся (flowchart `…-ДобавитьСчет.md`).

**Сценарий B (потенциальный разрыв).** Один из промежуточных счетов помечен на удаление → `МАКС(ДатаПо)` берётся по *непомеченным*, новый счёт продолжит цепочку от последнего непомеченного, оставляя «дыру» в покрытии периода.
**Ожидаемое (🟡).** Легаси не валидирует целостность покрытия — допускает разрыв; цепочка опирается только на максимум `ДатаПо`. Требует валидации (questions.md).

**Риск/проверка.** Пропуск дней аренды без счёта (недосчёт долга). Тесты: TT-03, TT-04.

## EC-04 — Раскрытие месяца аренды в десятки записей РС 🟢

**Контекст.** DK-01: `ОбработкаПроведения` пишет по одной записи `ЗанятостьНомеровКоворкинг` на каждый час/день периода без агрегации (`КоворкингЗаявка/КоворкингСчета ObjectModule.bsl`; flowchart `…-ОбработкаПроведенияКоворкинг.md`).

**Сценарий.** Посуточная аренда на 31 день (период МЕСЯЦ): цикл `Пока ТемпС<=ТемпПо` с шагом 86400 c.

**Ожидаемое.** Создаётся 31 запись РС на один документ; для почасовой аренды на сутки (24 ч) — 24 записи. На длинных периодах/множестве мест — заметная нагрузка на проведение и объём РС.

**Риск/проверка.** Производительность проведения и перепроведения; объём `ЗанятостьНомеровКоворкинг`. Кандидат на агрегацию (интервал вместо слотов) при переподнятии — см. questions.md Q-03.

## EC-05 — Расчёт `СчетДатаПо` для МЕСЯЦ от произвольного числа 🟢

**Контекст.** DK-04 (`СчетДатаПо`, `КоворкингСервер:455-505`): МЕСЯЦ — если день `ДатаС`=1 → конец месяца; иначе → та же дата следующего месяца −1 день (с переносом года при Месяц>12).

**Сценарий.** `ДатаС=31.01`, период МЕСЯЦ. «Та же дата следующего месяца» — 31.02, которой не существует.
**Ожидаемое (🟡).** Поведение для несуществующей даты следующего месяца (29/30/31 при коротком феврале) кодом явно не описано в фактуре — потенциальный краевой дефект арифметики дат. Требует валидации (questions.md).

**Риск/проверка.** Неверная `ДатаПо` для аренды, начатой в конце длинного месяца. Тест: расширить TT-03 граничными датами.

## EC-06 — Период аренды вне набора {МЕСЯЦ, НЕДЕЛЯ, ДЕНЬ, ЧАС} 🟢

**Контекст.** `СчетДатаПо` возвращает `Неопределено` для неизвестного `ПериодАренды`; `ДобавитьСчетДни` тогда возвращает `Неопределено`.

**Сценарий.** `ПериодАренды` пуст или содержит нераспознанный код.
**Ожидаемое.** Счёт не формируется (выход по `Неопределено`); пользователю — отсутствие результата/предупреждение. `Количество` жёстко = 1 действует только для распознанных периодов.

**Риск/проверка.** Молчаливый отказ формирования счёта. Валидация заполнения `ПериодАренды` до формирования.

## EC-07 — Частичный возврат больше распределённой суммы 🟢

**Контекст.** `УменьшитьОплатыКоворкингСчетаСуммаВозврата` (`КоворкингСервер:2-53`).

**Сценарий.** Сумма возврата ≥ распределённой суммы строки.
**Ожидаемое.** Строки `ДокументыОплаты`/`РаспределениеОплатКоворкинг` удаляются целиком + `ОплатыОбщееСервер.УдалитьДокументОплатыДокументДолгДолгОплата`; если меньше — уменьшение строк по очереди (последняя частично) + `ДобавитьЗаменитьДокументОплатыДолгОплата`. `СуммаОплачено` шапки пересчитывается в `ПередЗаписью`.

**Риск/проверка.** Расхождение `СуммаОплачено` при ошибке внутри транзакции без `Попытка` (Q-02). Тест: TT-08.
