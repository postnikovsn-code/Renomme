# ADR 0002 — Почасовая модель занятости номеров (одна запись РС на час)

- **Статус:** Принято (исторически) · 🟢 ПОДТВЕРЖДЕНО кодом (как решение — 🟡)
- **Дата:** неизвестна
- **Модуль:** Бронирование / Размещение / Коворкинг

## Контекст

Гостиница торгует не только сутками, но и частичными сутками (ранний заезд, поздний выезд, дневной отдых, почасовой коворкинг). Нужна модель доступности с точностью до часа.

Свидетельства:
- `ДокументыСервер.ЗанятостьНомераПериодРезерва` маппит времена заезда/выезда в часы и формирует почасовой интервал; на каждый час создаётся отдельная запись РС `ЗанятостьНомеров` (BR-04). 🟢
- Проверка занятости — пересечение по часам другого регистратора (BR-02). 🟢
- Та же модель повторена для коворкинга (`ЗанятостьНомеровКоворкинг`, по записи на час/день, DK-01). 🟢
- Особый случай вырожденного интервала → окно 13:00–18:00 (дневной отдых, BR-05). 🟢

## Решение

Хранить доступность как дискретный почасовой (для коворкинга — почасовой/посуточный) набор записей регистра сведений, подчинённого регистратору (`writeMode=RecorderSubordinate`), с измерениями Номер/ПериодРезерва и инкрементом `Номер_пп` для сосуществования резервов в одном часе.

## Рассмотренные альтернативы

- **Интервальная модель (хранить пары дата-С/дата-По).** Отклонено: проверка пересечений интервалов сложнее в запросах 1С; почасовая «развёртка» делает пересечение тривиальным сравнением записей.
- **Посуточная сетка (одна запись на сутки).** Отклонено: не поддерживает ранний заезд/поздний выезд/дневной отдых/почасовой коворкинг — а это ключевые продукты гостиницы.
- **Внешний движок доступности.** Отклонено: избыточно, всё решается средствами платформы.

## Последствия

- ➕ Простая и быстрая проверка пересечений; единый паттерн для номеров и коворкинга; естественная основа шахматки и аудита.
- ➕ Поддержка частичных суток и сложной тарификации полусуток (ADR-смежно: расчётный час в аудите).
- ➖ Объём записей: длинная посуточная аренда (месяц) = десятки записей РС на документ; нет агрегации (DK-01, перф-замечание).
- ➖ Захардкоженные магические часы (0/6/12/13/14/18/24) рассыпаны по коду расчёта периода и аудиту тарификации.
- ⚠ Этот инвариант — фундамент домена; при миграции его нужно сохранить или эквивалентно заменить интервальной моделью с корректной обработкой полусуток.
