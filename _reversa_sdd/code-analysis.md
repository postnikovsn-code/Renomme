## Модуль: Бронирование

**Назначение.** Управление жизненным циклом брони номера: приём заявок (со стойки, с сайта, из мессенджеров, из листа ожидания), проверка занятости номерного фонда, резервирование во времени (почасовая сетка), расчёт проживания и допуслуг, формирование счетов и долгов, отправка подтверждений/аннуляций гостю, аналитика глубины бронирования.

**Корневые объекты (seed + расширение по скану `ПСН_РЕНОМЕ__АУДИТ/src`):**

### 1. Поток управления

#### 1.1 `Документ.ЗаявкаНаБронирование.ОбработкаПроведения(Отказ, Режим)` 🟢
Файл: `Documents/ЗаявкаНаБронирование/ObjectModule.bsl:4-140`.

Ключевая процедура проведения. Логика (по порядку):

1. **Валидация.** `Отказ = Не ПроверкаЗаполнения()` — при незаполненных реквизитах отмена записи (`ObjectModule.bsl:5-6`).
2. **Ранний выход** для не-движущих статусов: если `ЛистОжидания` (бул.) истина → `Возврат`; если `Статус = ОтменаБронирования` или `ОтказОтБронирования` → `Возврат` (движения не формируются) (`:8-11`).
3. **Проверка занятости** через `ДокументыСервер.ЗанятостьНомераПроверить(...)`. Если номер занят другим регистратором — сообщение «Номер занят… ЗАПИСЬ ОТМЕНЯЕТСЯ», `Отказ = Истина` (`:13-18`).
4. **Обновление истории клиента**: `ЗаявкаСервер.ОбновитьИсториюКлиента(ЭтотОбъект)` (`:20`).
5. **Формирование движений `ЗанятостьНомеров`**: почасовой цикл `Пока ТемпС < ТемпПо` с шагом 3600 сек, на каждый час — запись резерва (`:61-76`).
6. **Формирование движений `Взаиморасчеты`**: по каждой строке ТЧ `Счета` — расход на сумму долга счёта (`:78-91`).
7. Закомментированный блок исторической логики долгов (`ДобавитьДвиженияДолг`) — мёртвый код (`:96-138`). 🟡 Логика долгов перенесена в `ПередЗаписью`/`ЗаявкаСервер`.

> Регистраторы проведения (из `.mdo`): `AccumulationRegister.Долги`, `Взаиморасчеты`, `ОстаткиПродукции`, `ПродажиТоваров`, `InformationRegister.ЗанятостьНомеров` (`ЗаявкаНаБронирование.mdo:78-82`). 🟢 Фактически в ObjectModule заполняются только `ЗанятостьНомеров` и `Взаиморасчеты`; остальные регистры — наследие/иные пути записи. 🔴 ПРОБЕЛ: где формируются движения `Долги`/`ОстаткиПродукции`/`ПродажиТоваров`.

#### 1.2 `Документ.ЗаявкаНаБронирование.ПередЗаписью(Отказ, РежимЗаписи, РежимПроведения)` 🟢
Файл: `ObjectModule.bsl:158-188`.
- Пересобирает счета: по каждой строке ТЧ `Счета` проверяет наличие детальных долгов; пустые счета удаляются (отложенно через `МассивКУдалению`, чтобы не удалять в цикле обхода) (`:160-181`). Соответствует правилу `DeletingCollectionItem`.
- `ЗаявкаСервер.ОбновитьСчетаСтроки(...)` пересобирает строки счёта; `Счет.Закрыт = ЗаявкаСервер.СчетЗакрытСчетаДетальноДолги(...)`.
- Проставляет `ДатаИзменения = ТекущаяДата()`; для нового объекта — `ДатаСоздания` (`:183-187`).

#### 1.3 `Документ.ЗаявкаНаБронирование.ПередУдалением(Отказ)` 🟢
Файл: `ObjectModule.bsl:203-220`.
- Право на удаление: только если `ПараметрыСеанса.ТекущийПользователь.Админ`; иначе «Удаление документов запрещено», `Отказ = Истина` (`:206-215`). 🟢 бизнес-правило прав.

- `ЗаявкаСервер.УдалитьИсториюКлиента(ЭтотОбъект)`.

#### 1.4 `Документ.ЗаявкаНаБронирование.ПриКопировании(ОбъектКопирования)` 🟢
Файл: `ObjectModule.bsl:265-310`. Сбрасывает оперативные реквизиты (времена, номер, оплата), выставляет `Статус = Бронь`, очищает все движения и табличные части. Защита от копирования «грязной» брони.

#### 1.5 `ДокументыСервер.ЗанятостьНомераПроверить(РезервС, РезервПо, ВремяЗаезда, ВремяВыезда, НомерКуда, БонШанс, ТекущийРегистратор)` 🟢
Файл: `CommonModules/ДокументыСервер/Module.bsl:264-311`. Возвращает структуру `{Результат(Булево), НачалоПериодаРезерва, КонецПериодаРезерва, Регистратор}`.

- Запрос к `РегистрСведений.ЗанятостьНомеров`: занят ли `Номер` в `[ПериодН; ПериодК-1]` другим регистратором (`Регистратор <> ТекущийРегистратор`).
- Если `БонШанс` — динамически добавляет условие `И БонШанс = ЛОЖЬ` (бронь по тарифу «БонШанс» не конфликтует с другими БонШанс). 🟡
- `Результат = Истина` ⇒ номер занят (конфликт найден).

#### 1.6 `ЗаявкаСайт.Форма.ФормаДокумента.СоздатьЗаявкуНаБронирование(Команда)` 🟢
Файл: `Documents/ЗаявкаСайт/Forms/ФормаДокумента/Module.bsl:26-64`.

### 2. Алгоритмы и логика

#### 2.1 Конвертация времён заезда/выезда в почасовой период резерва 🟢
`ДокументыСервер.ЗанятостьНомераПериодРезерва` (`Module.bsl:231-262`). Маппинг перечислений в часы:
- Заезд: `Вр0→0`, `Вр6→6`, `Вр14→14`, `Вр18→18`.
- Выезд: `Вр0→24`, `Вр6→6`, `Вр12→12`, `Вр18→18`.
- `НачалоПериодаРезерва = НачалоЧаса(НачалоДня(РезервС) + Заезд*3600)`; `КонецПериодаРезерва = НачалоЧаса(НачалоДня(РезервПо) + Выезд*3600)`.

Это превращает дату-диапазон брони в **точный почасовой интервал**, по которому `ЗанятостьНомеров` хранит по одной записи на час. 🟢 Ключевой инвариант модели доступности.

#### 2.2 Резервирование «суточной» брони (РезервС = РезервПо) 🟢
`ObjectModule.ОбработкаПроведения:23-40`. Особый случай однодневного резерва: если расчётный `ТемпПо = НачалоДня(ТемпС)`, окно расширяется до +24ч; если `ТемпПо < ТемпС` (вырожденный интервал) — принудительно ставится окно 13:00–18:00. `ТемпПо = ТемпПо - 1` — исключение последнего часа (выезд не занимает целый час). 🟡 Магические часы (13/18) — захардкоженная политика «дневного отдыха».

#### 2.3 Нумерация наложенных резервов `Номер_пп` 🟢
`ObjectModule:70-73`. При формировании почасовых движений ищется существующая запись того же часа/клиента/брони; если есть — `Номер_пп = НайденнаяСтрока.Номер_пп + 1`. Позволяет нескольким резервам сосуществовать в одном часе (разделение измерения `Номер_пп` в регистре). 🟡 Механизм мульти-резерва / переселения.

#### 2.4 Разделение счёта (split-bill) на двух гостей 🟢
`ЗаявкаСервер.УстановитьЦенаСуммаДляРазделитьСчет` (`Module.bsl:432-446`) и аналоги для детальных долгов (`:393-427`).
- При `РазделитьСчет И ЕстьКлиент2`:
  - первый гость (`НеПервый = Ложь`): `Цена = Цена/2 + 0.001`, `Сумма = Сумма/2 + 0.001`;
  - второй гость (`НеПервый = Истина`): `Цена = Цена − Цена/2 − 0.001`.
- `+0.001/−0.001` — приём, чтобы при нечётных суммах гарантировать копейку без потери при округлении (сумма частей = целому). 🟢 Нетривиальное бизнес-правило.
- Существуют две версии (`_1` учитывает `НЕ ЮрЛицо`, основная — закомментировала эту проверку). 🟡 Поведенческое расхождение версий.

#### 2.5 Расчёт глубины бронирования (прогноз спроса) 🟢
`DataProcessors/ГлубинаБронирования/Forms/Форма/Module.bsl` (несколько версий `СформироватьНаСервере*`, основная — `:22-195`).
- По каждому дню периода запрашиваются заявки, считается `РазностьДат` = дни между датой брони и датой заезда.
- Бронь раскладывается по корзинам глубины: `0-1, 2-3, 4-7, 8-14, 15-30, 31-60, >60` дней до заезда (`:96-133`).
- Брони с заездом раньше текущей даты — отдельный счётчик `ПроживанияЗаездРаньше`.
- `ПрогнозЗагрузки = Окр((ИтогоНомеров / КоличествоНомеров) * 100)` — % загрузки от общего числа номеров (`:138`).
- Добавляются `Мероприятия` города на дату (фактор спроса) (`:140-166`).
🔴 ПРОБЕЛ: есть 4 версии функции (`_1`/`_2`/`_3`/без суффикса) с дублирующейся логикой — какая активна, неочевидно.

#### 2.6 Комиссия агентству и наценка B2B 🟢
`ДокументыСервер.СуммаКомиссии` (`Module.bsl:314-353`): если `Заявка.Бронирует.Турагентство`, комиссия = % от суммы проживания без скидки + % от услуг с программным кодом `ПРОЖИВАНИЕ_УСЛУГИ`.
`ДокументыСервер.СуммаВ2В` (`:356-365`): наценка `Окр(Цена/((100−ПроцентВ2В)/100) − Цена) * Количество` для строк с флагом `В2В`.

#### 2.7 Округление цен 🟢
`ДокументыСервер.ОкруглитьЦену = Цел(Цена)`; `ОкруглитьЦену_25` — округление рублёвой части к шагу 0/50/100 по порогам 25/75 (`:374-389`). 🟡 граница с ценообразованием, но вызывается из расчёта брони.

#### 2.8 Денормализация истории клиента 🟢
`ЗаявкаСервер.ОбновитьИсториюКлиента` (`:255-316`): пере-записывает наборы `ИсторияКлиента` и `ИсторияКлиентаДопПожелания`, ключ — `ЗаявкаГУИД = Ссылка.УникальныйИдентификатор()`. Хранит срез брони (даты, номер, статус, доппожелания) для быстрых отчётов/CRM.

### 4. Метаданные и конфигурации

- **Машина состояний брони** (`Enum.СтатусБрони`): `Бронь → Проживает → Выехал`; ветви отмены: `ОтменаБронирования`, `ОтказОтБронирования`, `Неустойка`. Движущими являются только статусы кроме двух отмен и листа ожидания (см. 1.1). 🟢
- **Предопределённые каналы** (`КаналыБронирования`): WhatsApp, МобильноеПриложение, НашСайт, ОтСтойки, Телефон, Трэвеллайн, ЭлектроннаяПочта. 🟢
- **Предопределённые типы** (`ТипБронирования`): Агент, КорпоративныйКлиент, Ремонт, ЧастныйГость. 🟢
- **Сетка времени** (`ВремяЗаезда`/`ВремяВыезда`) задаёт почасовую гранулярность доступности.
- Дата перехода на новый календарь цен: `ДокументыСервер.ДатаПереходаНаНовыйКалендарьЦен = '20240401'` — хардкод-флаг ветвления старой/новой логики цен (`Module.bsl:369-371`). 🟢
- **Тариф «БонШанс»** — отдельная ценовая программа с собственным правилом непересечения в занятости (флаг-ресурс `БонШанс` в `ЗанятостьНомеров`). 🟡

- Конвертация `ЗаявкаСайт → ЗаявкаНаБронирование` 🟢: форма брони при `ПриСозданииНаСервере` принимает параметр `ЗаявкаСайт`, затем `ЗаполнитьЗаявкуИзЗаявкаСайтДействие` (`Forms/ФормаДокумента/Module.bsl:400-456`) выполняет: загрузку объекта сайта (`ЗаполнитьЗаявкаСайтОбъект`), поиск/сопоставление клиента по ФИО/телефону (`ПолучитьКлиентИзЗаявкаСайтНаСервере` — `ТипСовпадения` 1=нет, 2=несколько, иначе один), затем `ЗаполнитьЗаявкуИзЗаявкаСайт` и проверку заполнения проживания. 🟡 При неоднозначном клиенте пользователю предлагается создать/выбрать клиента вручную.
- 🔴 ПРОБЕЛ: не прочитано тело `ЗаполнитьЗаявкуИзЗаявкаСайт` (точный маппинг полей сайта на реквизиты брони) и `РасчетПроживания`/`ЗаполнитьТаблицуПроживания` (расчёт сумм проживания — граница с ценообразованием).

### 1. Поток управления

#### 1.1 `Catalog.НомернойФонд.ObjectModule` — `ПередЗаписью(Отказ)` 🟢
`Catalogs/НомернойФонд/ObjectModule.bsl:2-27`. Алгоритм:
1. Сохраняет старое значение `НомерГорничные` из БД (`ЭтотОбъект.Ссылка.НомерГорничные`) — для отслеживания переименования.
2. Вызывает `ОбновитьГорничныеНомера(старое, ЭтотОбъект)` — поддержание справочника `ГорничныеНомера` в актуальном виде (создаёт/находит по реквизиту, синхронизирует Наименование/ПометкаУдаления).
3. Если константа `ОбменСГорничными = Ложь` или не задана `Папка_Горничные` — выход.
4. Открывает внешнее COM-соединение `ОбменГорничныеСервер.Соединение()` и зеркалит карточку номера (`НомерГорничные`, `ПометкаУдаления`, `Наименование`) во внешнюю БД горничных через `Соединение.ОбменГорничныеСервер.ОбновитьНомерГорничные(...)`. Ошибка соединения подавляется `Попытка/Сообщить`. 🟡 граница с модулем «Горничные».

#### 1.2 `Catalog.НомернойФонд.ObjectModule` — `ОбновитьГорничныеНомера(СтароеЗначение, ТекущийОбъект)` 🟢
`ObjectModule.bsl:29-55`. Условная логика выбора объекта `ГорничныеНомера`:
- если задано старое значение → ищет по нему (`НайтиПоРеквизиту`);
- иначе если задано новое `НомерГорничные` → ищет по нему;
- иначе выход.
Если не найдено — создаёт новый элемент; затем перезаписывает поля и `Записать()`. 🔴 запись без транзакции/обработки исключения внутри метода.

#### 1.3 `Document.ОсмотрНомера.ObjectModule` — `ОбработкаПроведения(Отказ, Режим)` 🟢
`Documents/ОсмотрНомера/ObjectModule.bsl:2-28` (код сгенерирован конструктором движений). Логика:
- если ТЧ `Замечания` пуста → одна запись в РС `ЗамечанияПоНомерам` с `Замечание = Справочники.Замечания.Нет` (предопределённый «нет замечаний»);
- иначе цикл по строкам ТЧ → запись на каждое замечание.
Каждая запись: `Комната ← Комната`, `ВремяПроверки ← Дата` документа, `Комментарий ← Комментарий`, `Супервайзер ← ПостПроверка` (булев флаг постпроверки). Движения удаляются автоматически при отмене проведения (`registerRecordsDeletion=AutoDelete`).

#### 1.4 Шахматка размещения — `DataProcessor.Интерфейс.Форма` 🟢
`DataProcessors/Интерфейс/Forms/Форма/Module.bsl`. Две функции рисуют сетку «номер × время» в табличном документе `ПолеОтчета`:
- `ВывестиШахматку(ДатаС, ДатаПо, Детализация)` (стр. 1096-1432) — основная;
- `ВывестиШахматкуЧасы(ДатаС, ДатаПо)` (стр. 134-461) — почасовой вариант.

Алгоритм `ВывестиШахматку` (ключевое для номерного фонда):
1. Запрос к РС `ЗанятостьНомеров` (Зарезервирован=Истина, статус ≠ ОтказОтБронирования) за период → таблица клиентов с колонкой `Цвет`.
2. **Раскраска клиента по статусу брони** (см. алгоритм 2.1).
3. Шапка: горизонтальная ось — дни или 6-часовые интервалы (`шаг = 86400` для «День», `3600*6` иначе); косметическая замена метки «12:00»→«14:00».
4. `СпрНомеров = Справочники.НомернойФонд.Выбрать()` — перебор всех комнат (пропуск помеченных на удаление) → каждая комната = строка шахматки.
5. Заголовок строки: `Наименование + " / РК"` (если РаздельныеКровати) `+ "/ Б "` (если Балкон); фон строки = цвет номера (`ЦветНомераR/G/B`), цвет текста подбирается `ОбщийФункционалСервер.ПолучитьЦветТекстаПоЦветуФона`.
6. Расшифровка ячейки заголовка = ссылка на номер (для контекстного меню/выбора).
7. Внутренний цикл по периодам: поиск занятости `НайтиСтроки({ПериодРезерва, Номер})` в выгрузке РС → закраска ячейки цветом клиента. 🟡 детали внутреннего цикла (граница с Бронированием).

#### 1.5 Загрузчики номеров — `DataProcessor.ЗагрузкаНомеров{Лайв,Реноме,Чехов}.Форма` 🟢
Три обработки **структурно идентичны** (отличаются только строкой подключения). Каждая содержит 3 команды + хелпер:
- `ЗагрузитьКатегорииНомеровНаСервере()` — COM-запрос категорий из внешней базы, создание отсутствующих по коду;
- `ЗагрузитьНомераНаСервере()` — COM-запрос номеров, создание отсутствующих, маппинг реквизитов и категории (по `НайтиПоКоду(КатегорияНомера.Код)`);
- `ЗагрузитьДанныеНомеровНаСервере()` — догрузка связей (`ОбщийКондиционер`, ТЧ `Соседи`);
- `ИмяЗначенияПеречисление(Соединение, Значение)` — резолв имени значения перечисления `КатегорииХостела` через метаданные внешней базы по индексу.

Поток одинаков: `Новый COMОбъект("V83.COMConnector")` → `Connect(строка)` (ошибка → `Сообщить` + выход) → `База.NewObject("Запрос")` → `Выполнить().Выгрузить()` → цикл создания/обновления через менеджер справочника. 🔴 строки подключения с логином/паролем захардкожены (см. ПРОБЕЛы).

#### 1.6 `DataProcessor.ЗаменаНомеровВЗаявках.Форма` — `ЗаменитьНаСервере()` 🟢
`Forms/Форма/Module.bsl:3-29`. Клиентская обёртка `Заменить` валидирует заполнение `СтарыйНомер`/`НовыйНомер`. Серверная: перебор ВСЕХ `Документы.ЗаявкаНаБронирование.Выбрать()`, для строк с `НомерВРезерв = СтарыйНомер` → подмена на `НовыйНомер` и `Записать(РежимЗаписиДокумента.Проведение)` с подавлением ошибки. 🔴 полный перебор без отбора в запросе (антипаттерн производительности), перепроведение каждого документа.

### 2. Алгоритмы и логика

#### 2.1 Раскраска клиента на шахматке 🟢
`Интерфейс/Форма/Module.bsl:1124-1140`. Приоритет цвета:
1. Статус `Проживает` → белый `(255,255,255)`;
2. Статус `Выехал` → серо-бежевый `(231,227,217)`;
3. Статус `ОтказОтБронирования` → тёмный лосось `(233,150,122)`;
4. Иначе: цвет регистратора (`Регистратор.ЦветR/G/B`), затем цвет клиента (`Клиент.ЦветR/G/B`), иначе `СлучайныйЦвет(ТЗКлиентов)` (стр. 1077-1094) — генерация неконфликтного случайного цвета.

#### 2.2 Раскраска строки-номера 🟢
Фон заголовка строки = собственный цвет номера `ЦветНомераR/G/B` (если сумма ≠ 0). Это денормализованный визуальный признак комнаты, отдельный от цвета брони.

#### 2.3 Маппинг категории при импорте 🟢
В загрузчиках категория номера сопоставляется по коду: `Справочники.КатегорииНомеров.НайтиПоКоду(Строка.КатегорияНомера.Код)`. Перечисление `КатегорияХостел` мапится через рефлексию метаданных внешней базы (`ИмяЗначенияПеречисление`) → `Перечисления.КатегорииХостела[имя]` в `Попытка` (несовпадение имени подавляется).

#### 2.4 Резолв значения перечисления по индексу (рефлексия COM) 🟢
`ИмяЗначениеПеречисление`: берёт имя перечисления из `Значение.Метаданные().Имя`, индекс через `Соединение.Перечисления[имя].Индекс(Значение)`, затем линейный проход `ЗначенияПеречисления` до совпадения индекса → возвращает `.Имя`. Обходной приём кросс-базовой передачи enum-значений.

#### 2.5 Структура занятости как «слой» номерного фонда 🟢
`ЗанятостьНомеров` — это срез доступности комнаты по часам: измерения `Номер`, `Клиент`, `ПериодРезерва` (Date, час), `Номер_пп`; ресурсы `Зарезервирован`, `БонШанс`; `writeMode = RecorderSubordinate` (подчинён регистратору `ЗаявкаНаБронирование`). Шахматка читает именно этот регистр. Алгоритм формирования периода/записей — в модуле «Бронирование» (`ДокументыСервер.ЗанятостьНомераПериодРезерва` / `ЗанятостьНомераПроверить`).

### 3. Структуры данных
Полные таблицы реквизитов — в `data-dictionary.md`, секция «Модуль: Размещение и номерной фонд». Ключевые сущности: `НомернойФонд` (16 реквизитов + ТЧ `Соседи`), `КатегорииНомеров` (13 реквизитов, в т.ч. 10 базовых тарифов), `КатегорииНомеровСайт`, `ОсмотрНомера` (+ТЧ `Замечания`), РС `ЗанятостьНомеров`/`ЗамечанияПоНомерам`/`ПроданныеНомера`.

### 4. Метаданные и конфигурации
- `Enum.КатегорииХостела`: `М`, `Ж`, `О` (пол размещения в хостеле). 🟢
- `Catalog.НомернойФонд`: иерархический (2 уровня, `foldersOnTop`) — здания/блоки моделируются папками; **этаж** — числовой реквизит `Этаж` (precision 2). 🟢
- Признаки-тумблеры номера: `Курящий`, `РаздельныеКровати`, `Балкон`, `Хостел`, `Коворкинг` (булевы). 🟢
- `ОбщийКондиционер` (`CatalogRef.НомернойФонд`) — ссылка номер→номер: группировка комнат на один кондиционер. 🟢
- ТЧ `Соседи` (`СоседнийНомер: CatalogRef.НомернойФонд`) — граф смежности комнат. 🟢
- `ОсновнойНомер` (Number) — связь номера с «основным» (слияние/составные номера). 🟡
- Денормализованный цвет номера `ЦветНомераR/G/B` (Number) — визуализация на шахматке. 🟢
- Константы интеграции с горничными: `ОбменСГорничными` (Булево), `Папка_Горничные` — управляют зеркалированием номеров (граница). 🟢
- Предопределённый элемент `Справочники.Замечания.Нет` — «нет замечаний» при осмотре. 🟢

#### Технический долг / 🔴 ПРОБЕЛы
- 🔴 **Хардкод секретов**: во всех трёх загрузчиках строки COM-подключения с логином/паролем — `ЗагрузкаНомеровЛайв` `File="D:\DB";Usr="Администратор";Pwd="123"` (`Module.bsl:10,58,165`); `Реноме` `C:\_Base1C\BASE` (`:10`); `Чехов` `C:\_Base1C\InfoBase` (`:10`) и `D:\DB` (`:136`). Нарушения `UsingHardcodePath`, `UsingHardcodeSecretInformation`.
- 🔴 **Дубли-версии обработок**: `ОтчетПоЗагрузкеНомеров_Исходный` vs `ОтчетПоЗагрузкеНомеров`; в `Интерфейс` — `Оповещение_OLD`, `ФормаФинансы_OLD`, `ФормаФинансы_Старая`; в коде шахматки — `ПересеченияНомеров__`, `ПолеОтчетаВыбор__`, `ТарифыНажатие___` (мёртвые/устаревшие версии).
- 🔴 **Баг в загрузчиках Лайв/Чехов** (`ЗагрузитьДанныеНомеровНаСервере`): цикл соседей идёт по `ТЗ.Соседи` вместо `Строка.Соседи`, и присваивание `НоваяСтрокаСоседиСоседнийНомер = ...` без точки — поле строки ТЧ не заполняется (опечатка, соседи не записываются). В `Реноме` исправлено (`Строка.Соседи`, `НоваяСтрокаСоседи.СоседнийНомер`).
- 🔴 **Отсутствуют отдельные сущности** «Корпус/Здание/Помещение»: проверка `Grep Корпус|Здание` в каталоге номеров — пусто; нет каталогов зданий/этажей/помещений номерного фонда. Здания = иерархия `НомернойФонд`, этаж = реквизит. (Каталоги `*Помещения` — `ГорничныеПомещения` — принадлежат Горничным.)
- 🔴 `ЗаменаНомеровВЗаявках`: полный перебор документов без отбора в запросе + перепроведение — потенциальная деградация на больших объёмах.
- 🟡 Не прочитан внутренний цикл закраски ячеек занятости в `ВывестиШахматку` (стр. 1295-1432) — это пересечение с Бронированием; здесь зафиксирована только часть, относящаяся к выводу номерного фонда.

### 2. Алгоритмы и логика

- **Распознавание паспорта — мультиисточник с приоритетом** (`PassportBoxВызовСервера.ЗаполнитьПоляИзJSON:464-479`) 🟢: три набора соответствий json-ключей (page3 < OCR разворота < MRZ) применяются по возрастанию приоритета; более приоритетное непустое значение перезаписывает менее приоритетное; пустое — никогда. ФИО приводится `ТРег` (сканер отдаёт прописными). 9 обязательных полей паспорта проверяются после заполнения.
- **`СтрокаВДату`** (`PassportBoxВызовСервера.Module.bsl:214-229`) 🟢 — парсер даты "ДД.ММ.ГГГГ"/"ДД.ММ.ГГ": убирает точки/время, переставляет "ДДММГГ[ГГ]"→"ГГ[ГГ]ММДД", дополняет век "20" при 6 знаках, приводит через `ОписаниеТипов("Дата")`.
- **Формат выгрузки ФМС** (`ВыгрузкаДляФМС`) 🟢 — текстовый CSV `#v.2.0.0`, разделитель `;`; жёсткое ветвление по `ИностранныйГражданин` (для россиян гражданство `RUS`, тип документа `103008`, поля визы/пребывания/миграционной карты пустые). Даты `ДФ=dd.MM.yyyy`, ID `Формат(..., "ЧГ=")`. Полиморфный резолвер `ПунктВыдачиДокументаФМС` (Строка / СправочникСсылка / пусто). Имя файла `<10 симв. даты>.csv` в каталоге константы `ПАПКА_ВыгрузкаДляФМС`.
- **`ПунктыВыдачиФМС`** (`КлиентыСервер.Module.bsl:22-89`) 🟢 — выбор пункта выдачи паспорта по коду органа: при нескольких записях сортирует по `КонечнаяДата` убыв. и выбирает запись, актуальную на `ДатаВыдачи` (последняя, у которой `ДатаВыдачи < КонечнаяДата`); парсит дату из строки "ДДММГГГГ" (`Сред`).
- **Дедупликация по ИНН** (`КлиентыДвойныеИНН.ДвойныеИНННаСервере:22-143`) 🟢 — вложенная группировка `Справочник.Клиенты` по ИНН с `Количество > 1` и `ТипКлиента = ЮрЛицо`; счётчики связей (заявки/групповые счета/выписки) через подзапросы; вывод табличного документа с автогруппировкой по ИНН.
- **Объединение клиентов** (`КлиентыОбъединиение.ЗаменитьКлиента:224-417`) 🟢 — замена во всех реквизитах `ЗаявкаНаБронирование` (Бронирует/Турагентство/Оплачивает/Клиент + ТЧ Счета), `ГрупповыеСчета.Контрагент`, `ВыпискаБанка.ОтКого`, регистрах `ИсторияКлиента`/`ИсторияКлиентаДопПожелания`; пометка на удаление исходного только при отсутствии ссылок (`НайтиПоСсылкам`).
- **Дни рождения проживающих** (`ДниРождения.ЗаполнитьТаблицуДниРождения:11-102`) 🟢 — отбор активных броней (`Статус = Проживает`, период включает текущую дату) по `Клиент` и `Клиент2`; именинник, если день/месяц рождения попадает в интервал [РезервС; РезервПо]; сортировка по дате рождения.
- **Загрузка сканов** (`ЗагрузкаСканов.ПереместитьФайлВПутьДоФото:141-188`) 🟢 — jpg из `Папка_СКАНЫ`, имя файла = `<ГУИД клиента>_<имя>` с авто-инкрементом суффикса при коллизии; копирование в архив + приёмник, удаление оригинала; запись пути в ТЧ `СканыДокументов` клиента.

### 3. Логика валидации

- Антидубль клиента по 3 критериям (Наименование / ИНН+КПП / ПроверитьКонтрагента) — см. `ПередЗаписью`. 🟢
- Длина ИНН (10/12), нормализация телефона через `СлужебныеКлиентСервер.ПроверкаНомераТелефона` (`ТелефонНормализованный:1488-1500`), проверка e-mail (`ЭлПочтаПроверка`). 🟢
- PassportBox: проверка `doc_type` (паспорт `rus.passport.national`, регистрация `rus.passport.registration`); 9 обязательных полей паспорта / 6 регистрации; обязательное фото page3. 🟢
- Настройки сканера: при пустых константах подставляются дефолты Порт=80, Таймаут=30 (`НастройкиPassportBox`). 🟢

## Модуль: Горничные (Housekeeping)

**Домен:** учёт работы горничных — уборка номеров и помещений, смены, прачечная, расчёт стоимости уборок и зарплаты, обмен с внешней (отдельной) базой «Горничные» через COM. Карточка номера зеркалируется в БД горничных — это описано в модуле «Размещение» (`Catalog.НомернойФонд.ObjectModule`), здесь не дублируется, только используется как источник связки `НомерГорничные`.

**Архитектурная особенность.** В системе сосуществуют ДВЕ базы 1С: основная «ОТЕЛЬ» и отдельная база «Горничные» (планшеты горничных). Регистрация уборок физически выполняется в базе «Горничные», а в «ОТЕЛЬ» данные **загружаются** через COM-соединение (`CommonModule.ОбменГорничныеСервер`). В обеих базах присутствует одноимённый общий модуль `ОбменГорничныеСервер` (RPC-фасад). Зарплата считается уже по загруженным в «ОТЕЛЬ» документам.

### 1. Поток управления

**1.1. Создание задания уборки при бронировании** (`ОбменГорничныеСервер.СоздатьЗаявку`, вызывается из модуля Бронирование):
- Если `Константы.ОбменСГорничными = Ложь` → выход.
- Берётся `Заявка.НомерВРезерв.НомерГорничные`; если пуст — сообщение оператору и выход (задание в БД горничных не создаётся).
- Заявка сериализуется в `Структура` (ГУИД, статус/времена через `XMLСтрока`, доп.места, времена заезда/выезда) и через COM передаётся в БД горничных: `Соединение.ОбменГорничныеСервер.СоздатьЗаявку(ДанныеЗаявки, Событие)`.

**1.2. Загрузка фактов уборки из БД горничных** (`ОбменГорничныеСервер.ЗагрузитьОбслуживаниеНомеров(С, По, НомерГорничные)`):
- COM-выгрузка ТЗ из БД горничных → для каждой строки сопоставление номера (`НомернойФонд`/`ГорничныеНомера` по `НомерГорничные`), горничной (`НайтиПоНаименованию`, при отсутствии — авто-создание), заявки (по GUID).
- Поиск существующего документа по ключу (ДатаОбслуживания + НомерОбслуживания_пп + НомерГорничные); если документ помечен `РучноеИзменение` → пропуск (защита ручных правок).
- Заполнение всех реквизитов + ТЧ Минибар/ТехНеисправности/ДопОборудование, проведение (или пометка удаления). В конце — `ЗагрузитьСостояниеНомеров()` (бельё/доп.места в `ГорничныеНомера`).
- Аналогично `ЗагрузитьОбслуживаниеПомещений` и `ЗагрузитьСмены` (для смен поиск по ДатаСмены+Горничная, при отсутствии — создание).

**1.3. Проведение `ГорничныеОбслуживаниеНомера`** (`ObjectModule.ОбработкаПроведения`): одна запись в РС `УборкиНомеров` (измерение `Документ` = ссылка), денормализация полей; списки минибара/оборудования/неисправностей склеиваются в строки (`ПолучитьМинибар`/`ПолучитьОборудование`/`ПолучитьТехническиеНеисправности` через `ГорничныеОбслуживаниеНомераСервер`).

**1.4. Расчёт зарплаты** (`Document.ГорничныеЗарплата` форма, команда `РасчитатьЗарплату`): см. §2.1.

**1.5. Двусторонний обмен справочниками.** `Catalog.Горничные.ObjectModule`: при первой записи присваивается `ГорничнаяГУИДСтрока = Строка(Ссылка.УникальныйИдентификатор())`; при последующих записях, если изменились ключевые реквизиты И `УчетУборок=Истина`, горничная выгружается в БД горничных (`ОбновитьГорничнаяГорничные`). Обратное направление — процедуры `ОбновитьГорничныеОтель/ОбновитьГорничныеПомещенияОтель/ОбновитьНоменклатураМиниБараОтель/ОбновитьКомплектацияОтель` (вызываются ИЗ базы горничных через COM, пишут с `ОбменДанными.Загрузка=Истина` для разрыва цикла обмена).

### 2. Алгоритмы, расчёты, правила

**2.1. Расчёт зарплаты горничных** 🟢 (`ГорничныеЗарплата/Forms/ФормаДокумента/Module.bsl`). Модель «И / Р / Э / Есть» на каждый показатель:
- `_И` (исходное) — рассчитано системой; `_Р` (ручное) — дельта-корректировка; `_Э` (эффективное) — то, что идёт в итог; `_Есть` — флаг ручной замены значения целиком.
- Правило сведения (`ОбновитьСтрокаСуммы`): `Поле_Э = ?(Поле_Есть, Поле_Р, Поле_И)` для фиксированных сумм; для количеств уборок `Кол_Э = Кол_И + Кол_Р` (аддитивная корректировка), `Сумма = Кол_Э * Цена`.
- При ручном вводе в `_Э` (`ЗарплатаЭлемент_ПриИзменении`): для «замены» пишется `_Р = _Э` и `_Есть = Истина`; для «количества» `_Р = _Э − _И`.
- Источники: РС `УборкиНомеров` (агрегаты Г/Т/ТС/РК/МК/МДМ через `ВЫБОР КОГДА ТипУборкиПризнак=...`), смены (`КОЛИЧЕСТВО РАЗЛИЧНЫЕ ДатаСмены`), прачечная (Σ по ТЧ), помещения (`ГорничныеОбслуживаниеПомещения.ПомещенияУборки`, `КОЛИЧЕСТВО РАЗЛИЧНЫЕ Ссылка` где `Обслужено`).
- **Учёт сдельных уборок только если `Горничная.УчетУборок = Истина`** — иначе сдельная часть = 0.
- Цены берутся из `ГорничныеСтоимостьУборок` — первая запись с `ДатаНазначенияЦены <= ДН` (срез последних на дату начала периода).
- Перед расчётом, если включён обмен, форма дозагружает данные: `ЗагрузитьОбслуживаниеНомеров/Помещений/Смены`.

**2.2. Оклад с учётом отпуска** 🟢 (`СуммаОклад`/`КоличествоРасчетныхДней`): `Оклад_расч = Окр(Оклад_месяц * РасчётныеДни / ДнейВМесяце)`, где `РасчётныеДни = ДнейПериода − ДнейОтпуска`; `ДнейВМесяце = День(КонецМесяца(МесяцРасчета))`. Пересечение отпусков с периодом ДН..ДК обрабатывается 4 ветвями (отпуск внутри / охватывает / пересекает начало / пересекает конец).

**2.3. Надбавка за стаж** 🟢: `РазницаВДнях = (ДН − ДатаПриема)/86400`; ищется строка шкалы (РС `ГорничныеНадбавкаЗаСтаж`, срез на `ДК`) где `РазницаВДняхС <= РазницаВДнях < РазницаВДняхПо`; затем пропорционально периоду: `Окр(Сумма * РасчётныеДни / ДнейВМесяце)`. Комментарий-шкала в коде: 0.5г→500, 1г→1000, 2г→2000, 3г→3000, 5л→3500.

**2.4. Отпускные** 🟢 (`СуммаОтпуск`): `Окр(ДнейОтпускаВпериоде * Горничная.Отпуск / Горничная.ВсегоДнейОтпуска)`.

**2.5. Количество часов** 🟢: `КоличествоЧасов = КоличествоСмен * Горничная.ДлинаСмены` (на сервере). ⚠ Баг: клиентский вариант `КоличествоЧасовНаКлиенте` использует жёсткое `* 8` вместо `ДлинаСмены`.

**2.6. Итог по горничной** 🟢 (`ОбновитьЗарплатаИтого`): `Итого = Оклад_Э + Отпуск_Э + НадбавкаСтаж_Э + НадбавкаСтандарты_Э + Больничный + Премия + ΣСуммыУборок(Г+Т+ТС+РК+МК+МДМ) + ДопРаботы + Сдельно_Э + КорректировкаДопНачислено + СуммаПомещения`; `ЗарплатаИтого = Итого + СуммаПрачечная_Э`; `ОстатокКВыдаче = ЗарплатаИтого − (Аванс_кк + Аванс_нал + Зарплата_кк + Отпуск_кк + Отпуск_нал + Сдельно_нал_Э + ИныеВыплаты_нал)`.

**2.7. Прачечная — деление выручки** 🟢 (`ГорничныеПрачечная/Forms`, `ОбновитьСуммаПрачечная`): на каждую строку: `СуммаНДС = Окр(СуммаОплаты * СтавкаНДС/(100+СтавкаНДС))`; `СуммаБезНДС = СуммаОплаты − СуммаНДС`; `СуммаОтелю = Окр(СуммаБезНДС * ПроцентОтеля/100)` (по умолчанию `ПроцентОтеля=10`); `СуммаПрачечная (к выдаче горничной) = Окр(СуммаБезНДС * (1 − ПроцентОтеля/100))`.

**2.8. Цена помещений на форме зарплаты** 🟡: реквизиты формы и колонки таблицы создаются динамически (`ДобавитьРеквизитыПомещения`) по числу помещений в `Catalog.ГорничныеПомещения`; имена вида `Количество_<N>`, `Количество_<N>_Р/_Э`, `Сумма_<N>`, `ПомещениеЦена_<N>`. Сумма помещения = `Кол_Э * ЦенаПомещения`; `СуммаПомещения` строки = Σ по всем помещениям горничной.

**2.9. Защита ручных правок при загрузке** 🟢: если загруженный из БД горничных документ (`ГорничныеОбслуживаниеНомера`/`...Помещения`) имеет `РучноеИзменение = Истина`, повторная загрузка его пропускает.

**2.10. Признак типа уборки** 🟢: `ТипУборкиПризнак` (строка `Г`/`Т`/`ТС`) — управляющий код, по которому агрегируются количества и применяются цены Г/Т/ТС. РК/МК/МДМ — флаги обработки (раздельные кровати / манипуляция кровати / манипуляция доп.места 1+2; `МДМ = МДМ_1 + МДМ_2`).

## Модуль: Минибар

**Назначение.** Товарный учёт минибара отеля: приход товара минибара, расход (продажа гостю / списание), партионный учёт по FIFO, расчёт себестоимости методом средневзвешенной цены и помесячный перенос остатков, аналитические отчёты (движение и прибыль минибара). Расход фактически формируется из фактов потребления, зарегистрированных в ТЧ `Минибар` документа `ГорничныеОбслуживаниеНомера` (граница с модулем «Горничные»).

> **Важное архитектурное разграничение.** В конфигурации сосуществуют ДВА товарных контура:
> 1. **Минибар (основной контур модуля)** — номенклатура `Catalog.НоменклатураМиниБара`, регистры накопления `МинибарОстатки` (количество + суммы прихода/расхода) и `МинибарПартии` (FIFO-партии), регистр сведений `МинибарСебестоимость` (помесячные средневзвешенные остатки). Документы `МинибарПриход`, `МинибарРасход`. Управляется обработкой `DataProcessor.Минибар`.
> 2. **«Бар» / общий товарный контур** — номенклатура `Catalog.Товары` (группа «Бар»), регистр накопления `ОстаткиПродукции`, регистр сведений `СебестоимостьТоваров`. Документ инвентаризации `ИнвентарицацияБара` (опечатка в имени — «Инвентарицация»). Этот документ проводится по `ОстаткиПродукции`, а НЕ по минибарным регистрам. `AccumulationRegister.ПродажиТоваров` относится к этому же/смежному торговому контуру (общий с другим товарным учётом — см. ниже, «связь»).
>
> Оба seed-объекта `DataProcessor.ИнвентарицацияБара` и `Document.ИнвентарицацияБара` принадлежат именно контуру «Бар»/`Товары`, а не минибару `НоменклатураМиниБара`. Документируются здесь как часть модуля, с явной пометкой контура.

### 1. Поток управления

**1.1. `Документ.МинибарПриход.ОбработкаПроведения(Отказ, Режим)`** 🟢 (`Documents/МинибарПриход/ObjectModule.bsl:2-28`).
- Цикл по ТЧ `Приход` → движение `МинибарОстатки` (ВидДвижения=Приход): `Количество`, `ЦенаПриход`, `СуммаПриход = Цена*Количество`. Период = `ДатаДокументаПрихода` (не дата документа!).
- Второй цикл по ТЧ `Приход` → движение `МинибарПартии` (Приход): создаёт партию с `ДокументПрихода = Ссылка`, `НоменклатураМинибара`, `Количество`, `ЦенаПриход`. Каждый приход = отдельная партия (ключ партии — документ прихода).

**1.2. `Документ.МинибарРасход.ОбработкаПроведения(Отказ, Режим)`** 🟢 (`Documents/МинибарРасход/ObjectModule.bsl:2-64`) — самый сложный алгоритм модуля (FIFO-списание партий). См. детальный flowchart `Минибар-РасходПроведение.md` и §2.1.

**1.3. `Функция ПартииОстатки(Дата, НоменклатураМинибара)`** 🟢 (`Documents/МинибарРасход/ObjectModule.bsl:66-98`).
- Запрос к виртуальной таблице `РегистрНакопления.МинибарПартии.Остатки(&Дата, НоменклатураМинибара = &Номенклатура)` с `КоличествоОстаток > 0`, **упорядоченный по `ДокументПрихода.ДатаДокументаПрихода`** (это и задаёт порядок FIFO). Граница даты — `Включая`.

**1.4. `Документ.ИнвентарицацияБара.ОбработкаПроведения(Отказ, Режим)`** 🟢 (контур «Бар», `Documents/ИнвентарицацияБара/ObjectModule.bsl:2-30`).
- Цикл по ТЧ `Товары`. Если `Расхождение = 0` → пропуск. Если `Расхождение > 0` → приход `ОстаткиПродукции` на `КоличествоФакт − КоличествоУчет`; если `< 0` → расход на `−1*(Факт − Учёт)`. Период = `Дата`. (Фрагмент построен конструктором движений.)

**1.5. `DataProcessor.Минибар.Форма`** 🟢 (`DataProcessors/Минибар/Forms/Форма/Module.bsl`):
- `СоздатьДокументРасходНаСервере(ДатаРасчета)` (стр. 17-94) — главный сборщик расхода из уборок.
- `ОтчетМесяцНаСервере()` (стр. 159-537) — отчёт движения минибара (приход/расход/списание по дням, остатки, контроль отрицательных остатков).
- `ПрибыльНаСервере()` (стр. 551-677) — отчёт прибыли (выручка − себестоимость расхода − себестоимость списания).
- `ОбновитьСебестоимостьМиниБара` / `ОбновитьСебестоимостьМиниБараНаСервере(ДатаРасчета_П)` (стр. 808-1081) — перерасчёт средневзвешенной себестоимости с цепочкой месяцев.
- `ДатыОбновления()` / `БудущиеДаты()` — определение диапазона месяцев для пересчёта (поиск разрыва в цепочке `МинибарСебестоимость`).

### 2. Алгоритмы и логика

**2.1. FIFO-списание партий минибара** 🟢 (`МинибарРасход/ObjectModule.bsl:16-62`). Ядро модуля. На каждую строку расхода:
1. Получить остатки партий `ПартииОстатки(ДатаРасхода, Номенклатура)` — упорядочены по дате прихода (FIFO).
2. **Скорректировать остатки на уже сделанные в этом проведении движения**: пройтись по уже добавленным строкам `Движения.МинибарПартии` той же номенклатуры/партии и вычесть их `Количество` из `КоличествоОстаток` (предотвращает двойное списание одной партии в рамках одного документа с несколькими строками).
3. `РасходОстаток = Количество строки`. Идти по партиям от старейшей: если `КоличествоОстаток > 0` — списать с партии `Мин(РасходОстаток, КоличествоОстаток)`, движение Расход с `ЦенаПриход` партии и `ЦенаРасход` строки. Уменьшать `РасходОстаток`; при полном покрытии — `Прервать`.
4. **Если партий не хватило** (`РасходОстаток > 0`) — добавить движение Расход БЕЗ `ДокументПрихода` (партия пустая) на остаток. Это уводит `МинибарПартии` в минус по «безпартионной» позиции 🟡 (учётное допущение «торговля в минус»).

**2.2. Сборка `МинибарРасход` из уборок** 🟢 (`DataProcessors/Минибар/Forms/Форма/Module.bsl:17-94`).
- Сначала `ОбменГорничныеСервер.ЗагрузитьОбслуживаниеНомеров(ДатаС, ДатаПо, "")` — подтягивает факты из БД горничных.
- Запрос к `Документ.ГорничныеОбслуживаниеНомера.Минибар` за месяц (по `КОНЕЦПЕРИОДА(...МЕСЯЦ) = ДатаСебестоимость`), упорядочен по дате/номеру обслуживания/номенклатуре.
- Идемпотентность: ищется существующий `МинибарРасход` с `Программно = Истина` за `ДатаДокументаРасхода = ДатаСебестоимость`; если есть — очищается ТЧ и переписывается («Обновлён программно»), иначе создаётся новый («Создан программно»). `ДатаДокументаРасхода = КонецМесяца`.
- Каждая строка уборки → строка расхода: `ДатаРасхода`, `Номенклатура`, `Количество`, `Цена`, `ДокументИсточник` (ссылка на уборку), `НомерОтель = Ссылка.НомерВРезерв`. Запись с проведением.

**2.3. Средневзвешенная себестоимость и помесячный перенос** 🟢 (`...Минибар/Forms/Форма/Module.bsl:968-1081`). На каждый месяц:
- Начало месяца = срез последних `МинибарСебестоимость` (Количество/Сумма).
- `ЦенаСписания = (СуммаНачало + СуммаПриход) / (КоличествоНачало + КоличествоПриход)` (средневзвешенная). Если знаменатель 0 — fallback на `СуммаНачало/КоличествоНачало` или 0.
- `СуммаКонец = СуммаНачало + СуммаПриход − КоличествоРасход*ЦенаСписания`; `КоличествоКонец = КоличествоНачало + КоличествоПриход − КоличествоРасход`.
- Запись на `Период = КонецМесяца + 1` (т.е. начало следующего месяца). Пишется только если есть движение (начало/приход/расход ≠ 0).
- `ДатыОбновления()` ищет в `МинибарСебестоимость` первый разрыв в помесячной цепочке и пересчитывает от него до даты расчёта + будущие месяцы с движениями (`БудущиеДаты()`).

**2.4. Отчёт «Прибыль»** 🟢 (`...Минибар/Forms/Форма/Module.bsl:645-668`). На номенклатуру: `ЦенаСписания = (НачалоСумма+ПриходСумма)/(НачалоКоличество+ПриходКоличество)`; `СебестоимостьРасход = Окр(ЦенаСписания*РасходКоличество, 2)`; `СебестоимостьСписание` аналогично; `Прибыль = Окр(РасходСумма − СебестоимостьРасход − СебестоимостьСписание)`. Разделение расхода (`Списание=Ложь`, продажа) и списания (`Списание=Истина`) по флагу документа.

**2.5. Отчёт «Движение/Количество»** 🟢 (`...Минибар/Forms/Форма/Module.bsl:159-537`). Колонки-шапки строятся динамически по датам приходов, датам/типам списаний и дням месяца. Ключевой учётный баланс на строку: `КонецМесяца = СкладНачалоМесяца + ВНомерах + ПриходМесяц − РасходМесяц − СписаниеМесяц`, где `СкладНачалоМесяца = НачалоМесяцаКоличество − ВНомерах` (ВНомерах = число номеров отеля — допущение «по 1 шт каждого товара в каждом номере»). Отрицательные остатки красятся красным.

**2.6. Инвентаризация бара = Факт − Учёт** 🟢 (`ИнвентарицацияБара/Forms/ФормаДокумента/Module.bsl:130-186`). Заполнение ТЧ запросом: остатки `ОстаткиПродукции` + `СебестоимостьТоваров.СрезПоследних` по товарам группы «Бар» (`Товары.НайтиПоНаименованию("Бар")`, в иерархии). `Себестоимость = Себестоимость / ?(Остаток=0,1,Остаток)` (себестоимость за единицу). `Расхождение = КоличествоФакт − КоличествоУчет` (пересчёт при окончании редактирования строки). Условное оформление: расхождение =0 зелёное, >0 светло-зелёное, <0 коралловое.

**2.7. Зеркалирование номенклатуры минибара** 🟢 (`Catalogs/НоменклатураМиниБара/ObjectModule.bsl`). При записи: `ОбновитьДопУслуги` создаёт/обновляет элемент `Справочник.ДопУслуги` (родитель = группа с `ПрограммныйКодУслуги.Минибар`), копирует Наименование/Цена/ПометкаУдаления — так минибар продаётся гостю как доп. услуга. Затем (если `Константа.ОбменСГорничными`) выгружает карточку в БД горничных через COM (`ОбновитьНоменклатураМиниБараГорничные`).

### 3. Структуры данных
См. `data-dictionary.md` → раздел «Минибар».

### 4. Метаданные и конфигурации
- `Document.МинибарРасход`: флаг `Программно` (Boolean) — расход создан/обновлён обработкой `Минибар` из уборок; флаг `Списание` (Boolean) — отличает списание (брак/недостача) от продажи. ТЧ `Расход` несёт `ДокументИсточник` (DocumentRef.ГорничныеОбслуживаниеНомера), `НомерОтель`, `ТипСписания` (CatalogRef.ТипСписанияМинибар).
- `МинибарПриход`/`МинибарРасход`: проведение в привилегированном режиме (`postInPrivilegedMode=true`). Дата движений берётся из реквизита `ДатаДокументаПрихода`/`ДатаРасхода`, а не из даты документа.
- `Catalog.НоменклатураМиниБара`: `Номер_пп_Отчет` (порядок в отчётах), `НеИспользуется` (исключение из отчётов/срезов), `Сортировка`.
- `Catalog.ТипСписанияМинибар`: представления «Причина списания»/«Причины списания»; `Номер_пп` для сортировки в отчётах.
- `InformationRegister.МинибарСебестоимость`: периодичность = Месяц, основной отбор по периоду; точка истины по средневзвешенной себестоимости и переходящим остаткам.
- `Enum.ПрограммныйКодУслуги.Минибар` — код группы доп.услуг, под которую падает зеркало номенклатуры минибара.

### Зависимости
- **Горничные** — источник фактов потребления: ТЧ `Минибар` документа `ГорничныеОбслуживаниеНомера`; `ОбменГорничныеСервер.ЗагрузитьОбслуживаниеНомеров`. Двусторонняя синхронизация справочника `НоменклатураМиниБара`.
- **Доп. услуги и коворкинг** — зеркало номенклатуры минибара в `Справочник.ДопУслуги` (продажа гостю/в чек).
- **Размещение и номерной фонд** — `НомернойФонд` (реквизит `НомерОтель` в расходе; число номеров в отчёте движения).
- **Финансы и касса** — продажа минибара как доп.услуги попадает в счёт/чек (через `ДопУслуги`), не через регистры минибара напрямую.

### 🔴 Пробелы
- 🔴 «Торговля в минус»: при нехватке партий FIFO добавляется движение `МинибарПартии` Расход без `ДокументПрихода`, уводящее остаток партий в минус (`МинибарРасход/ObjectModule.bsl:54-61`). Себестоимость такого расхода = 0 (партия пустая) — занижает себестоимость, завышает прибыль. Учётное допущение, корректность не гарантирована.
- 🔴 Опечатка в имени метаданного `Document.ИнвентарицацияБара` / `DataProcessor.ИнвентарицацияБара` («Инвентарицация» вместо «Инвентаризация») — закреплена в FQN, переименование требует правки всех ссылок.
- 🔴 `ИнвентарицацияБара` инвентаризирует контур `Catalog.Товары`/`ОстаткиПродукции`, а НЕ `НоменклатураМиниБара`/`МинибарОстатки`. Связь двух контуров («Бар» в `Товары` vs «минибар» в `НоменклатураМиниБара`) и синхронизация остатков между ними в коде не обнаружены — вероятно, два независимых учёта; нуждается в подтверждении бизнеса.
- 🔴 Жёсткая привязка `Справочники.Товары.НайтиПоНаименованию("Бар")` (`ИнвентарицацияБара/Forms/ФормаДокумента/Module.bsl:154`) — магическая строка имени группы, ломается при переименовании группы.
- 🔴 Допущение отчёта движения «ВНомерах = число всех номеров отеля» (по 1 шт каждого товара в каждом номере) — не параметризовано (`...Минибар/Forms/Форма/Module.bsl:416-421`).
- 🔴 Дубль метода `ПрибыльНаСервере` / `ПрибыльНаСервере_1` (стр. 551 и 680) и закомментированные/мёртвые процедуры (`ТоварыПриВыводеСтроки__`, `КоманднаяПанель1Заполнить__`, `ТЕСТ`) — техдолг.
- 🟡 `AccumulationRegister.ПродажиТоваров` и `СебестоимостьТоваров` отнесены к контуру «Бар»/общему торговому учёту по структуре; их точная роль для минибара (продажа товаров минибара через кассу) детально не разобрана — описаны как связь.
- 🟡 `Document.ИнвентарицацияБара` форма `ФормаДокумента_OLD` (обычная форма) — устаревшая версия, не разбиралась.

## Модуль: Доп. услуги и коворкинг

**Назначение.** Два связанных контура. (1) **Доп. услуги гостю** — справочник-прайс `ДопУслуги` (платные услуги: транспорт, проживание-услуги, завтраки, минибар, прачечная, штраф, коворкинг — по `Enum.ПрограммныйКодУслуги`), куда зеркалируется номенклатура минибара; долг за допуслуги копится в ТЧ `ЗаявкаНаБронирование.ДопУслуги` (контур долгов брони) и закрывается документом-реестром `СписаниеДопУслуг`. (2) **Коворкинг** — аренда рабочих мест: заявка (`КоворкингЗаявка`), счета по заявке (`КоворкингСчета`) с собственным мини-контуром взаиморасчётов (ТЧ `ДопУслугиКоворкинг`/`ДокументыОплаты`/`РаспределениеОплатКоворкинг`), проверка/резервирование занятости в `РегистрСведений.ЗанятостьНомеровКоворкинг`, рабочее место оператора (`КоворкингЗаявкаОбработка`) и визуальная шахматка (`КоворкингШахматка`). Печать счетов/актов — `КоворкингПечатьСервер`.

> **Разграничение модулей.** Финансовый низ (`Document.ПрочиеОплаты`, `КассовыйДокумент`, `ВыпискаБанка`, регистры `Деньги`/`Долги`/`Взаиморасчеты`, `ОплатыОбщееСервер`, `ЗаявкаСервер`) и контур долгов брони (`ЗаявкаНаБронирование.СчетаДетально*`) принадлежат модулю **«Финансы и касса»** / **«Бронирование»** — здесь показаны как связи. Зеркало номенклатуры минибара описано в модуле **«Минибар»** (точка истины), здесь — как граница.

### 1. Поток управления

**1.1. `Документ.КоворкингЗаявка.ОбработкаПроведения(Отказ, РежимПроведения)`** 🟢 (`Documents/КоворкингЗаявка/ObjectModule.bsl:3-45`).
- `ПроверкаЗаполнения()` → `КоворкингСервер.ПроверкаЗаполненияКоворкингЗаявкаТекстСообщения`; при ошибке `Сообщить` + `Отказ=Истина`.
- `КоворкингСервер.ПроверкаЗанятостиКоворкинг(ЭтотОбъект)`; при конфликте — `Отказ=Истина`, «ЗАПИСЬ ОТМЕНЯЕТСЯ».
- Почасовая аренда (`КоворкингНомер.ПочасоваяОплата`): `ТемпС = НачалоЧаса(ДатаС)+ЧасС*3600`, `ТемпПо = НачалоЧаса(ДатаПо)+ЧасПо*3600-1`, шаг 3600 c. Иначе посуточно: `НачалоДня(ДатаС)…НачалоДня(ДатаПо)`, шаг 86400 c.
- Цикл `Пока ТемпС<=ТемпПо` — **по одной записи `ЗанятостьНомеровКоворкинг` на каждый час/день** (`ДокументРегистратор=Ссылка`, `Зарезервирован=Истина`, `Клиент`).

**1.2. `Документ.КоворкингСчета.ОбработкаПроведения(Отказ, РежимПроведения)`** 🟢 (`Documents/КоворкингСчета/ObjectModule.bsl:3-44`). Идентичен 1.1, но номер берётся из `КоворкингЗаявка.КоворкингНомер`, а флаг почасовости — из собственного реквизита `ПочасоваяОплата`. `ПередЗаписью` пересчитывает `СуммаОплачено` шапки и `СуммаОплачено` строк по ТЧ `РаспределениеОплатКоворкинг`, проставляет `СчетГУИД`/`ГУИД` строк допуслуг. См. flowchart `ДопУслугиКоворкинг-ОбработкаПроведенияКоворкинг.md`.

**1.3. `КоворкингСервер.ЗанятостьНомераКоворкингПроверить`** 🟢 (`CommonModules/КоворкингСервер/Module.bsl:111-178`). Двухпроходный поиск конфликта: 1-й проход ищет пересечение со *счетами* других заявок (пропуская записи-заявки), 2-й — среди заявок (исключая собственную/родительскую). Возвращает `{Результат, НачалоПериодаРезерва, КонецПериодаРезерва, Регистратор}`. См. flowchart.

**1.4. Формирование счёта из заявки** 🟢 (`КоворкингСервер.ДобавитьСчетЧасы/ДобавитьСчетДни`, `:349-505`; форма `КоворкингЗаявкаОбработка/Forms/Форма/Module.bsl:321-365`). См. flowchart `ДопУслугиКоворкинг-ДобавитьСчет.md`.

**1.5. Распределение оплат по счёту** 🟢 (`КоворкингСервер.ДобавитьДокументОплатаКоворкингСчет` и др., `:637-824`). См. flowchart `ДопУслугиКоворкинг-РаспределениеОплатКоворкинг.md`.

**1.6. `СписаниеДопУслуг` (форма)** 🟢. `СоздатьДокументыСписания` → `ДобавитьОплатаСписание` → `ОплатыОбщееСервер.СоздатьПрочиеОплатыСписание` (ВидОперации=`СписаниеДопУслуг`) + `ЗаявкаСервер.РаспределитьСтрокаОплатыСчетаДетальноДолги`. Документ движений не делает. См. flowchart `ДопУслугиКоворкинг-СписаниеДопУслуг.md`.

**1.7. `КоворкингШахматка` (форма)** 🟢/🔴. `ВывестиШахматкуДни`/`ВывестиШахматкуЧасы` рисуют табличный документ по `ЗанятостьНомеровКоворкинг`; клик `ПолеОтчетаВыбор`→`ОпределитьПоКоординатам` открывает заявку/счёт. См. flowchart `ДопУслугиКоворкинг-Шахматка.md`.

### 2. Алгоритмы и логика

**2.1. Почасовое/посуточное резервирование** 🟢. Период резерва раскрывается в дискретные записи РС: почасовая аренда — по часу (`ЧасС..ЧасПо`, минус 1 c на верхней границе), посуточная — по дню. На длинном посуточном периоде (месяц) — десятки записей на документ, без агрегации.

**2.2. Двухпроходная проверка занятости** 🟢 (`:111-178`). Заявка резервирует «черновой» период, счёт — фактический; конфликт со *счётом* другой заявки приоритетнее конфликта с заявкой. Заявка исключает счета собственной заявки; счёт исключает сам себя и родительскую заявку.

**2.3. Цепочка счетов от заявки** 🟢 (`СледующийСчетДатаС`, `:326-345`). `ДатаС` нового счёта = `МАКСИМУМ(КоворкингСчета.ДатаПо)` по непомеченным счетам заявки `+1 день`; если счетов нет — `Заявка.ДатаС`. Счета идут непрерывной цепочкой без разрывов; для посуточного — стоп, если `СледующийСчетДатаС > Заявка.ДатаПо`.

**2.4. Расчёт `ДатаПо` по периоду аренды** 🟢 (`СчетДатаПо`, `:455-505`). `МЕСЯЦ`: 1-е число → конец месяца, иначе → та же дата след. месяца −1 день (с переносом года). `НЕДЕЛЯ`: `ДатаС+6 дней`. `ДЕНЬ`/`ЧАС`: `НачалоДня(ДатаС)`. Иначе `Неопределено`. Для `МЕСЯЦ/НЕДЕЛЯ/ДЕНЬ` `Количество` жёстко = 1; пропорциональный расчёт (длина месяца/недели, выходные) **закомментирован**.

**2.5. Распределение оплаты по счёту коворкинга** 🟢 (`:637-790`). `СуммаКОплатеКоворкинг` = долг тела счёта (`Сумма−СуммаОплачено`) + долг строк допуслуг (`ДопУслугиКоворкинг.Итог("Сумма")−Итог("СуммаОплачено")`). Оплата (тип `КассовыйДокумент`/`ВыпискаБанка`, за вычетом возвратов) распределяется сначала на тело (`ЭтоУслуга=Ложь`), затем по строкам допуслуг (`ЭтоУслуга=Истина`, `ГУИДДолги=ГУИД` строки) до исчерпания остатка. Затем синхронизация с финансовым низом — `ОплатыОбщееСервер.ЗаполнитьДокументОплатыДолгОплатаДляКоворкинг`.

**2.6. Частичный возврат / пересчёт оплат** 🟢. `УменьшитьОплатыКоворкингСчетаСуммаВозврата` (`:2-53`) — уменьшает строки распределения на сумму возврата (последнюю частично) или удаляет целиком. `ОбновитьОплатыКоворкинг` (`:791-824`) — обнуляет и заново распределяет все `ДокументыОплаты`.

**2.7. Списание долга за допуслуги** 🟢. Источник долга — `ЗаявкаНаБронирование.ДопУслуги` (`ВСчет=Истина`, `Сумма=Цена*Количество`), сверяется со `СчетаДетальноДолги` (`Услуга=Истина`). **Предохранитель**: списание создаётся только если `СуммаДолг = СуммаСчетДолг`; иначе строка попадает в ТЧ `Ошибки`. Динамические колонки «Услуга_N» строятся по группам справочника `ДопУслуги` (`ЗаголовокОтчеты`, сортировка `НомерПП`), суммы группируются по родительской услуге (`ОбщийФункционалСервер.ВерхняяПапка`).

**2.8. Зеркало номенклатуры минибара в `ДопУслуги`** 🟢 (точка истины — модуль «Минибар»). Здесь — как граница: минибар продаётся гостю как доп. услуга через `Catalog.ДопУслуги` (`НоменклатураМинибара`, `Товар`, `ПрограммныйКод=МИНИБАР/КОВОРКИНГ`).

### 3. Структуры данных
См. `data-dictionary.md` → раздел «Доп. услуги и коворкинг».

### 4. Метаданные и конфигурации
- `Document.КоворкингЗаявка` / `КоворкингСчета`: проведение в привилегированном режиме (`postInPrivilegedMode`/`unpostInPrivilegedMode=true`), `realTimePosting=Deny`, `registerRecordsDeletion=AutoDelete`, единственный регистратор — `ЗанятостьНомеровКоворкинг`.

- Макеты печати по организациям: `КоворкингСчета.Template.{СчетКоворкинг_,Акт_}{Лайв,СтритАрт,Реноме,Чехов}`; `СписаниеДопУслуг.Template.{АктСписания,Акт_Лайв,Акт_ДомСоветов,Акт_Чехов,Акт_СтритАрт,Акт_Реноме1}`. Выбор области по организации (`НастройкиСервер.ЭтоРеноме/ЭтоЛайв/…`).

### 🔴 Пробелы
- 🔴 `СписаниеДопУслуг` — аномальная архитектура: документ без `ObjectModule` и без движений регистров; вся бизнес-логика и транзакции вынесены на форму.
- 🔴 Нарушение паттерна транзакций (`BeginTransactionBeforeTryCatch`): `НачатьТранзакцию/ЗафиксироватьТранзакцию` БЕЗ `Попытка/Исключение` в `ДобавитьДокументОплатаКоворкингСчет`, `Уменьшить…`, `ОбновитьОплатыКоворкинг`, `ДобавитьОплатаСписаниеНаСервере`, `УдалитьДокументСписанияНаСервере` — при ошибке `Записать` транзакция повисает.
- 🔴 Запись в цикле без агрегации: `ОбработкаПроведения` создаёт запись РС на каждый час/день периода (длинная посуточная аренда = десятки записей на документ).
- 🔴 Массивное дублирование: `ДобавитьСчетЧасы/ДобавитьСчетДни/СчетДатаПо/ЗаполнитьСрокиАренды/РабочийДень` продублированы между `КоворкингСервер` и `КоворкингКлиент`; в `КоворкингШахматка` — несколько параллельных реализаций отрисовки (`ВывестиШахматкуДни_1`, `ВывестиШахматку`, мёртвые `ТЕСТ`/`ИмяОбработки_ПеренесеноВОбщийМодуль`).
- 🔴 Мёртвый код: блок «ВключатьВыходные» (`РазницаВДняхВключатьВыходные`, `РабочийДень`, `ЭтоРабочийДень`, `ЗаполнитьСрокиАрендыВключатьВыходные`) помечен «Не используется» с `Перейти ~Продолжение`; вся пропорциональная логика цены за период закомментирована.
- 🔴 `СписаниеДопУслуг` печать акта повторно дёргает `ПолучитьДокументыКСписанию` в цикле по строкам ТЧ (`CreateQueryInCycle`).
- 🟡 Несогласованность инверсии возврата `ПроверкаЗаполнения`: заявка — `Истина` при ошибке, счёт — `Ложь` при ошибке (эквивалентно, но путает).
- 🟡 `КоворкингЗаявка.ПередЗаписью_Вариант` (запрет пометки удаления при наличии счетов) назван `_Вариант` — как обработчик, судя по имени, не подключён; фактическую защиту даёт `КоворкингКлиент.ПроверкаУдаленияЗаявки` на форме.
- 🔴 Внутренние циклы отрисовки `КоворкингШахматка` (`:122-1145`, ~1670 строк с дублями) построчно не разобраны — задокументирован только контракт вход/выход.
- 🟡 ТЧ `СписаниеДопУслуг.ДокументыКСписанию.ДокументДолг` типизирована только `DocumentRef.ЗаявкаНаБронирование` — групповые счета/иные регистраторы долга не охвачены.
- 🟡 Маппинг полей макетов печати (`Акт_*`, `СчетКоворкинг_*`) по организациям не детализирован.


## Модуль: Ценообразование

> Домен: базовые/долгосрочные цены, тарифные планы, динамический календарь цен по датам, расчёт стоимости проживания, скидки/комиссия/B2B, аналитика конкурентов и задание цен по загрузке. Ядро расчёта проживания (`ЗаполнитьТаблицуПроживания_Таблица`, `РасчетПроживания`) физически лежит в `ОбщийМодуль.ДокументыСервер`, но принадлежит ценообразованию (вызывается из модуля «Бронирование»).

### 1. Поток управления

**1.1. `ДокументыСервер.ЗаполнитьТаблицуПроживания_Таблица(Объект, Двухместный)`** 🟢 (`:428-513`). Раскладывает период брони `[РезервС; РезервПо-86400]` по дням; для каждого дня задаёт `Количество` (коэффициент частичных суток по времени заезда/выезда: Вр0=2, Вр6=1.5, иначе 1; выезд Вр18=1.5, Вр0=2) и вызывает `ЗаполнитьЦенаСуммыСтрокаПроживание`. Однодневная бронь и `БонШанс` — отдельные ветки. Граница legacy `'20240401'` переключает на `ДокументыСервер_Старый`. См. `flowcharts/Ценообразование-РасчетПроживания.md`.

**1.2. `ДокументыСервер.ЗаполнитьЦенаСуммыСтрокаПроживание`** 🟢 (`:515-539`). Приоритет цены: тарифный план (`ЦенаНаДеньТарифныйПлан`) → при цене 0 ценовая политика (`ЦенаНаДень`). У тарифа скидка НЕ применяется; у ценовой политики применяется `ЗаполнитьСтрокаПроживаниеСкидкаСумма`.

**1.3. `КалендарьЦен.ПолучитьТекущаяЦенаДня(ДатаЦены, КатегорияНомера, БезЗавтрака)`** 🟢 (`:161-224`). Трёхуровневый каскад База→Долгосрочная→Текущая, чтение 5 запросов на день. См. `flowcharts/Ценообразование-ЦенаДняКалендарь.md`.

**1.4. `ДокументыСервер.ЦенаНаДеньТарифныйПлан`** 🟢 (`:553-628`). Выбор строки тарифа по дате/категории + ячейка матрицы 2×2×2 с fallback «без завтрака»→«с завтраком». См. `flowcharts/Ценообразование-ЦенаТарифныйПлан.md`.

**1.5. `КалендарьЦен (форма).ИзменитьВыбранныеНаСервере / ИзменитьДолгосрочныеЦеныНаСервере`** 🟢 (`:1565-1661`, `:1825+`). Фактическая запись изменения цен: наборы записей `КалендарьЦенБазовый`/`КалендарьЦенКатегории` (Очистить→заполнить только изменённое) + логирование в `*История`. См. `flowcharts/Ценообразование-ИзменениеЦен.md`.

**1.6. `РасчетПроживания (форма).РассчитатьПроживаниеНаСервере`** 🟢 (`:73-115`). Автономный калькулятор стоимости: цикл по дням, тариф → ценовая политика, итоги с/без завтрака; вывод табличного документа-расшифровки.

**1.7. `КалендарьЦенЗаданиеНаЦены (форма).СоздатьЗаданиеНаСервере / ЗаписатьЗаданиеНаСервере`** 🟢. Динамическое задание цены по корзинам загрузки; запись в РС `ЦеныКонкурентовАналитика`.

### 2. Алгоритмы и логика

**2.1. Каскад цены дня** 🟢. Базовая цена («с даты установки», справочник `БазовыеЦены`, ПЕРВЫЕ 1 УБЫВ по `ДатаУстановкиЦены`) → долгосрочные правки календаря (`ВидЦены=Долгосрочная`) → текущие правки (`ВидЦены=Текущая`). Состав: `Одноместный = База + ДоплКатегория (+ ДоплЗавтрак×1)`; `Двухместный = База + ДоплДвух + ДоплКатегория (+ ДоплЗавтрак×2)`.

**2.2. Матрица тарифного плана 2×2×2** 🟢. Будни/выходные (`ДеньНедели>4`) × одно/двухместный × с/без завтрака = 8 цен в ТЧ `ТарифныйПланСтроки`; «без завтрака» падает на обычную цену при 0.

**2.3. Скидка = MAX категорийной и клиентской** 🟢 (`ИтогоСкидкаКлиент:657-673`, `ИтогоСкидка:773-808`, `СкидкаКлиента:676-768`). `ИтогоСкидка` выбирает скидку по приоритету Бронирует(турагентство)→Оплачивает→Клиент из реквизита `Категория.Скидка`; для турагентств с типом оплаты Взаимозачет/ОплатаТурагентствомСоСкидкой — процент комиссии. `СкидкаКлиента` (только для «Реноме», физлиц) считает накопительную скидку по истории оплаченных ночей. Итоговая скидка строки = `MAX(ИтогоСкидка, СкидкаКлиент)`.

**2.4. Комиссия и B2B-наценка** 🟢. `СуммаКомиссии:314-353` — для турагентств: `Окр(СуммаПроживанияБезСкидки × %/100,2)` + комиссия по услугам с программным кодом ПРОЖИВАНИЕ_УСЛУГИ. `СуммаВ2В:356-365` — наценка `(Цена/((100-%)/100) - Цена) × Количество` для строк с флагом В2В. Процент берётся из ТЧ `Клиенты.ПроцентыКомиссии`/`ПроцентыВ2В` (последняя запись ≤ даты) с fallback на реквизит клиента.

**2.5. Округление цен** 🟢. `ОкруглитьЦену = Цел()`; `ОкруглитьЦену_25` — округление до 0/50/100 руб (порог 25/75); `ОкруглитьСумма = Окр(,2)`.

**2.6. Динамическое задание цены по загрузке** 🟢 (`КалендарьЦенЗаданиеНаЦены:390-422`). Корзины загрузки 30/45/60/75/90% (`ТЗГраницы`); `ГраницаЗначение` маппит фактический % загрузки в нижнюю границу корзины — основа для рекомендации цены.

**2.7. Средняя цена конкурентов** 🟢 (`КалендарьЦен.СредняяЦенаКонкурентовАналитика:577-595`). Среднее по отелям с непустой ценой и `НЕ ПродажиЗакрыты`; при отсутствии — fallback на цену TravelLine. Источник — документ `ЦеныКонкурентовАналитика` (ТЧ `ДанныеДата` + `ДанныеОтели`, % загрузки/ADR/глубина).

**2.8. БонШанс (горящий тариф)** 🟢 (`ПолучитьБонШансЦена:405-425`). Цена из РС `ЦеныБонШанс` (последняя ≤ даты) с fallback на `Константы.БонШансЦена`; скидка не применяется.

### 3. Структуры данных
См. `data-dictionary.md` → раздел «Ценообразование».

### 4. Метаданные и конфигурации
- `Enum.КалендарьЦенТипЦены`: `БазоваяЦена`, `ДоплатаЗаДвухместный`, `ДоплатаЗаЗавтрак`.
- `Enum.КалендарьЦенВидЦены`: `ДолгосрочнаяЦена`, `ТекущаяЦена`.
- `Enum.ПрограммныйКодУслуги.ПРОЖИВАНИЕ_УСЛУГИ` — маркер услуг, облагаемых комиссией турагентства.
- Константы: `ТарифныеПланы` (тумблер использования тарифов), `БонШансЦена` (дефолтная горящая цена).
- Жёсткая дата перехода календаря `ДатаПереходаНаНовыйКалендарьЦен = '20240401'`.
- Документы `ИзменениеЦены` / `ИзменениеБазовойЦены` — UI-реестры (ТЧ `ДатаЦены`: Процент/Категория/Двухместный/БезЗавтрака), без `ObjectModule` и движений.
- Регистры истории цен (`КалендарьЦенБазовыйИстория`, `КалендарьЦенКатегорииИстория`) — аудит изменений с `Автор`/`ДатаВремяИзменения`.

### Зависимости
- **Бронирование** — потребитель: `ЗаполнитьТаблицуПроживания_Таблица` заполняет ТЧ `ЗаявкаНаБронирование.Проживание`; `РассчитатьСуммуЗаПроживание`/`РасчитатьДолг`.
- **Размещение и номерной фонд** — `Catalog.КатегорииНомеров` (разрез всех цен; в нём же legacy-реквизиты `БазовыйТарифБудни/Выходные/БудниДвух`).
- **Гости и регистрация** — `Catalog.Клиенты` (`Категория.Скидка`, ТЧ `ПроцентыКомиссии`/`ПроцентыВ2В`, `ТипОплатыСчета`, `Турагентство`).

### 🔴 Пробелы
- 🔴 Дублирующая кодовая база: `ДокументыСервер` vs `ДокументыСервер_Старый`, `КалендарьЦен` vs `КалендарьЦен_Старый`, `Тариф_НеИспользуется` — параллельные реализации цены с жёсткой датой-границей `'20240401'` (`MagicDate`).

- 🟡 Несимметрия скидок: тарифный план игнорирует скидку клиента, ценовая политика — учитывает.
- 🟡 Опечатка ключа структуры `ИзменениЦеныДня` (`КалендарьЦен.Module.bsl:266`).
- 🟡 Магические числа: коэффициенты суток 2/1.5/1, 86400, порог округления 25/75, граница `ДеньНедели>4`.
- 🟡 4 версии `ПолучитьТабДокРасшифровкаКонкурентыЦенаАналитика(_1/_2)` и методы `*_OLD`/`Тест` в форме `КалендарьЦен` (2826 строк) построчно не разобраны.

## Модуль: Финансы и касса

**Назначение.** Учёт денежных средств, долгов гостей/контрагентов и взаиморасчётов: приём оплат (касса, банк, прочие), банковские выписки, групповые счета (один плательщик на несколько заявок), гашение долгов, закрытие финансового периода/месяца и кассовой смены. Долги фактически ведутся не в регистре, а в табличных частях документа `ЗаявкаНаБронирование` (`СчетаДетальноДолги`, `РаспределениеОплатДолги`); регистры накопления `Деньги/Долги/Взаиморасчеты` — учётный контур, из которого по факту наполняется только `Взаиморасчеты`.

**Основные файлы.**
- `Documents/КассовыйДокумент/ObjectModule.bsl` — проведение оплаты наличными/картой, валидация.
- `Documents/ВыпискаБанка/ObjectModule.bsl` — безналичная оплата (структурно идентична кассе).
- `Documents/ПрочиеОплаты/ObjectModule.bsl` — взаимозачёт/списание, ТЧ `ДолгиОплата`.
- `Documents/ВзаиморасчетыКоректировка/ObjectModule.bsl` — ручная корректировка взаиморасчётов.
- `Documents/ГрупповыеСчета/ObjectModule.bsl` — групповой счёт (ПередЗаписью/ПередУдалением).
- `Documents/ГашениеДолгов_Старая/ObjectModule.bsl` — устаревший контур гашения (пишет регистр Долги).
- `CommonModules/ГрупповойСчетСервер/Module.bsl` — движок групповых счетов, распределение оплат, комиссия турагента, НДС-позиции чека.
- `CommonModules/ЗаявкаОбщееКлиентСервер/Module.bsl` — FIFO-распределение оплаты по строкам долга (`РаспределитьОплатаСтрокаДолгСтрока`, `РаспределитьОплатаНаСчетаДетальноДолги`).
- `DataProcessors/ЗакрытиеФинансовогоПериода/{ManagerModule.bsl, Forms/Форма/Module.bsl}` — отчёт-сверка «Долги/Списания» за период.
- `DataProcessors/ЗакрытиеДокументов/Forms/Форма/Module.bsl` — пометка заявок `Закрыто` за месяц.
- `DataProcessors/ЗакрытьСмену/Forms/Форма/Module.bsl` — закрытие фискальной смены (обёртка над ФУ/БПО).
- Регистры: `AccumulationRegisters/{Деньги,Долги,Взаиморасчеты}/*.mdo`.

### 1. Поток управления

- **`КассовыйДокумент.ОбработкаПроведения(Отказ, Режим)`** 🟢 — `ТекстОшибки()` → при ошибке `Отказ=Истина` + `Возврат`; иначе одно движение `Взаиморасчеты` (знак по флагу `Приход`, период=`ДатаОплаты`) и **ранний `Возврат`**. Весь последующий код (движения `Деньги`, `Долги`, начисление бонусов через COM `СлужебныеСервер.ConnectБаза_BONUS()`) — мёртвый.
- **`ВыпискаБанка.ОбработкаПроведения`** / **`ПрочиеОплаты.ОбработкаПроведения`** 🟢 — структурно идентичны кассе: валидация → движение `Взаиморасчеты` → `Возврат` → мёртвый блок `Деньги/Долги`.
- **`ВзаиморасчетыКоректировка.ОбработкаПроведения`** 🟢 — одно движение `Взаиморасчеты`, знак по реквизиту-перечислению `ВидДвижения` (Перечисления.ВидыДвиженияНакопления).
- **`ГашениеДолгов_Старая.ОбработкаПроведения`** 🟢 — цикл по ТЧ `Долги`: движение `Долги` Расход (`СуммаПогашения`) по контрагенту и документу-долгу. Единственный живой писатель `Расход` в регистр `Долги`.
- **`ГрупповыеСчета.ПередЗаписью/ПередУдалением`** 🟢 — синхронизация связей счёт↔заявка через `ГрупповойСчетСервер`; вычисление `ДатаДокумента = Макс(Счет.ДатаПо)`.
- **`ЗаявкаНаБронирование.ОбработкаПроведения`** 🟢 (модуль Бронирование, но пишет ядро финансов) — `Движения.Долги` Приход (возникновение долга по заявке) и `Движения.Взаиморасчеты`.

### 2. Алгоритмы и логика

- **FIFO-гашение долга** (`ЗаявкаОбщееКлиентСервер.РаспределитьОплатаСтрокаДолгСтрока`) 🟢 — оплата распределяется по строкам `СчетаДетальноДолги` по порядку: `ОплатыОстаток = Остаток − СуммаКЗакрытию`; если хватает — строка закрывается (`СуммаКЗакрытию=0`, `СуммаОплачено=СуммаДолг`), иначе частичное гашение; накопление в ТЧ `РаспределениеОплатДолги` идемпотентно по ключу (ДокументОплаты, ДолгиГУИД). Коды-флаги +1/−1/0.
- **Распределение оплаты по групповому счёту** (`ГрупповойСчетСервер.РаспределитьДокументОплатыГрупповойСчетОбъект`) 🟢 — обход `ДокументыДолги`, на каждую заявку `Мин(остаток оплаты, СуммаСчетаКЗакрытию)`, запись оплаты в каждую заявку (`ЗаписьДокумента.Проведение`), возврат нераспределённого остатка.
- **Комиссия турагента** (`ЗапросТекстОтборЗаявокКомиссияСчет`) 🟢 — `СуммаКомиссии = СуммаПроживание · Бронирует.ПроцентКомиссии / 100`; ветвление по `ТипОплатыСчета` (ПолнаяОплатаТурагентствомСВозвратомКомиссии vs Оплачивает≠Бронирует).
- **НДС-позиции чека группового счёта** (`ЗаполнитьПозицииЧекаККМОплатаГрупповойСчет`) 🟢 — агрегирование `СуммаПроживание/СуммаУслуги` по строкам долга, `ДатаУчетаНДС = Макс(РезервПо)`, ставка/сумма НДС через `ДокументыСервер.СуммаНДС`, обработка `БезНДС`/`НДС0`.
- **Возврат оплаты группового счёта** (`УменьшитьОплатыГрупповойСчетСуммаВозврата`) 🟢 — транзакция: снятие оплаты со всех заявок, пересчёт остатка по `Сумма − Σ ВозвратДокумент`, повторное распределение остатка.
- **Закрытие периода** (`ЗакрытиеФинансовогоПериода`) 🟢 — запрос по заявкам Выехал/Неустойка в периоде с левыми соединениями ТЧ; отчёт «Долги» (`СуммаКЗакрытию>0`) и «Списания» (`ВидыОпераций` ∈ Списание/СписаниеЗачет/СписаниеДопУслуг), разбивка списаний доп.услуг МИНИБАР/ПРАЧЕЧНАЯ по `ПрограммныйКодУслуги`.

### 3. Структуры данных (регистры-ядро)

- **РегистрНакопления.Взаиморасчеты** (Обороты, `enableTotalsSplitting`) 🟢 — измерение `Контрагент` (CatalogRef.Клиенты); ресурсы `Сумма` (10,2), `СуммаКомисииРасчет` (10,2). Единственный фактически наполняемый регистр модуля.
- **РегистрНакопления.Долги** (Обороты) 🟢 — измерения `ДокументДолг` (DocumentRef.ЗаявкаНаБронирование, Index), `Контрагент` (Пользователи/Клиенты, Index); ресурс `Сумма` (15,2). Приход = долг возник (из заявки), Расход = долг погашен (ГашениеДолгов_Старая).
- **РегистрНакопления.Деньги** (Обороты) 🟢 — измерения `ВидОплаты` (Enum: Наличные/Безнал), `Контрагент` (Пользователи/Клиенты), `КредитнаяКарта` (Boolean), `Оплата` (ЗаявкаНаБронирование/ДопУслуги); реквизиты `ВидОперации` (ВидыОпераций), `ДокументОплаты`; ресурс `Сумма` (15,2).

### 4. Метаданные / перечисления

- **Справочник.ВидыОпераций** (иерархия 2 уровня, 8 предопределённых) 🟢 — Проживание, Возврат, Взаимозачет, Списание, оverbooking, СписаниеПроживание, СписаниеДопУслуг, СписаниеЗачет. Управляет классификацией списаний и поведением оплат.
- **Перечисление.ВидОплаты** — Наличные, Безнал. 🟢
- **Перечисление.ТипОплатыСчета** — Взаимозачет, ОплатаТурагентствомСоСкидкой, ПолнаяОплатаТурагентствомСВозвратомКомиссии. 🟢 (управляет логикой комиссии).

### 🔴 Пробелы и техдолг (Финансы)

- 🔴 **Дублирование контуров учёта долга.** Долг/гашение реально живёт в ТЧ заявки (`СчетаДетальноДолги`/`РаспределениеОплатДолги`), но регистры `Деньги/Долги` остались от старого контура. Регистр `Деньги` фактически НЕ наполняется (только мёртвый код после `Возврат`); регистр `Долги` пишется заявкой (Приход) и устаревшим `ГашениеДолгов_Старая` (Расход) — баланс по нему недостоверен.
- 🔴 **Мёртвый код проведения.** В `КассовыйДокумент/ВыпискаБанка/ПрочиеОплаты` после движения `Взаиморасчеты` стоит безусловный `Возврат`; ~90 строк построения `Деньги/Долги` и бонусов недостижимы. Дубли процедур `ОбработкаПроведения___` (закомментированы целиком).
- 🔴 **Хардкод подключения к бонусной базе** через COM (`СлужебныеСервер.ConnectБаза_BONUS()`, ранее `"File=""C:\BONUS""; Usr=""Admin""; Pwd=""123"""`) — в мёртвом коде, но присутствует.
- 🟡 `ГашениеДолгов_Старая` — суффикс `_Старая`: устаревший документ, прямо пишущий регистр `Долги`, рядом с актуальным ТЧ-контуром.
- 🟡 4 версии методов отчёта в `ЗакрытиеФинансовогоПериода` (`ЗаполнитьОтчет*_Перенесено`, `_ПокаСохранить`) — часть перенесена в ManagerModule, старые оставлены в форме.
- 🟡 `ЗакрытьСмену` опирается на модуль ФУ/БПО (`ФУ_Клиент.ЗакрытьСмену`); фискальная логика смены вне модуля «Финансы» (см. модуль «Подключаемое оборудование»).
- 🟡 Оплата эквайрингом (PayKeeper) и обмен с банком/бухгалтерией — протокольно в модуле «Интеграции и обмен»; здесь описаны лишь порождаемые ими движения денег/взаиморасчётов.

## Модуль: Подключаемое оборудование (БПО)

**Назначение.** Встроенная типовая «Библиотека подключаемого оборудования» (БПО, ред. 3.2) — подсистема `ПоддержкаОборудования`: фискальные регистраторы/ККТ (локальные, облачные, автономные, распределённые), эквайринг/платёжные системы (30+ драйверов), маркировка и форматно-логический контроль (ФЛК), устройства распознавания (весы/сканеры), электронные сертификаты, внешние компоненты-драйверы, логирование операций и регламентная очистка истории. Конфигурация «ОТЕЛЬ» использует библиотеку через тонкий слой доменных обёрток (`ФУ_Клиент`, `ФУ_Сервер`, `ОплатыЧекКлиент`, `СерверККМ`) для фискализации кассовой смены и чеков. Дополнительно в модуль включено доменное расширение «телеметрия датчиков» (`Catalog.Датчики`, `Document.ПоказанияДатчиков`), смежное по смыслу, но не входящее в типовую БПО.

> **Граница анализа (🔴 осознанная).** БПО — типовая библиотека на сотни тысяч строк (255 уникальных объектов метаданных в подсистеме, ~98 общих модулей, 63 шаблона-драйвера). Анализ выполнен НА АРХИТЕКТУРНОМ УРОВНЕ: дерево подсистемы, фасады, точки интеграции с доменом. Внутренности драйверов, протоколов устройств и низкоуровневой фискализации построчно НЕ разбирались.

**Дерево подсистемы `ПоддержкаОборудования` (🟢).** HttpBridge · ЛогированиеОборудования · НастройкиПрограммы (`DataProcessor.ПанельАдминистрированияБПО`) · ПодключаемоеОборудование (→ Несертифицированное, Облачные ККТ, Платёжные системы, Устройство распознавания, Чекопечатающие устройства → Автономная ККТ / Кассовая смена / Маркировка / Распределённая фискализация / Рассылка электронных чеков / ФЛК) · Сообщения в техподдержку · Электронные сертификаты (→ Сертификаты НУЦ Минцифры).

**Фасады библиотеки (🟢).**
- `МенеджерОборудования(Клиент/Сервер/КлиентСервер/ВызовСервера/Переопределяемый/КлиентПовтИсп/Глобальный)` — ядро: выбор и подключение/отключение устройств по типу.
- `ОборудованиеЧекопечатающиеУстройства(Клиент/КлиентСервер/ВызовСервера/Локализация/РФКлиентСервер)` — фискализация чеков, открытие/закрытие смены, инкассация, печать текста.
- `ПодключаемоеОборудованиеДрайвер*` / `ВнешниеКомпонентыБПО*` — загрузка/установка внешних компонент-драйверов.
- `МенеджерОборудованияМаркировка*`, `ФорматноЛогическийКонтроль*` — проверка КМ, ФЛК/ИСМ/ЕГАИС.
- `ОборудованиеПлатежныеСистемы*` (эквайринг), `ОборудованиеЧекопечатающиеОблачныеККТ*`, `РаспределеннаяФискализация*` (через РС `ОчередьЧековККТ`), `РассылкаЭлектронныхЧеков*`.
- `ИнтеграцияПодсистемБПО*` — точки расширения БСП (подписки на события, регламентные задания, параметры сеанса, серверные оповещения).

**Доменные обёртки конфигурации «ОТЕЛЬ» → БПО (🟢).**
- `ФУ_Клиент` — `ОткрытьСмену`/`ЗакрытьСмену`/`ОтчётБезГашения`/`ВнесениеДенег`/`ВыемкаДенег`/`ВыполнитьПечатьТекста`; внутри — асинхронные вызовы `ОборудованиеЧекопечатающиеУстройстваКлиент.Начать…` и `МенеджерОборудованияКлиент.Начать…ПоТипу`; формирование шаблонов чека (`ПолучитьШаблонЧека*`).
- `ФУ_Сервер` — `ДанныеОрганизацииДляФУ`, `Кассир(ЭтоКоворкинг)`, признак `ЭтоСерверККМ`.
- `ОплатыЧекКлиент` — сборка позиций и оплат чека (`ЗаполнитьПозицииЧекаККМОплата/…ГрупповойСчет/…Коворкинг/…Аванс`), копия чека, печать текста через ФУ.
- `СерверККМ` — HTTP-клиент внешнего «Сервера ККМ» (АТОЛ): `СоздатьСоединение`, `ПолучитьДанныеККМ/Смены`, `ОткрытьСмену`/`ЗакрытьСмену`.
- `DataProcessor.АТОЛ10106` — регистрация драйвера АТОЛ (`ДобавитьДрайверНаСервере`).
- `ПечатьСервер/ПечатьКлиент` — НЕфискальная печать счетов/документов в табличный документ.

**Ключевые сценарии интеграции (см. flowcharts).**
1. *Подключение устройства/драйвера* — `ФУ_Клиент.ПриОткрытии_Подключить` → `МенеджерОборудованияКлиент.НачатьПодключениеОборудованиеПоТипу` → загрузка внешней компоненты; привязка «устройство → РМ» через `Catalog.РабочиеМеста` + `SessionParameter.РабочееМестоКлиента`.

### 1. Поток управления

#### 1.1 `Документ.ЕжедневныйАудит.ОбработкаПроведения(Отказ, Режим)` 🟢
Файл: `Documents/ЕжедневныйАудит/ObjectModule.bsl:2-24`.
- Движения формируются **только если установлен флаг `Проверка`** (`:6`). По каждой строке ТЧ `ПроданныеНомера` пишется запись РС `ПроданныеНомера` (план/факт суммы проживания, тариф, коррекция, коэф, комментарий) (`:7-21`).
- `registerRecords` в `.mdo` = `InformationRegister.ПроданныеНомера` (единственный регистратор), `RegisterRecordsDeletion=AutoDelete`, `WriteModified` (`ЕжедневныйАудит.mdo:66-68`). 🟢
- Сам документ — «конструктор движений» (фрагмент помечен `__КОНСТРУКТОР_ДВИЖЕНИЙ_РЕГИСТРОВ`). Вся аналитическая работа (сбор и расчёт строк) выполнена ранее, в форме.

#### 1.2 `ЕжедневныйАудит.Форма.ФормаДокумента.ПриСозданииНаСервере(...)` 🟢
Файл: `Forms/ФормаДокумента/Module.bsl:30-67`.
- Динамически достраивает на форме параллельную таблицу `ПроданныеНомераОтклонения` (реквизиты копируются из ТЧ `ПроданныеНомера` через `ОбщийФункционалСервер.РеквизитыИзТабличнаяЧастьДокумента`) — генерация элементов формы во время выполнения (`:84-138`).
- Для нового документа: `Автор = ТекущийПользователь`, `Дата`/`ДатаОтбора = ТекущаяДата()`, затем `ЗаполнитьТаб()` (основной сбор) (`:38-48`).

#### 1.3 `ЕжедневныйАудит.Форма…ЗаполнитьТаб()` — сбор операционного дня 🟢
Файл: `Forms/ФормаДокумента/Module.bsl:422-799`. Главная процедура night-audit. Шаги:
1. Очищает ТЧ `ПроданныеНомера`, `Незаезды`, `Аннуляции` (`:424-426`).
2. **Проживающие** — большой вложенный запрос к РС `ЗанятостьНомеров`: отбирает регистраторов (брони) со статусом `Проживает`/`Выехал`, у которых `ПериодРезерва`, или точное время заезда/выезда попадают в `ДатаОтбора`; левым соединением подтягивает суммы оплат, разнесённые по способам (карта/наличные/безнал) через `РаспределениеОплатДолги` × `СчетаДетальноОплаты` с разбором типа документа оплаты (`КассовыйДокумент.КредитнаяКарта` → карта/наличные, `ВыпискаБанка` → безнал) (`:448-578`).
3. Фильтр: пропуск выехавших до `ДатаОтбора + 14ч` (`:595-597`).
4. По каждой брони: находит строку ТЧ `Проживание` за день (`СтрокаПроживание`), определяет двухместность (`ДокументыСервер.ДвухМестный`), вызывает `ПроживаниеОтклонение(...)` (расчёт отклонений — см. 2.1) (`:617-634`).
5. Заполняет строку `ПроданныеНомера`: суммы заявки/факт/отклонение/отклонение-по-часам, цена ценовой политики (через `ДокументыСервер.ЗаполнитьЦенаСуммыСтрокаПроживание` со скидкой клиента), допместо, ГУИД, суммы оплат по способам (`:628-716`).
6. **Незаезды** — запрос РС `ЗанятостьНомеров` со статусом `Бронь` за день → ТЧ `Незаезды` (`:728-759`).
7. **Аннуляции** — запрос `Документ.ЗаявкаНаБронирование` с `ДатаАннуляции` за день и статусом `ОтменаБронирования` → ТЧ `Аннуляции` (`:763-798`).

#### 1.4 `ЕжедневныйОтчетФакт.Форма…СформироватьОтчетНаСервере()` 🟢
Файл: `DataProcessors/ЕжедневныйОтчетФакт/Forms/Форма/Module.bsl:64-72`.

### 2. Алгоритмы и логика

#### 2.1 Расчёт отклонения тарификации факт-vs-план (`ПроживаниеОтклонение`) 🟢
`Forms/ФормаДокумента/Module.bsl:873-1006`. Ядро аудита: сравнивает фактическое время заезда/выезда с тарифной политикой брони и считает **доплату/недоплату** за «лишние» полусутки и часы.
- `ЦенаНаДень = Окр(СтрокаПроживание.Сумма / Количество, 2)`; `ЦенаЗаЧас = Окр(ЦенаНаДень/24, 2)` (`:890-893`).
- **Ранний заезд** (заезд в `ДатаОтбора`, `Час(Заезд)<6`): если тариф предполагал `Вр6` (или кол-во=1.5) → отклонение `ЦенаНаДень*0.5`, часы `6−ЧасЗаезд`; если `Вр14` (или кол-во=1) → отклонение `ЦенаНаДень`, часы `14−ЧасЗаезд` (`:898-922`).
- **Поздний выезд** (выезд в `ДатаОтбора`): по диапазонам часа выезда (14–18 / 18–23 / =23) и сопоставлению с плановым `ВремяВыезда` (`Вр12`/`Вр18`) или кол-вом суток (1/1.5/2) → отклонение `ЦенаНаДень*0.5` или `ЦенаНаДень`, часы `ЧасВыезд−13`/`−17` (`:936-997`).
- Возвращает структуру `{СуммаЗаПроживаниеОтклонение, КоличествоОтклонениеЧасы, СуммаЗаПроживаниеОтклонениеЧасы, ЦенаНаДень, ЦенаЗаЧас}`.
🟡 Магические часы (6/13/14/17/18/23) — захардкоженная политика расчётного часа гостиницы. Существует более старая урезанная версия `СуммаЗаПроживаниеОтклонение` (`:807-871`) без расчёта часов — дубль.

#### 2.2 Свод факт vs план vs ценовая политика 🟢
`ЗаполнитьТаб:682-716`. По каждой брони сводятся три суммы: `СуммаЗаПроживаниеЗаявка` (из ТЧ Проживание + допместо), `СуммаЗаПроживаниеФакт = Заявка + Отклонение`, `СуммаЗаПроживаниеФактЧасы = Заявка + ОтклонениеЧасы`, плюс цена/скидка/сумма ценовой политики (пересчёт `ДокументыСервер.ЗаполнитьЦенаСуммыСтрокаПроживание` со скидкой `ИтогоСкидкаКлиент`). Оплаты сводятся по способам и в `СуммаОплатыИтого`. Строка попадает в «Отклонения», только если есть расхождение суммы/часов или `СуммаОплатыИтого <> СуммаЗаПроживаниеФактЧасы` (`:220-223`).

#### 2.3 Метрики ежедневного факт-отчёта (загрузка / ADR / RevPAR-эквивалент) 🟢
`DataProcessors/ЕжедневныйОтчетФакт/Forms/Форма/Module.bsl:203-239` + `CommonModules/ЕжедневныйОтчетФакт`.
- **ADR по типу размещения**: `ADRДвухместные = Окр(СуммаДвухместные / КоличествоДвухместные)`; аналогично одноместные (`:206-215`). ADR = выручка / число проданных номеро-ночей.
- **Загрузка (occupancy %)**: `ИтогоЗанятыеНомера = КолОдноместные + КолДвухместные`; `ПроцентЗаселяемости = Окр(ИтогоЗанятыеНомера / КоличествоНомеров * 100)`, где `КоличествоНомеров` = число непомеченных номеров справочника `НомернойФонд` (`:217-221`, знаменатель из `ОбщееКоличествоНомеров()` `:3-15`).
- **Средняя стоимость номера** (≈ ADR общий): `ИтогоСредняяСтоимоть = Окр(ИтогоСумма / ИтогоЗанятыеНомера)` (`:223-230`).
- **Структура размещений**: % одно-/двухместных от занятых (`:232-239`).
- `ADR_НА` / `Процент_НА` — отдельные «наценочные/без агентского» показатели, хранятся в РС.
- Защита от деления на ноль везде через `Если …=0 Тогда 0` — 🟢.

#### 2.4 Источник денежных метрик факт-отчёта 🟢
`CommonModules/ЕжедневныйОтчетФакт.ТЗ_ОтчетДанные(ДатаС, ДатаПо)` (`:2-287`). Основа — ТЧ `Документ.ЗаявкаНаБронирование.Проживание`, отобранная по `ДеньПроживания` в периоде, статусам `Проживает/Выехал/Неустойка`, `БонШанс=ЛОЖЬ`, с внутренним соединением со `СчетаДетальноДолги` (только то, что реально вынесено в счёт). Допуслуги, оплаты и эквайринг подтягиваются отдельными запросами; число номеров — из `НомернойФонд`. Суммы эквайринга считаются по проценту (`СуммаЭквайринга`, `ПроцентыЭквайринга` с датой установки) (`:288-357`).

#### 2.5 Сводный отчёт сети отелей 🟢
`СформироватьЕжедневныйОтчетСводный` (`:436-762`). Объединяет показатели РС `ЕжедневныйОтчетФакт` нескольких баз: локальные + HTTP-загруженные массивы по 5 отелям, нумерует `СортировкаОтель` 1..N и строит общий табличный документ. 🟡 Имена отелей (Реноме/Лайв/Чехов/ДомСоветов/СтритАрт) захардкожены в коде.

### 3. Структуры данных

#### 3.1 `Документ.ЕжедневныйАудит` 🟢
Шапка: `Дата`, `ДатаОтбора` (за какой день делается аудит), `Автор` (СправочникСсылка.Пользователи), `Проверка` (Булево — разрешает движения), `Комментарий`.

### 4. Метаданные и конфигурации

- **Тумблер аудита**: реквизит `Проверка` (Булево) — без него `ОбработкаПроведения` не пишет движения.
- **Скрытый/срезанный механизм**: множество закомментированных исторических запросов в форме (`ЗаполнитьТаб__`, `ТарифНаДату`, `РасчитатьСтоимостьПлан/Факт`, `ПолучитьСтоимостьНовыйРасчет`) помечены «Не Используется».
- **HTTP-конфигурация сводного отчёта**: имена серверов отелей передаются в `ЗагрузитьHTTP_ЕжедневныйОтчетФакт(…, ИмяСервера)`.
- **Проценты эквайринга**: `ПроцентыЭквайрингаЗагрузить()` + `ДатаУстановкиПроцентаЭквайринга` (история ставок, в т.ч. СБП).
- `РегистрСведений.АктивностиКалендарь` (изм. `Дата`, рес. `АктивностьКалендарь`) — справочные события, фактор спроса.

- 🔴 30+ отчётов разобраны только на уровне «тема + источник по имени/беглой выборке», без построчного анализа СКД/макетов — осознанная граница (объём). - 🟡 Магические часы расчётного дня (6/12/13/14/17/18/23) и доли (0.5/1/1.5) захардкожены в `ПроживаниеОтклонение` — бизнес-политика тарификации полусуток.
- 🟡 Имена отелей сети и параметры HTTP-сбора сводного отчёта захардкожены в `CommonModules/ЕжедневныйОтчетФакт`.

## Модуль: Персонал и зарплата

**Назначение.** Кадровый учёт администраторов стойки (ресепшн) и расчёт их заработной платы: оклады/сдельные ставки по сменам, надбавки (стаж, стандарты, иностранные языки), переработки, доплаты «за проживающих» и «за заселения/завтраки» по внешним базам сети, премии/больничные/отпускные, авансы и итог «к выплате». Зарплата горничных реализована отдельно (модуль «Горничные»); здесь — общий паттерн виден, но логика администраторов независима.

**Корневые объекты (seed + расширение по скану `ПСН_РЕНОМЕ__АУДИТ/src` на «Администратор/Зарплат/Должност/Табель/Смен/Оклад/Премия»):**

| Вид | Объект | Роль в модуле | Доверие |
|-----|--------|---------------|---------|
| Catalog | `Администраторы` | Карточка администратора: Пользователь, ДатаПриема, Должность, флаги Постоянный/НеНачислятьЗаСтаж/НеРаботает, коды во внешних базах. ТЧ `Начисления` — история ставок/окладов/надбавок по `ДатаУстановки`. | 🟢 |
| Catalog | `Должности`, `ТипыДолжностей` | Справочник должностей (иерархия 2 ур., `ТипДолжности`, `Номер_пп`). | 🟢 |
| Document | `АдминистраторыЗарплата` | Ядро: расчётный документ ЗП за период [ДН;ДК]. ТЧ `Зарплата` (итог по администратору) и `ЗарплатаСмены` (детализация). Не проводится по регистрам — хранит данные в ТЧ. | 🟢 |
| InformationRegister | `АдминистраторыНадбавкаЗаСтаж` | Шкала надбавки за стаж по диапазонам дней (изм. `ГУИД`, глобальная). | 🟢 |
| InformationRegister | `АдминистраторыСуммаЗаПроживающих` | Шкала доплаты за проживающих по числу номеров × длине смены (Сумма_12/Сумма_24). | 🟢 |
| InformationRegister | `АдминистраторыТабель` | Табель часов (Администратор×Дата→Часы). Фактически не используется в расчёте. | 🟢 |
| Catalog/Document/IR | `*_Версия` | Дубли-версии (техдолг). | 🟡 |
| DataProcessor | `АдминистраторыТабель_НеИспользуется` | Мёртвая обработка (явный маркер). | 🟢 |

**Граничные объекты (связи, вглубь не разбираются):** `ЗаявкаНаБронирование` + его ТЧ `Проживание` (источник «проживающих» по дням, через `ОтчетыСервер.ТЗ_Проживание*`); `НомернойФонд` (число номеров за день); внешние базы заселений «Лайв/ДомСоветов/СтритАрт» (HTTP, модуль «Интеграции»); `СтатусБрони` (Проживает/Выехал — фильтр проживающих).

### 1. Поток управления

#### 1.1 `Форма.РасчитатьЗарплатуНаСервере()` 🟢
Файл: `Documents/АдминистраторыЗарплата/Forms/ФормаДокумента/Module.bsl:2449-2480`.
- Внешний цикл по строкам ТЧ-формы `ЗарплатаСмены` (одна строка = один администратор).
- Внутренний цикл по дням `[ДН;ДК]`: для каждого дня вызывается `РасчитатьСтрокаЗарплатаСменыСмена` — формирует строковый код смены `Часы_DDMMYY = "ДлинаСмены-НомерСмены/Переработка"` (`:2769-2791`).
- После дней: агрегация сумм по дням (`ОбновитьСтрокаЗарплатыСменаИзДат`), затем `РасчитатьНадбавки`, `РасчитатьПостоянный` (если `Администратор.Постоянный`), `РасчитатьПрочее`, выбор эффективных значений `ОбновитьСтрокаЗарплатаСменыОсновные_Э`, итоги `ОбновитьЗарплатаСменыИтоги`.

#### 1.2 Заполнение справочных данных 🟢
- `ЗаполнитьСправочныеДанные` (`:280-337`): выгрузка справочника `Администраторы` (ПометкаУдаления=Ложь И НеРаботает=Ложь), для каждого — выбор актуальной строки ТЧ `Начисления` с `ДатаУстановки ≤ ДК` (сортировка УБЫВ, берётся первая ≤ ДК).
- `ЗаполнитьСправочныеДанныеПоДНиДКНаСервере` (`:382-445`): загрузка двух шкал (`НадбавкаЗаСтаж`, `СуммаЗаПроживающих`) на `ДатаНазначения ≤ ДК`, берётся последняя дата назначения.
- `ЗаполнитьПроживающие` (`:1187-1303`): запрос броней со статусом Проживает/Выехал, пересекающих период, агрегирует `КоличествоНомеров` по каждому дню — знаменатель доплаты «за проживающих».

#### 1.3 Запись/проведение 🟢
- `ПередЗаписью` (`:2123`): отказ, если ДН/ДК пусты; иначе `РежимЗаписи=Проведение` и `ЗаполнитьПередЗаписью`.
- `ЗаполнитьПередЗаписью` (`:2136-2353`): разворачивает денормализованные реквизиты формы `*_DDMMYY` в строки ТЧ объекта `Зарплата` (итог) и `ЗарплатаСмены` (по дням, пропуская «пустые» дни через `Перейти ~ПРОДОЛЖИТЬ_ДАТА`). Движений регистров нет.

### 2. Алгоритмы и формулы (🟢)

| Формула | Выражение | Источник |
|---------|-----------|----------|
| Оклад за смену (сдельный) | ДлС=0→0; ДлС≤12→Окр(Ст12×ДлС/12); 12<ДлС≤24→Окр(Ст24×ДлС/24); >24→Ст24 | `ОкладЗаСмену` :2866 |

| Надбавка за стандарты/инязыки | Справочник.Надбавка × (ДК−ДН+1)/ДнейМесяца, Окр | :2533/:2547 |

| Итого смены | Оклад_Э + Переработка_Э + Проживающие_Э + Заселения_Э(3 сети) + Завтраки_Э(3 сети) | `ОбновитьЗарплатаСменыИтоги` :2076 |

**Паттерн «тройка реквизитов» И / _Р / _Есть** (`ОбновитьСтрокаЗарплатаСменыОсновные_Э` :2011): эффективное значение `_Э = _Р если _Есть, иначе И` (замена). Для количеств заселений/завтраков иное правило: `_Э = И + _Р` (дельта, :2055-2071).

### 3. Структуры данных
Полный словарь — в `data-dictionary.md` (раздел «Персонал и зарплата»). Ключевые: `Catalog.Администраторы` (+ ТЧ `Начисления`), `Document.АдминистраторыЗарплата` (ТЧ `Зарплата`, `ЗарплатаСмены`), 3 регистра сведений.

### 4. Метаданные и конфигурации
- Номера смен: 0 (нет), 1 (день, старт 09:00), 2 (ночь, старт 21:00), 3 (отпуск), 4 (особая для постоянных, по умолч. 8 ч) — `ManagerModule.ДатаВремяСмена`, валидации :2600. 🟡 семантика 1/2 выведена.
- Ветвление источников заселений по имени отеля («Реноме»→Лайв, «Чехов»→ДомСоветов+СтритАрт) — хардкод :347-376.
- Шкалы стажа/проживающих — данные в РС, не в коде (конфигурируемы пользователем).

### Пробелы / границы модуля «Персонал и зарплата» (🔴/🟡)

- 🔴 Денормализация: ~30+ динамических реквизитов формы вида `НомерСмены_DDMMYY`/`Оклад_DDMMYY`/`СуммаЗавтракиЛайв_DDMMYY` (по каждому дню месяца) не перечислены поимённо — это сгенерированная по дате схема, а не объявленные реквизиты `.mdo`.
- 🔴 Точный расчёт «отпускных» (`Отпуск`/`Отпуск_Р`/`СтавкаЗаОтпуск`) построчно не разобран — ставка читается из справочника, но место начисления в `РасчитатьЗарплату*` не локализовано однозначно.
- 🟡 РС `АдминистраторыТабель` объявлен, но в расчёте ЗП не используется (часы вводятся вручную в форме) — потенциально мёртвая/будущая интеграция.
- 🟡 Дубли-версии: `Администраторы_Версия`, `АдминистраторыЗарплата_Версия` (форма 4012 строк), `АдминистраторыСуммаЗаПроживающих_Версия`, `АдминистраторыСуммаЗаЗавтраки_Версия`; мёртвый `DataProcessor.АдминистраторыТабель_НеИспользуется`.
- 🟡 Документ зарплаты не проводится по регистрам — отчётность строится прямым запросом к ТЧ документа; нет «единого источника правды» для бухгалтерских движений.
- 🟡 Логика «зарплата за проживающих» делит между администраторами смены закомментирована (:2966-2973) — сейчас вся сумма идёт одному, без деления.

### 1. Поток управления

#### Планы обмена 1С (узловой обмен, XML + FTP) — `ОбменГостиницы`, `ОбменВыписка`, `ОбменТест` (🟢)
- `ОбменГостиницы.ВыполнитьОбменДанными()` — перебирает узлы `ПланыОбмена.ОбменГостиницы.Выбрать()`, пропускает `ЭтотУзел`; для каждого узла сначала `ПрочитатьСообщениеСИзменениями()`, затем `ЗаписатьСообщениеСИзменениями()`. Коды ошибок 1 и 30 трактуются как «нет нового сообщения» (не фатальны).
- `ЗаписатьСообщениеСИзменениями(УзелИсточник, УзелПриемник)` — классический паттерн платформы: `ЗаписьXML.ОткрытьФайл(временный)` → `ПланыОбмена.СоздатьЗаписьСообщения().НачатьЗапись()` → `ПланыОбмена.ВыбратьИзменения(Получатель, НомерСообщения)` цикл → `ОбменГостиницы.ЗаписатьДанныеXML()` на каждую порцию → `ЗакончитьЗапись()`. Затем файл кладётся на FTP через `ФТПСервер.ЗаписатьФТПФайл()`; реквизиты узла (`АдресФТП`, `ИмяПользователя`, `Пароль`, `КаталогОбменаFTP`) берутся из `ФТПСервер.ПолучитьДанныеУзлаОбмена(Код)`.
- `ПрочитатьСообщениеСИзменениями(...)` (зеркальная процедура, строки 138+) — забирает файл с FTP, `ЧтениеXML` + `ПланыОбмена.СоздатьЧтениеСообщения()`, цикл `ВозможностьЧтенияДанныхXML/ПрочитатьДанныеXML`, регистрация добавленных/заменённых/удалённых.
- Состав плана `ОбменГостиницы`: единственный объект `<mdObject>InformationRegister.БезналЗагрузка</mdObject>` (без `<autoRecord>`). `ОбменТест`: `InformationRegister.Тест`, `autoRecord=Allow`. `ВГ_ВыпискаГостиницы`: состав ПУСТ (обмен ведётся вручную через сериализацию `DocumentObject.Выписка` в `ОбменВыписка`, не через `ВыбратьИзменения`).

#### Обмен с сайтом (HTTPS GET, JSON) — `ОбменСайт` (🟢)
- `ОбменСайт.ПолучитьДанныеБронирования(АдресСервера, НачальнаяДата, КонечнаяДата)` — `Соединение = Структура(АдресСервера, Порт=443, SSL=Истина)`, путь `"/test/manager/index.php?r=reservation/export&startDate=...&endDate=..."` (формат дат `дд-ММ-гггг`, окно по умолчанию 90 дней назад). `ВыполнитьЗапрос()` → `ПрочитатьJSON`. Ошибки оборачиваются в `Структура(ДанныеJSON, Ошибка, Описание)`.
- `СтрВДату()` — собственный парсер строковой даты с локализацией названий месяцев (Янв/Фев…), используется при разборе ответа сайта.

#### HTTP-инфраструктура заселений / ежедневного отчёта — `HTTP_Модуль`, `ОбменHTTP`, `ОбменЗаселенияСервер` (🟢)
- `HTTP_Модуль.ПолучитьЗаселения(ДатаС, ДатаПо, ИмяСервера)` — `Новый HTTPСоединение(Сервер,,,,,120)`, GET по пути, зависящему от константы-сервера: `СерверЛайвHTTP→/LIVE_HTTP/`, `СерверЧеховHTTP→/CHEHOV_HTTP/`, `СерверДомСоветовHTTP→/DomSovetov_HTTP/`, `СерверСтритАртHTTP→/StreetArt_HTTP/`, далее `hs/products/get_product/date_from/<dd.MM.yyyy>/date_to/<dd.MM.yyyy>`. Ответ сохраняется в файл `<КаталогБД>HTTPЗаселения<ИмяСервера>.txt` и читается `ЧтениеJSON`. Код состояния ≥ 300 → ошибка.
- `ПолучитьЕжедневныйОтчетФакт(...)` — то же, метод `hs/products/get_Report_1`, чтение JSON с массивом дат в формате ISO.
- `ОбменHTTP.ВыгрузитьЗаселения / ВыгрузитьЕжедневныйОтчетФакт` — запросы к собственной БД (выборка `ЗаявкаНаБронирование` / агрегаты `ЕжедневныйОтчетФакт`), отдают ТЗ (серверная сторона того же HTTP-сервиса, со стороны источника). `ОбменЗаселенияСервер.ВыгрузитьЗаселения_КУдалению` — аналогичный запрос на удаление.

#### Мессенджеры — `МесенджерСервер` → адаптеры → Green API (🟢)
- `МесенджерСервер.МесенджерВключен()` — ИЛИ по константам `СообщенияЧерезGREЕN_WhatsApp / _MAX / _Telegram`.
- `МесенджерСервер.ОтправитьДанные_Месенджер(ТипОтправки, НомерТелефона, Текст, ИмяФайла, Ссылка)` — единая точка входа (диспетчер). Нормализует телефон `GREEN_WhatsApp.ТелефонGREEN()`, затем по включённым каналам вызывает `WhatsAppСервер.Отправить*GreenWhatsApp()` и/или `TelegramСервер.Отправить*GreenTelegram()`. ТипОтправки ∈ {ОтправитьТекст, ОтправитьФайл, ОтправитьСсылку}. КодОшибки 100 = «нет WhatsApp/Telegram на телефоне».
- `WhatsAppСервер` — тонкий адаптер: оборачивает `GREEN_WhatsApp.ОтправитьТекст/ОтправитьВидеоАудиоИзображениеДокумент/ОтправитьСсылку/ПроверитьНаличиеWhatsAppДействие` в `Попытка`-обёртку со структурой `{Ошибка, КодОшибки, Описание}`.
- `TelegramСервер` — адаптер поверх `Обработки.GREEN_Telegram` (внешняя обработка-движок): `ПроверитьНаличиеТелеграм()` возвращает `chatid`, затем `ОтправитьТекст/ОтправитьВидеоАудиоИзображениеДокумент(chatid, ...)`.
- `РассылкаWhatsApp.РассылкаWhatsApp(ДатаРассылки)` — регламентный сценарий: рассылка «Сайт» (выехавшим вчера гостям) и закомментированная «ДеньРождения». Идемпотентность через РС `РассылкаWhatsApp` (ключ Клиент+ДатаРассылки+ТипРассылки). Ошибки накапливаются в файл и отправляются на e-mail `postnikov_sn@invina.ru` (🟡 хардкод адреса).

#### Эквайринг PayKeeper (REST, протокол оплаты) — `PayKeeper`, `PayKeeperСервер` (🟢)
- `PayKeeper.СоздатьСоединение(Адрес, ИмяПользователя, ПарольПользователя)` — формирует структуру `{Параметры, Токен{Идентификатор, ВремяИстечения}, Ошибка, Описание}`.
- `PayKeeper.ОбновитьТокен(Соединение)` — ленивое обновление токена: если истёк (`ВремяИстечения < ТекущаяДата()`), GET `/info/settings/token/`, читает `token`, TTL = 1200 сек. Без токена — `ВызватьИсключение`.
- Транспорт `ВыполнитьЗапрос/ВыполнитьЗапросИзПолучитьQRКод(Соединение, Путь, ТелоЗапроса)` — `Новый HTTPСоединение(Адрес, 443, Имя, Пароль, , , Новый ЗащищенноеСоединениеOpenSSL)`; Content-Type `application/x-www-form-urlencoded`; тело = `"token="+Токен+ТелоЗапроса`. Детектирует HTML-страницы ошибок («Система заблокирована. Требуется продление хостинга», `<!DOCTYPE html>`) и извлекает текст.
- API-методы: `ПолучитьQRКод()` (СБП, `/change/invoice/preview/`-подобный), `ПолучитьСтатусПлатежа()` (`/info/payments/byid/?id=`), `ПолучитьСписокПлатежей()` (`/info/payments/bydate/?...&status[]=...&serverid[]=...`, статусы по умолчанию `success,canceled,failed,refunding,partially_refunded,refunded`, системы `93,52`), `ВозвратДенег()` (`/change/payment/reverse/`), `ПолучитьСписокПлатежныхСистем()` (`/info/systems/list/`).
- `PayKeeperСервер.ПолучитьИОбработатьСписокПлатежей()` — оркестрация: тянет список платежей, на каждый `ОбновитьPayKeeperПлатежи()` (upsert в РС `PayKeeperПлатежи` по `ИД_Платежа`, сохраняя ГУИД/ДатаСоздания при повторе), для статуса `success` → `СвязатьPayKeeperПлатежи()` (привязка к документу долга/оплаты). Маппинг полей ответа: `id→ИД_Платежа, clientid→Плательщик, orderid→НомерСчета, pay_amount→Сумма, status→Статус, success_datetime→ДатаОплаты`.
- `PayKeeperСервер.ОтправитьВPayKeeperДолг(...)` (стр. 349+) — формирование позиций чека с НДС (`СтавкаНДСPayKeeper`), сумм к оплате (коворкинг/групповой счёт НДС), реквизитов счёта/контрагента.

#### Обмен картинками с планшетом — `ОбменКартинкаСервер` (🟡 COM)
- `Соединение()` — COM-подключение `V83.COMConnector` к файловой базе `C:\_Base1C\<Организация>_Картинка Планшет`; до 3 попыток через метку `~Соединение` (`Перейти`); соединение кэшируется во временном хранилище через параметр сеанса. `ВыгрузитьКартинку()` вызывает RPC `Соединение.ОбменДанными.ЗагрузитьКартинку()`.

#### Выгрузка в Бухгалтерию/НДС — `ОбменБухгалтерияНДС`, DataProcessor `ВыгрузкаНДС` (🟡)
- `ОбменБухгалтерияНДС.ЗаписатьФайлСообщение(ДатаС, ДатаПо, ТипыСчетов)` → `ЗаписатьЗаявки()` сериализует заявки/счета в XML, имя файла FTP через `ПолучитьИмяФайлаОбменаФТП(КаталогОбменаFTP)`; транспорт — тот же `ФТПСервер`.

### 2. Алгоритмы и логика

- **Узловой обмен 1С** (🟢): инфраструктура сообщений платформы (`СоздатьЗаписьСообщения/СоздатьЧтениеСообщения`, `ВыбратьИзменения`, регистрация изменений по плану обмена), сериализация порций через `ЗаписатьДанныеXML/ПрочитатьДанныеXML`. Файл-носитель — временный XML, доставка — FTP.
- **Нормализация телефона `ТелефонGREEN`** (🟢): отбрасывает все не-цифры; `8…`→`7…`; 10 цифр→`7`+номер; иначе 0 (невалидно). Формат chatId: `<номер>@c.us`.
- **Green API REST** (🟢, `GREEN_WhatsApp`): хост `api.green-api.com`, медиа `media.green-api.com`; URL метода `waInstance<Инстанс>/<Метод>/<Токен>`; POST JSON через `HTTPСоединение(..., ЗащищенноеСоединениеOpenSSL)`, разбор ответа `ЧтениеJSON`. Файлы — multipart/form-data, ручная сборка границ (`ПараметрFormData`/`ФайлFormData`, MIME по расширению). Методы: `sendMessage`, `sendLink`, `sendFileByUpload`, `checkWhatsapp`.
- **PayKeeper токен-сессия** (🟢): кэш токена в структуре соединения с TTL 1200 c, ленивое обновление; вся аутентификация — Basic (логин/пароль в `HTTPСоединение`) + `token` в теле.
- **Сериализация XDTO** (🟡): пакеты `Cashbox_1_21_1` (фискальный обмен, граница БПО) и `ExchangeMessage` (схема сообщения обмена). Детально схемы `.xdto` не разбирались.
- **Маппинг JSON→РС** в PayKeeper и обмене сайта (🟢): через `ОбщийФункционалКлиентСервер.ПолучитьЧисло/ПолучитьДату` и собственные парсеры дат.

### 3. Структуры данных

- **Планы обмена** (`ExchangePlan`): стандартные реквизиты узла `Code/Description/SentNo/ReceivedNo/ThisNode/DeletionMark`. `ВГ_ВыпискаГостиницы` доп. реквизит `Организация` (String); узел текущего обмена ищется `НайтиПоКоду("БУХ")`.
