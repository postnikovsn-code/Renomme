# Минибар

> Файл `requirements.md`. Фокус — ЧТО делает модуль, не как. Уровень: detalhado. Каждое утверждение помечено 🟢 (подтверждено кодом) / 🟡 (выведено) / 🔴 (пробел). Пути относительны корня `C:\_dev\ANB\AI\Hotel\`.

## Обзор

Модуль ведёт товарный учёт минибара отеля: приход товара минибара, расход (продажа гостю / списание), партионный учёт по FIFO, расчёт себестоимости методом средневзвешенной цены с помесячным переносом остатков и аналитические отчёты (движение и прибыль). Расход обычно формируется автоматически из фактов потребления, зарегистрированных горничными в ТЧ `Минибар` документа `ГорничныеОбслуживаниеНомера`. Номенклатура минибара зеркалируется в `Справочник.ДопУслуги` (продажа гостю) и в БД горничных по COM 🟢.

> **Важное архитектурное разграничение.** В конфигурации сосуществуют ДВА товарных контура. Этот документ полностью покрывает контур **Минибар** (`Catalog.НоменклатураМиниБара` → регистры `МинибарОстатки`/`МинибарПартии`/`МинибарСебестоимость`, документы `МинибарПриход`/`МинибарРасход`, обработка `DataProcessor.Минибар`). Контур **«Бар»/Товары** (`Catalog.Товары` группа «Бар» → `ОстаткиПродукции`/`СебестоимостьТоваров`, документ `ИнвентарицацияБара`) описан как **СВЯЗАННЫЙ, но отдельный** контур: он инвентаризирует другой справочник и другие регистры; синхронизация остатков между контурами в коде НЕ обнаружена 🔴 (см. `questions.md` Q-02, ADR 0012).

## Ответственности

- Приход товара минибара: +остаток в `МинибарОстатки` и создание FIFO-партии в `МинибарПартии` (партия = документ прихода) 🟢.
- Расход минибара: −остаток в `МинибарОстатки` и FIFO-списание партий в `МинибарПартии` (от старейшей по дате прихода) 🟢.
- Автоматический идемпотентный сбор документа расхода из уборок горничных за месяц (`Программно=Истина`) 🟢.
- Расчёт средневзвешенной себестоимости с помесячным переносом остатков в `МинибарСебестоимость` и пересчётом цепочки месяцев от первого разрыва 🟢.
- Аналитические отчёты «Движение/Количество» и «Прибыль» (выручка − себестоимость расхода − себестоимость списания) 🟢.
- Зеркалирование номенклатуры минибара в `Справочник.ДопУслуги` (продажа гостю) и в БД горничных по COM 🟢.
- (Связанный контур) Инвентаризация бара = Факт − Учёт по `ОстаткиПродукции` 🟢.

## Бизнес-правила

- Приход создаёт **отдельную партию на каждый документ прихода** (ключ партии — `ДокументПрихода = Ссылка`); это и обеспечивает FIFO 🟢 (`МинибарПриход/ObjectModule.bsl:2-28`).
- Период движений регистров берётся из реквизита `ДатаДокументаПрихода` (приход) / `ДатаРасхода` строки (расход), а НЕ из даты документа — позволяет регистрировать движения «фактической» датой 🟢 (flowchart Приход, замечания).
- Расход списывает партии строго по FIFO: порядок задаётся `УПОРЯДОЧИТЬ ПО ДокументПрихода.ДатаДокументаПрихода`; цена списания с партии = `ЦенаПриход` партии 🟢 (`МинибарРасход/ObjectModule.bsl:66-98`).
- В одном документе расхода остатки партий корректируются на уже сделанные в этом же проведении движения той же номенклатуры/партии — защита от двойного списания одной партии при нескольких строках 🟢 (`МинибарРасход/ObjectModule.bsl:16-29`).
- При нехватке партий расход не блокируется: добавляется движение `МинибарПартии` Расход БЕЗ `ДокументПрихода` (пустая партия), уводящее остаток в минус; себестоимость такого количества = 0 — допущение «торговля в минус» 🔴 (`МинибарРасход/ObjectModule.bsl:54-61`, ADR 0012).
- Автосбор расхода идемпотентен по ключу `Программно=Истина` + `ДатаДокументаРасхода = КонецМесяца`: повторный запуск перезаписывает один и тот же документ за месяц, а не плодит дубли 🟢 (`DataProcessors/Минибар/Forms/Форма/Module.bsl:17-94`).
- Перед автосбором подтягиваются свежие факты из БД горничных (`ОбменГорничныеСервер.ЗагрузитьОбслуживаниеНомеров`) 🟢.
- Себестоимость — **средневзвешенная**: `ЦенаСписания = (СуммаНачало + СуммаПриход) / (КоличествоНачало + КоличествоПриход)`, fallback при делении на 0 🟢 (`...Минибар/Forms/Форма/Module.bsl:968-1081`).
- Результат себестоимости пишется на `Период = КонецМесяца + 1` (начало следующего месяца), формируя переходящий остаток 🟢.
- Пересчёт себестоимости идёт цепочкой месяцев от первого разрыва в помесячной непрерывности `МинибарСебестоимость` до даты расчёта + будущие месяцы с движениями (`ДатыОбновления`/`БудущиеДаты`) 🟢.
- Себестоимость записывается на номенклатуру только если есть движение (Начало/Приход/Расход ≠ 0); `НеИспользуется`-номенклатура исключается из срезов/отчётов 🟢.
- Отчёт «Прибыль» разделяет продажу (`Списание=Ложь`) и списание (`Списание=Истина`) по флагу документа 🟢 (`...Module.bsl:645-668`).
- Отчёт «Движение» использует допущение `ВНомерах = число всех номеров отеля` (по 1 шт каждого товара в каждом номере), не параметризованное 🔴 (`...Module.bsl:416-421`).
- При записи номенклатуры минибара зеркало в `ДопУслуги` создаётся/обновляется под группой `Enum.ПрограммныйКодУслуги.Минибар` (копируются Наименование/Цена/ПометкаУдаления); затем при `Константа.ОбменСГорничными=Истина` карточка выгружается в БД горничных по COM 🟢 (`Catalogs/НоменклатураМиниБара/ObjectModule.bsl`).
- (Связанный контур) Инвентаризация бара корректирует `ОстаткиПродукции`: расхождение > 0 приходует, < 0 расходует, = 0 пропускается 🟢 (`ИнвентарицацияБара/ObjectModule.bsl:2-30`).

| RF-03 | Корректировать остатки партий на движения текущего проведения (несколько строк одной номенклатуры) | Must | Документ с двумя строками одной номенклатуры не списывает одну партию дважды 🟢 |

## Критерии приёмки

```gherkin
# RF-01 — проведение прихода (happy)
Дано документ МинибарПриход со строкой (Номенклатура, Количество=10, Цена=50) и ДатаДокументаПрихода
Когда документ проводится
Тогда в МинибарОстатки создаётся приход с Количество=10, ЦенаПриход=50, СуммаПриход=500
  И в МинибарПартии создаётся партия с ДокументПрихода=ссылка прихода и Количество=10

# RF-02 — FIFO-списание (happy)
Дано две партии номенклатуры N: партия А (приход 01.06, 10 шт по 50) и партия Б (приход 05.06, 10 шт по 60)
  И документ МинибарРасход со строкой (N, Количество=12) и ДатаРасхода=10.06
Когда документ проводится
Тогда списываются 10 шт из партии А (ЦенаПриход=50) и 2 шт из партии Б (ЦенаПриход=60)
  И МинибарОстатки уменьшается на 12 шт

# RF-04 — торговля в минус (failure-путь правила)
Дано номенклатура N без доступных партий (остаток партий = 0)
  И документ МинибарРасход со строкой (N, Количество=3)
Когда документ проводится
Тогда расход проводится без отказа
  И в МинибарПартии добавляется движение Расход БЕЗ ДокументПрихода на 3 шт
  И себестоимость этих 3 шт равна 0 (остаток партий уходит в минус)

# RF-05/RF-06 — идемпотентный автосбор (happy + повтор)
Дано за месяц есть факты потребления минибара в уборках горничных
Когда выполняется СоздатьДокументРасход(ДатаРасчета) первый раз
Тогда создаётся МинибарРасход с Программно=Истина, ДатаДокументаРасхода=КонецМесяца и строками по фактам
Когда команда выполняется повторно за тот же месяц
Тогда тот же документ очищается и перезаполняется, дублей не создаётся

# RF-05 — нет потребления (failure-путь)
Дано за месяц нет фактов потребления минибара
Когда выполняется СоздатьДокументРасход(ДатаРасчета)
Тогда выводится сообщение об отсутствии расхода и документ не создаётся/не изменяется

# RF-08/RF-09 — пересчёт себестоимости задним числом (happy)
Дано в МинибарСебестоимость есть помесячная цепочка с разрывом в месяце M
  И задана ДатаРасчета позже M
Когда выполняется ОбновитьСебестоимостьМиниБара
Тогда пересчитываются все месяцы от M до ДатаРасчета и будущие месяцы с движениями
  И каждый результат записан на КонецМесяца+1 со средневзвешенной ценой

# RF-08 — деление на ноль (failure-путь правила)
Дано номенклатура с КоличествоНачало+КоличествоПриход = 0
Когда считается ЦенаСписания
Тогда применяется fallback (СуммаНачало/КоличествоНачало или 0), исключения деления на ноль нет

# RF-12 — зеркало в ДопУслуги (happy)
Дано элемент НоменклатураМиниБара с Наименованием и Ценой
Когда элемент записывается
Тогда в ДопУслуги под группой ПрограммныйКодУслуги.Минибар существует элемент с тем же Наименованием/Ценой/ПометкойУдаления

# RF-13 — выгрузка в БД горничных по тумблеру (happy + отказ)
Дано Константа.ОбменСГорничными = Истина
Когда записывается номенклатура минибара
Тогда карточка выгружается в БД горничных по COM
Дано Константа.ОбменСГорничными = Ложь
Когда записывается номенклатура минибара
Тогда выгрузка в БД горничных НЕ выполняется
```

## Приоритет (MoSCoW)

| Требование | MoSCoW | Обоснование |
|-----------|--------|---------------|
| Проведение прихода и расхода (FIFO) RF-01..RF-03 | Must | Критический путь — ядро товарного учёта минибара |
| Торговля в минус RF-04 | Must | Закреплённое в коде учётное допущение, влияет на каждый расход без партии (ADR 0012) |
| Идемпотентный автосбор расхода RF-05, RF-06 | Must | Основной способ формирования расхода (из уборок), без альтернативы |
| Средневзвешенная себестоимость и цепочка месяцев RF-08, RF-09 | Must | Точка истины по себестоимости и переходящим остаткам |
| Зеркало в ДопУслуги RF-12 | Must | Без зеркала минибар не продаётся гостю (попадает в счёт через ДопУслуги) |
| Дозагрузка фактов из БД горничных RF-07 | Should | Важно для полноты, но при отключённом обмене сбор идёт по имеющимся данным |
| Отчёты «Прибыль» и «Движение» RF-10, RF-11 | Should | Аналитика, не в критическом пути проведения |
| Выгрузка номенклатуры в БД горничных RF-13 | Should | Зависит от тумблера `ОбменСГорничными`, есть ручной ввод |
| Инвентаризация бара RF-14, RF-15 | Could | Связанный, но отдельный контур «Бар»/Товары; не влияет на остатки минибара 🔴 |
| Дубль `ПрибыльНаСервере_1`, мёртвые процедуры, `ФормаДокумента_OLD` | Won't | Техдолг/мёртвый код, не переносится 🔴 |

> Приоритет выведен по частоте вызова и позиции в цепочке зависимостей.
