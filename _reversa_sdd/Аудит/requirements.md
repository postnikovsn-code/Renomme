## Обзор

Unit покрывает три связанных контура:
1. **Ночной аудит (night audit)** — закрытие операционного дня документом `ЕжедневныйАудит`: сверка фактических заездов/выездов/оплат с планом брони, расчёт отклонений тарификации (доплата/недоплата за расчётный час), фиксация подтверждённой витрины продаж дня. 🟢
2. **Ежедневные управленческие отчёты** — обработки `ЕжедневныйОтчетФакт` (ADR, загрузка, выручка по одному отелю) и `ЕжедневныйОтчетФактСводный` (сводка по сети из 5 отелей через HTTP). 🟢
3. **Подсистема отчётности** — каталог `Reports` (39 отчётов: финансы/выручка, загрузка/продажи, спрос/бронирование, качество/горничные, минибар/ТМЦ). 🟢/🟡

Unit — конечный потребитель данных: ночной аудит наполняет витрины РС `ПроданныеНомера` и `ЕжедневныйОтчетФакт`, которые читают управленческие и финансовые отчёты. 🟢

## Ответственности

- Собрать операционный день за `ДатаОтбора`: проживающих (статус `Проживает`/`Выехал`), незаезды, аннуляции — из РС `ЗанятостьНомеров` и Док `ЗаявкаНаБронирование`. 🟢
- Разнести оплаты дня по способам (карта / наличные / безнал) по типу платёжного документа (`КассовыйДокумент.КредитнаяКарта` → карта/наличные, `ВыпискаБанка` → безнал). 🟢
- Рассчитать отклонение тарификации факт-vs-план по расчётному часу (ранний заезд / поздний выезд), включая отклонение по часам. 🟢
- При подтверждении (`Проверка=Истина`) зафиксировать движения РС `ПроданныеНомера` — подтверждённую витрину продаж дня. 🟢
- Рассчитать и записать в витрину РС `ЕжедневныйОтчетФакт` показатели дня (количества/суммы размещений, ADR_НА, %_НА, B2B, комиссия, агентское), затем прочитать витрину обратно и вывести табличный документ. 🟢
- Рассчитать управленческие метрики: ADR (раздельно одно-/двухместные), загрузку %, среднюю стоимость номера, структуру размещений. 🟢
- Сформировать сводный отчёт по сети отелей, собрав данные локальной базы + 5 удалённых баз по HTTP. 🟢
- Предоставить подсистему из 39 управленческих и операционных отчётов. 🟢/🟡

## Бизнес-правила

- **AU-01** Движения РС `ПроданныеНомера` формируются ТОЛЬКО при флаге `Проверка=Истина`; иначе документ проводится без движений. 🟢 (`Documents/ЕжедневныйАудит/ObjectModule.bsl:6`)
- **AU-02** Отклонение тарификации: `ЦенаНаДень = Окр(СтрокаПроживание.Сумма / Количество, 2)`, `ЦенаЗаЧас = Окр(ЦенаНаДень / 24, 2)`; доплата/недоплата считается по фактическому часу заезда/выезда против тарифной политики; магические часы расчётного дня 6/13/14/17/18/23 и доли 0.5/1/1.5. 🟢 (формула цены), часы как политика 🟡 (`Forms/ФормаДокумента/Module.bsl:873-1006`)
- **AU-03** Строка попадает в таблицу «Отклонения» только при расхождении суммы/часов ИЛИ при `СуммаОплатыИтого ≠ СуммаЗаПроживаниеФактЧасы`. 🟢 (`Forms/ФормаДокумента/Module.bsl:220-223`)
- **AU-04** Фильтр проживающих: пропускаются выехавшие до `ДатаОтбора + 14ч`. 🟢 (`Forms/ФормаДокумента/Module.bsl:595-597`)
- **AU-05** Факт-отчёт сначала ПЕРЕСЧИТЫВАЕТ и записывает витрину РС `ЕжедневныйОтчетФакт`, затем читает её обратно запросом и рисует макет. 🟢 (`DataProcessors/ЕжедневныйОтчетФакт/Forms/Форма/Module.bsl:64-72`)
- **AU-06** Загрузка = `Окр(ИтогоЗанятыеНомера / КоличествоНомеров × 100)`, знаменатель — число НЕпомеченных номеров справочника `НомернойФонд`. 🟢 (`.../Forms/Форма/Module.bsl:203-239`, `:3-15`)
- **AU-07** ADR = выручка / число проданных номеро-ночей, раздельно по одно- и двухместным: `ADRДвухм = Окр(СуммаДвухм / КолДвухм)`, `ADRОдном = Окр(СуммаОдном / КолОдном)`. 🟢 (`.../Forms/Форма/Module.bsl:206-215`)
- **AU-08** Средняя стоимость номера ≈ общий ADR: `Окр(ИтогоСумма / ИтогоЗанятыеНомера)`. 🟢 (`.../Forms/Форма/Module.bsl:223-230`)
- **AU-09** Все деления в метриках защищены `Если знаменатель=0 Тогда 0` — при пустом дне отчёт выдаёт нули, а не ошибку. 🟢 (`flowcharts/Аудит-ЕжедневныйОтчетФакт.md`, «Защита»)
- **AU-10** Сводный отчёт собирает данные по 5 отелям сети (Реноме/Лайв/Чехов/ДомСоветов/СтритАрт) — локальная база + HTTP-загрузка; имена отелей и параметры HTTP захардкожены. 🟡 (`CommonModules/ЕжедневныйОтчетФакт/Module.bsl:436-762, 817-851`, ADR-0008)
- **AU-11** Источник денежных метрик факт-отчёта — ТЧ `ЗаявкаНаБронирование.Проживание`, отобранная по `ДеньПроживания` в периоде, статусам `Проживает/Выехал/Неустойка`, `БонШанс=ЛОЖЬ`, ВНУТР. соединением со `СчетаДетальноДолги` (только реально вынесенное в счёт). Эквайринг считается процентом по дате установки ставки. 🟢 (`CommonModules/ЕжедневныйОтчетФакт/Module.bsl:2-357`)
- **AU-12** Документ `ЕжедневныйАудит` — «конструктор движений»: вся аналитика выполнена в форме до проведения, `ОбработкаПроведения` лишь переписывает строки ТЧ в регистр. 🟢 (`ObjectModule.bsl:3-23`)
- 🔴 Точные формулы `СуммаАгентскогоВознаграждения` / `СуммаВ2В` / `ADR_НА` / `Процент_НА` внутри `ЗаполнитьРегистрЕжедневныйОтчетФакт`/`ТЗ_ОтчетДанные` построчно не разобраны (граница с «Финансами»/«Ценообразованием»).
- 🔴 Схема ресурсов/измерений 14 DCS-отчётов из `Template.dcs` не извлекалась; 30+ отчётов разобраны только на уровне «тема + источник».

|----|-----------|-----------|------------------|

| RF-10 | Сформировать сводный отчёт по сети: локальный отель + 5 удалённых по HTTP | Should | Свод содержит строки всех доступных отелей с `СортировкаОтель`; недоступный отель → сообщение об ошибке (AU-10) 🟡 |
| RF-11 | Предоставить подсистему из 39 отчётов (14 DCS + ~25 на запросах) | Should | Каждый отчёт строится из заявленного источника 🟡 |
| RF-12 | Редактор РС `АктивностиКалендарь` (события/факторы спроса) | Could | Записи РС `АктивностиКалендарь` редактируются обработкой 🟢 |

## Критерии приёмки

```gherkin
# Ночной аудит — happy path
Дано документ ЕжедневныйАудит с ДатаОтбора = операционный день
И в РС ЗанятостьНомеров есть проживающие со статусом Проживает/Выехал за этот день
Когда вызывается ЗаполнитьТаб() и документ проводится с флагом Проверка=Истина
Тогда ТЧ ПроданныеНомера заполнена строками проживающих с разнесёнными оплатами и отклонениями
И в РС ПроданныеНомера сформированы движения по каждой строке ТЧ

# Ночной аудит — проведение без подтверждения
Дано документ ЕжедневныйАудит с заполненной ТЧ ПроданныеНомера
И флаг Проверка = Ложь
Когда документ проводится
Тогда движения РС ПроданныеНомера НЕ формируются (0 записей)

# Расчёт отклонения тарификации — ранний заезд
Дано бронь с заездом в ДатаОтбора и фактическим часом заезда < 6
И тарифная политика Вр14 (количество суток = 1)
Когда вызывается ПроживаниеОтклонение(...)
Тогда СуммаЗаПроживаниеОтклонение = ЦенаНаДень
И КоличествоОтклонениеЧасы = 14 − ЧасЗаезда

# Факт-отчёт — метрики
Дано период с непустыми продажами в витрине ЕжедневныйОтчетФакт
Когда формируется ежедневный факт-отчёт
Тогда Загрузка% = Окр(ЗанятыеНомера / КоличествоНомеров × 100)
И ADRДвухм = Окр(СуммаДвухм / КолДвухм), ADRОдном = Окр(СуммаОдном / КолОдном)
И значения сначала записаны в РС, затем прочитаны для макета

# Факт-отчёт — пустой день (failure/edge)
Дано период без проданных номеров (ИтогоЗанятыеНомера = 0)
Когда формируется факт-отчёт
Тогда Загрузка%, ADR и средняя стоимость = 0 (деление на ноль не возникает)
И табличный документ строится без ошибки

# Сводный отчёт — отель сети недоступен (failure)
Дано сводный отчёт по сети из 5 отелей
И один отель недоступен по HTTP
Когда формируется свод
Тогда оператору выдаётся текст ошибки соединения с указанием имени сервера
И свод по доступным отелям не прерывается аварийно
```

## Приоритизация (MoSCoW)

| Требование | MoSCoW | Обоснование |
|-----------|--------|-------------|
| Сбор операционного дня + фиксация витрины РС `ПроданныеНомера` (RF-01..RF-06) | Must | Критический путь: закрытие дня; питает все финансовые отчёты |
| Тумблер `Проверка` как условие движений (AU-01) | Must | Бизнес-инвариант без fallback |
| Расчёт витрины и метрик факт-отчёта (RF-07, RF-08) | Must | Главное управленческое ядро (ADR/загрузка/выручка) |
| Защита деления на ноль (AU-09) | Must | Без неё пустой день валит отчёт |
| Режим «Помесячно» (RF-09) | Should | Удобство, есть базовый режим по датам |
| Сводный отчёт по сети + HTTP (RF-10) | Should | Важно для сети, но есть локальный отчёт-fallback |
| Подсистема из 39 отчётов (RF-11) | Should | Управленческая ценность; ядро покрыто факт-отчётом |
| Редактор `АктивностиКалендарь` (RF-12) | Could | Справочный фактор спроса, редко правится |
| `_Исходный`/`_OLD`/закомментированные версии | Won't | Tech-debt: дубли и мёртвый код, не переносить |

> Приоритет выведен по частоте вызова, позиции в цепочке зависимостей и наличию fallback.
