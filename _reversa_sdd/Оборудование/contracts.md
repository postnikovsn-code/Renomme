# Подключаемое оборудование (БПО) — Контракты

> Внешние контракты, которыми домен «ОТЕЛЬ» пользуется для фискализации/эквайринга.
> Описаны **контракты использования** (вход/выход со стороны домена), а не внутренняя
> реализация типовой БПО. 🟢 подтверждено · 🟡 выведено · 🔴 пробел.

## 1. Контракт «Сервер ККМ» (внешний HTTP REST)

Внешний сервис фискализации (АТОЛ «Сервер ККМ» / rbsoft), к которому домен обращается
через модуль `СерверККМ` (`ПСН_РЕНОМЕ__АУДИТ/src/CommonModules/СерверККМ/Module.bsl`). 🟢

### 1.1 Транспорт

| Параметр | Значение | Источник |
|----------|----------|----------|
| Протокол | HTTP (`Новый HTTPСоединение`) | `СерверККМ/Module.bsl:138` 🟢 |
| Базовый путь | `/PrintService/api/v2/<ИмяМетода>` | `:140` 🟢 |
| Порт по умолчанию | `4398` | `:8` 🟢 |
| Content-Type | `application/json` | `:142` 🟢 |
| Тело запроса | JSON (`ЗаписатьJSON`) | `ПолучитьСтрокуJSON`, `:165` 🟢 |
| Тело ответа | JSON (`ПрочитатьJSON`) | `ВыполнитьЗапрос`, `:145-147` 🟢 |
| Метод HTTP | `ОтправитьДляОбработки` (POST) | `:144` 🟢 |

### 1.2 Авторизация (токен)

- `GetToken` с телом `{login, password}` → `{tokenId, expire}`. 🟢 (`ОбновитьТокен`, `:155`)
- Токен хранится в `Соединение.Токен{Идентификатор, ВремяИстечения}`.
- Обновляется лениво, если `Идентификатор = Неопределено` ИЛИ `ВремяИстечения < ТекущаяДата()`. 🟢
- Дефолтные креды: `login="Admin"`, `password="Admin"`. 🔴 (Q-01)

### 1.3 Методы

| Метод API | Обёртка домена | Тело запроса | Успех |
|-----------|----------------|--------------|-------|
| `GetToken` | (внутр. `ОбновитьТокен`) | `{login, password}` | `Code=0`, `Result.tokenId`, `Result.expire` 🟢 |
| `GetDataKKT` | `ПолучитьДанныеККМ(Соединение)` | `{Token, DeviceName}` | `Code=0` → `{ДанныеККМ, Ошибка=Ложь, Описание=""}` 🟢 |
| `GetCurrentStatus` | `ПолучитьДанныеСмены(Соединение)` | `{Token, DeviceName}` | `Code=0` → `{ДанныеСмены{SessionState,SessionNumber}, Ошибка=Ложь}` 🟢 |
| `OpenShift` | `ОткрытьСмену(Соединение)` | `{Token, DeviceName}` | `Code=0` → данные открытия смены 🟢 |
| `CloseShift` | `ЗакрытьСмену(Соединение)` | `{Token, DeviceName}` | `Code=0` → данные закрытия смены 🟢 |

`DeviceName` = `Соединение.Параметры.ИдУстройства`; `Token` = `Соединение.Токен.Идентификатор`. 🟢

### 1.4 Контракт ответа и обработка ошибок

- Любой ответ библиотеки/сервера несёт целочисленный `Code`; `Code = 0` — успех. 🟢
- При `Code <> 0` обёртки бросают исключение `"Ошибка запроса: " + Description`. 🟢
- Каждая публичная функция обёрнута в `Попытка…Исключение` и **никогда не пробрасывает исключение наружу**, а возвращает `Структура{Ошибка: Булево, Описание: Строка}`. 🟢
- `SessionState` (от `GetCurrentStatus`): `1` — смена закрыта, `2` — открыта, `3` — истекла. 🟢

### 1.5 Состояние смены (state)

```gherkin
Dado SessionState = 1 (закрыта)
Quando ОткрытьСмену(Соединение)
Então OpenShift возвращает Code=0
  E SessionState переходит в 2 (открыта)

Dado SessionState = 3 (истекла)
Quando оператор пробует пробить чек
Então требуется ЗакрытьСмену затем ОткрытьСмену
```

### 1.6 Валидация входа

`СерверККМ.ПроверитьПараметр(ИмяПроцедуры, ИмяПараметра, Значение, ОжидаемыйТип)` — строго
проверяет типы аргументов `СоздатьСоединение` (Адрес=Строка, Порт=Число, и т.д.); при
несоответствии — исключение, перехваченное и преобразованное в `{Ошибка=Истина}`. 🟢 (`:189-313`)

## 2. Контракт фасадов фискализации (типовая БПО)

> 🟢 **Стабильный контракт библиотеки — НЕ модифицируется.** Описан с точки зрения домена:
> что домен подаёт на вход и что получает на выходе.

### 2.1 Пробитие чека

**Фасад:** `ОборудованиеЧекопечатающиеУстройстваКлиент.НачатьПробитиеЧека(...)` (локальная ККТ),
параллельно — `ОборудованиеЧекопечатающиеОблачныеККТ*` / `РаспределеннаяФискализация*` / `СерверККМ`.

| Сторона | Состав |
|---------|--------|
| **Вход (готовит домен)** | Массив **позиций** (`ПараметрыФискальнойСтрокиЧека`: номенклатура/услуга, кол-во, цена, сумма, ставка НДС, признак предмета/способа расчёта; для маркировки — КМ) + массив **оплат** (`ПараметрыСтрокиОплаты`: тип нал/безнал, сумма) + **реквизиты** (организация, кассир, СНО — из `ФУ_Сервер`). 🟢 |
| **Выход (от библиотеки)** | `РезультатВыполнения` в callback `ФУ_Клиент.ОперацияЗавершение`: признак успеха, данные фискального документа (ФД/ФП/смена) либо описание ошибки. 🟢 |
| **Побочные эффекты** | Запись РС `ФискальныеОперации`; опционально `Catalog.ОчередьЭлектронныхЧековКОтправке`. 🟢 |

Состав позиций по типам долга (домен):

| Тип | Метод сборки |
|-----|--------------|
| Проживание / общий счёт | `ОплатыЧекКлиент.ЗаполнитьПозицииЧекаККМОплата` 🟢 |
| Групповой счёт | `…ЗаполнитьПозицииЧекаККМОплатаГрупповойСчет` 🟢 |
| Коворкинг | `…ЗаполнитьПозицииЧекаККМОплатаКоворкинг` 🟢 |
| Аванс | `…ЗаполнитьПозицииЧекаККМАванс` 🟢 |

### 2.2 Кассовая смена

| Операция | Фасад / обёртка | Вход | Выход |
|----------|-----------------|------|-------|
| Открыть смену | `ФУ_Клиент.ОткрытьСмену(Форма, ОповещениеЗавершение, Параметры)` | реквизиты кассира | callback с результатом 🟢 |
| Закрыть смену (Z-отчёт) | `ФУ_Клиент.ЗакрытьСмену(...)` | — | callback 🟢 |
| Отчёт без гашения (X) | `ФУ_Клиент.ОтчетБезГашения(...)` | — | callback 🟢 |
| Инкассация | `ФУ_Клиент.ВыполнитьОперациюВыбораУстройстваИнкассация(...)` | сумма, направление | callback 🟢 |

### 2.3 Подключение оборудования

| Операция | Фасад | Вход | Выход |
|----------|-------|------|-------|
| Подключить по типу | `МенеджерОборудованияКлиент.НачатьПодключениеОборудованиеПоТипу(...)` | тип оборудования, РМ | callback `ПодключитьОтключитьОборудованиеЗавершение`, идентификатор объекта 🟢 |
| Отключить по типу | `МенеджерОборудованияКлиент.НачатьОтключениеОборудованияПоТипу(...)` | идентификатор | callback 🟢 |
| Текущее РМ | `МенеджерОборудованияКлиентПовтИсп.РабочееМестоКлиента()` | — | `СправочникСсылка.РабочиеМеста` 🟢 |

### 2.4 Эквайринг (платёжные системы)

**Фасад:** `ОборудованиеПлатежныеСистемы(Клиент/КлиентСервер/ВызовСервера)`. 🟡 (вглубь не разбирался)

| Сторона | Состав |
|---------|--------|
| Вход | сумма операции, тип (оплата/возврат), РМ |
| Выход | callback: код авторизации, RRN, слип; запись РС `ПлатежныеОперации` 🟡 |

### 2.5 Рассылка электронных чеков

**Фасад:** `РассылкаЭлектронныхЧеков(Клиент/ВызовСервера)` + `ScheduledJob.РассылкаЭлектронныхЧеков`.

| Сторона | Состав |
|---------|--------|
| Вход | `Catalog.ОчередьЭлектронныхЧековКОтправке` (контакт получателя, тип рассылки `Enum.ТипыРассылкиЭлектронныхЧеков`) 🟢 |
| Режим | `Constant.ОтправкаЭлектронныхЧековПослеПробитияЧека` (сразу/отложенно) 🟢 |
| Выход | отметка доставки в очереди; при ошибке — повтор на следующем запуске 🟢 |

## 3. Инварианты контрактов

- **И-1** Домен НЕ вызывает внутренние (не-фасадные) процедуры библиотеки напрямую. 🟢 (ADR-0006)
- **И-2** Все обёртки Сервера ККМ возвращают `{Ошибка, Описание}` и не пробрасывают исключения. 🟢
- **И-3** Успех HTTP-операции Сервера ККМ ⇔ `Result.Code = 0`. 🟢
- **И-4** Пробитие/подключение/смена — асинхронные; результат только в callback. 🟢
- **И-5** Каждая фискальная/платёжная операция оставляет запись в соответствующем РС-журнале. 🟢

## Пробелы (🔴)

- 🔴 Точная JSON-схема `Result` методов Сервера ККМ (поля `ДанныеККМ`/`ДанныеСмены`/открытия/закрытия) — только по сигнатурам и комментариям-ссылкам на docs.rbsoft.ru; не верифицирована против живого сервера.
- 🔴 Параметры строки чека и оплаты (`ПараметрыФискальнойСтрокиЧека`/`ПараметрыСтрокиОплаты`) — структура внутри библиотеки, точный набор полей не разбирался.
- 🔴 Контракт эквайринга (`ОборудованиеПлатежныеСистемы*`) описан гипотетически (🟡), вглубь не разбирался.
