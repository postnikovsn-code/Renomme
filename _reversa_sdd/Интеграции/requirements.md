## Обзор

Модуль «Интеграции и обмен» — транспортный/протокольный слой внешних интеграций конфигурации «ОТЕЛЬ». Он отвечает за: межбазовую репликацию через планы обмена 1С (XML + FTP), получение бронирований с сайта (HTTPS GET JSON), HTTP-инфраструктуру заселений/ежедневного отчёта, рассылку и точечные сообщения гостям через мессенджеры (WhatsApp/Telegram поверх Green API), приём оплаты и синхронизацию платежей через эквайринг PayKeeper, выгрузку в Бухгалтерию/НДС и обмен картинками с базой планшета (COM). 🟢

Архитектура слоистая: диспетчер `МесенджерСервер` → адаптеры `WhatsAppСервер`/`TelegramСервер` → REST-клиенты `GREEN_WhatsApp`/`Обработка.GREEN_Telegram`; общий транспорт FTP (`ФТПСервер`) для планов обмена и выгрузок; токены и адреса каналов вынесены в константы. 🟢

## Границы (не дублируется — только связь)

- Выгрузка ФМС и `PassportBox` → модуль «Гости». 🟢
- `СерверККМ`/фискальное оборудование → модуль «Оборудование» (БПО). 🟢
- `ОбменГорничныеСервер` (COM-обмен с базой горничных) → модуль «Горничные». 🟢
- Документ «Выписка» как учётная сущность → модуль «Финансы»; здесь — только её сериализация в обмене (`ОбменВыписка`). 🟢

## Ответственности

- Узловой обмен между базами сети: чтение/запись сообщений с изменениями плана обмена, доставка XML по FTP. 🟢
- Получение бронирований с сайта по HTTPS (окно 90 дней, JSON). 🟢
- Получение заселений и ежедневного отчёта от удалённых HTTP-сервисов (LIVE/CHEHOV/DomSovetov/StreetArt). 🟢
- Диспетчеризация исходящих сообщений гостям по включённым каналам (WhatsApp/Telegram/MAX). 🟢
- Нормализация телефонного номера к формату Green API (`<номер>@c.us`). 🟢
- Регламентная рассылка выехавшим гостям с идемпотентностью. 🟢
- Приём оплат PayKeeper: token-сессия, опрос списка платежей, upsert в РС, привязка success-платежей к долгам. 🟢
- Выгрузка заявок/счетов/НДС в Бухгалтерию (XML + FTP). 🟡
- Обмен картинками с базой планшета через COM с ретраями. 🟡

## Бизнес-правила

- BR-01 — При узловом обмене коды ошибок чтения `1` и `30` трактуются как «нет нового сообщения» и НЕ являются фатальными; обмен продолжается по следующим узлам. 🟢 (`ОбменГостиницы/Module.bsl`)
- BR-02 — `ЭтотУзел` пропускается при переборе узлов плана обмена. 🟢
- BR-03 — Окно выборки бронирований с сайта по умолчанию — последние 90 дней (`КонечнаяДата − 90`), формат дат `дд-ММ-гггг`. 🟢 (`ОбменСайт/Module.bsl:2-25`)
- BR-04 — Сообщение гостю отправляется ТОЛЬКО если включён хотя бы один канал (`МесенджерВключен()` — ИЛИ по константам `СообщенияЧерезGREЕN_WhatsApp/_Telegram/_MAX`). 🟢
- BR-05 — Нормализация телефона: отбросить не-цифры; `8…`→`7…`; ровно 10 цифр→`7`+номер; иначе `0` (невалидно). 🟢 (`GREEN_WhatsApp.ТелефонGREEN`)
- BR-06 — КодОшибки `100` от Green API/диспетчера означает «нет WhatsApp/Telegram на этом телефоне». 🟢
- BR-07 — Идемпотентность рассылки обеспечивается РС `РассылкаWhatsApp` (ключ Клиент+ДатаРассылки+ТипРассылки); уже разосланные и пустые телефоны исключаются из выборки. 🟢
- BR-08 — Токен PayKeeper кэшируется в структуре соединения c TTL 1200 c; обновляется лениво, когда `ВремяИстечения < ТекущаяДата()`. Без токена — `ВызватьИсключение`. 🟢
- BR-09 — При upsert платежа PayKeeper по `ИД_Платежа` сохраняются `ГУИД` и `ДатаСоздания` существующей записи (повторный приём не перезаписывает их). 🟢
- BR-10 — Привязка платежа к документу долга (`СвязатьPayKeeperПлатежи`) выполняется ТОЛЬКО для статуса `success`. 🟢
- BR-11 — Транспорт PayKeeper детектирует HTML-страницы ошибок хостинга («Система заблокирована…», `<!DOCTYPE html>`) и извлекает текст ошибки вместо разбора JSON. 🟢
- BR-12 — Список платежей по умолчанию запрашивается по статусам `success,canceled,failed,refunding,partially_refunded,refunded` и платёжным системам `93,52`. 🟢
- BR-13 — `ВГ_ВыпискаГостиницы` имеет пустой состав плана; обмен выписками идёт вручную через сериализацию `DocumentObject.Выписка` (`ОбменВыписка`), узел ищется `НайтиПоКоду("БУХ")`. 🟡
- BR-14 — COM-соединение с базой планшета выполняется до 3 попыток (ретрай через метку `Перейти ~Соединение`). 🟡 (`ОбменКартинкаСервер`)

## Функциональные требования

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|-------------------|
| RF-01 | Выполнять узловой обмен по всем узлам плана `ОбменГостиницы`: чтение, затем запись сообщения с изменениями, доставка XML по FTP | Must | Для каждого узла (кроме `ЭтотУзел`) вызываются чтение и запись; коды 1/30 не прерывают цикл; файл доставлен через `ФТПСервер` |
| RF-02 | Получать бронирования с сайта по HTTPS GET с окном 90 дней и парсингом JSON | Must | Возвращается `{ДанныеJSON, Ошибка, Описание}`; при отсутствии дат подставляются `ТекущаяДата()` и `−90 дней` |
| RF-03 | Получать заселения и ежедневный отчёт от HTTP-сервисов по серверу из константы | Must | GET по корректному пути сервера; код состояния ≥ 300 → ошибка; ответ распарсен из JSON |
| RF-04 | Диспетчеризовать исходящие сообщения (`ОтправитьДанные_Месенджер`) по включённым каналам | Must | Телефон нормализован; вызваны адаптеры только включённых каналов; результат — структура с `Ошибка/КодОшибки/Описание` |
| RF-05 | Отправлять текст/файл/ссылку через Green API (WhatsApp) | Must | POST на `waInstance<Инстанс>/<Метод>/<Токен>`; ответ 200 → JSON; иначе исключение со статусом и телом |
| RF-06 | Отправлять сообщения через Telegram (Green API) поверх `Обработка.GREEN_Telegram` | Should | `ПроверитьНаличиеТелеграм()` возвращает `chatid`; отправка по `chatid` |
| RF-07 | Выполнять регламентную рассылку выехавшим гостям с идемпотентностью | Should | Повторный запуск за ту же дату не дублирует отправку (проверка РС `РассылкаWhatsApp`) |
| RF-08 | Поддерживать token-сессию PayKeeper с ленивым обновлением (TTL 1200 c) | Must | При истёкшем токене делается GET `/info/settings/token/`; токен подставляется в тело запросов |
| RF-09 | Опрашивать список платежей PayKeeper и делать upsert в РС `PayKeeperПлатежи` | Must | Маппинг полей применён; повторный приём сохраняет `ГУИД/ДатаСоздания`; success → привязка к долгу |
| RF-10 | Возврат денег PayKeeper, статус платежа, QR-код СБП, список платёжных систем | Should | Вызовы соответствующих endpoint возвращают результат либо извлечённую ошибку HTML |
| RF-11 | Выгружать заявки/счета/НДС в Бухгалтерию (XML + FTP) | Should | Файл сериализован и доставлен через `ФТПСервер` с именем из `ПолучитьИмяФайлаОбменаФТП` |
| RF-12 | Обмен картинками с базой планшета через COM с ретраями | Could | COM-соединение установлено (до 3 попыток); вызван RPC `ЗагрузитьКартинку()` |
| RF-13 | Сериализовать `DocumentObject.Выписка` в XML для обмена с Бухгалтерией | Should | Узел `БУХ` найден; XML сформирован и доставлен |

## Критерии приёмки

```gherkin
# Узловой обмен (RF-01)
Дано настроенный план обмена ОбменГостиницы с одним внешним узлом и доступным FTP
Когда вызывается ВыполнитьОбменДанными()
Тогда по узлу прочитано входящее сообщение, записано исходящее с изменениями
  И XML-файл доставлен на FTP узла
  И временный файл удалён

Дано узел плана обмена без нового входящего сообщения (код ошибки 1 или 30)
Когда выполняется ПрочитатьСообщениеСИзменениями()
Тогда ошибка НЕ считается фатальной и цикл продолжается по следующим узлам

# Обмен с сайтом (RF-02)
Дано адрес сервера сайта и пустые даты периода
Когда вызывается ПолучитьДанныеБронирования(АдресСервера)
Тогда КонечнаяДата = ТекущаяДата(), НачальнаяДата = КонечнаяДата − 90 дней
  И выполняется HTTPS GET и возвращается {ДанныеJSON, Ошибка=Ложь}

Дано недоступный сервер сайта
Когда вызывается ПолучитьДанныеБронирования(...)
Тогда возвращается {ДанныеJSON=Массив(), Ошибка=Истина, Описание=ОписаниеОшибки()}

# Диспетчер мессенджеров (RF-04, RF-05)
Дано включён канал WhatsApp и валидный телефон гостя
Когда вызывается ОтправитьДанные_Месенджер('ОтправитьТекст', Телефон, Текст)
Тогда телефон нормализован к <номер>@c.us
  И GREEN_WhatsApp.sendMessage возвращает 200
  И результат содержит Ошибка=Ложь

Дано телефон без установленного WhatsApp
Когда выполняется отправка через Green API
Тогда результат содержит КодОшибки=100 и Ошибка=Истина

# Рассылка (RF-07)
Дано рассылка за дату D уже выполнена клиенту K (запись в РС РассылкаWhatsApp)
Когда повторно запускается рассылка за дату D
Тогда клиент K исключается из выборки и сообщение не отправляется повторно

# PayKeeper (RF-08, RF-09)
Дано истёкший токен PayKeeper (ВремяИстечения < ТекущаяДата())
Когда выполняется любой запрос к PayKeeper
Тогда сначала делается GET /info/settings/token/ и токен обновляется (TTL 1200 c)

Дано платёж PayKeeper со статусом success, ранее принятый (есть запись в РС)
Когда выполняется ПолучитьИОбработатьСписокПлатежей()
Тогда запись обновляется с сохранением ГУИД и ДатаСоздания
  И платёж привязывается к документу долга

Дано хостинг PayKeeper вернул HTML-страницу «Система заблокирована»
Когда выполняется ВыполнитьЗапрос(...)
Тогда вместо разбора JSON извлекается и возвращается текст ошибки из HTML
```

## Приоритизация (MoSCoW)

| Требование | MoSCoW | Обоснование |
|-----------|--------|---------------|
| Узловой обмен XML+FTP (RF-01) | Must | Критический путь межбазовой репликации сети отелей |
| Обмен с сайтом (RF-02) | Must | Источник входящих бронирований (канал продаж) |
| HTTP заселения (RF-03) | Must | Питает оперативные данные заселений из удалённых баз |
| Диспетчер + Green API (RF-04, RF-05) | Must | Единственная точка исходящих сообщений гостям |
| PayKeeper token-сессия + платежи (RF-08, RF-09) | Must | Приём оплаты и сверка долгов — финансовый контур |
| Telegram-канал (RF-06) | Should | Альтернативный канал, есть fallback на WhatsApp |
| Рассылка выехавшим (RF-07) | Should | Маркетинговый сценарий, не критичен для операций |
| Выгрузка Бухгалтерия/НДС (RF-11, RF-13) | Should | Периодическая интеграция, есть ручной режим |
| Возврат/статус/QR PayKeeper (RF-10) | Should | Вспомогательные операции эквайринга |
| COM-обмен картинками (RF-12) | Could | Узкий сценарий (планшет горничных), ретраи через goto |

> Приоритет выведен по частоте вызова и позиции в цепочке зависимостей.
