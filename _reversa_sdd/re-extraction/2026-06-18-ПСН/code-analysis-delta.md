## 1. Бронирование

### 1.1 Документ `ЗаявкаНаБронирование` (изменён, НЕ новый)
🟢 Документ существовал в `ec0e8d9`; статус всех файлов — Modified. Коммит **дополняет** его.

**Новый реквизит:**
- `ЦенаПродажиАгентом` — `Число(10,2)`, денежный; необязателен (🟡 нет `fillChecking`). Сумма продажи номера турагентством; база печати «Чека агента». 🟢 тип / 🟡 обязательность.

**Новая функциональность «Чек агента»** (модуль формы `Forms/ФормаДокумента/Module.bsl`, +89; форма +124):
- Группа `ГруппаЧекАгенту` (`UsualGroup`, горизонтальная) с полем `ЦенаПродажиАгентом` и кнопкой `ЧекАгента`; команда формы `ЧекАгента` (id 71). 🟢
- `&НаКлиенте Процедура ЧекАгента(Команда)` — формирует параметры чека ККМ: одна позиция «Услуги гостиницы N сут.» (`N = Цел((РезервПо − РезервС)/86400)`, минимум 1), цена/сумма = `ЦенаПродажиАгентом`, `ЭтоАванс = Ложь`. НДС считается через `ДокументыСервер.СтавкаНДСТекущая / СуммаНДС / УчитыватьНДС_Чек` с учётом флагов организации `ВсеСНДС/СтавкаНДС`. Открывает `ОбщаяФорма.Чек` с блокировкой интерфейса. 🟢
- `&НаКлиенте Процедура ЗакрытиеФормы_ЧекАгента(Результат, ДополнительныеПараметры) Экспорт` — обработчик-заглушка: при `Неопределено` выход, иначе `ОчиститьСообщения()`. 🟢
- В `ПриСозданииНаСервере` (две вставки): `ГруппаЧекАгенту.Доступность = ОбщийФункционалСервер.ЗначениеРеквизитаНаСервере(Объект.Бронирует, "Турагентство")`. Группа доступна, только если контрагент `Бронирует` (тип `СправочникСсылка.Клиенты`) — турагентство. 🟢

**Проведение/движения регистров** — в дельте отсутствуют; `ObjectModule`/`ManagerModule` не затрагивались. Чек печатается через внешнюю форму, движений не порождает. 🟢

### 1.2 `ЛистОжидания` → `ЛистОжидания_НеИспользуется` (deprecation)
🟢 Переименование объекта (не удаление): `name`/синоним → «Лист ожидания не используется»; `inputByString`/`defaultObjectForm`/`defaultListForm` перенацелены; UUID объекта и реквизитов сохранены. В `Configuration.mdo` строка регистрации заменена на `Document.ЛистОжидания_НеИспользуется` — объект по-прежнему зарегистрирован. 🟢
- Новый `Forms/ФормаДокумента/Module.bsl` функционально почти идентичен старому (diff `-w`); единственное содержательное отличие — `ПарамФормы.Вставить("НомерВРезерв", НомерВРезерв)` (локальная переменная найденного свободного номера) вместо `Объект.НомерВРезерв` (пустого реквизита), помечено `// + Аудит`. Остальное — удаление мёртвых комментариев и отступы. 🟢
- Структура модуля без изменений: `ПриСозданииНаСервере`, `ПеревестиВБронь`/`ПеревестиВБроньНаСервере` (поиск свободного номера запросом по `РегистрСведений.ЗанятостьНомеров` + `Справочник.НомернойФонд`, установка пометки удаления), `СоздатьОткрытьЗаявкаНаБронирование` (открывает `Документ.ЗаявкаНаБронирование`). 🟢

**Связь:** 🟡 `ЛистОжидания` — очередь-предшественник: при появлении свободного номера переводил запись в `ЗаявкаНаБронирование` и помечался на удаление. Новый документ функционально **не заменяет** лист ожидания (это была отдельная сущность-очередь). 🔴 ПРОБЕЛ: откуда вызывался лист ожидания и чем заменён его бизнес-поток — вне дельты.

## 2. Аудит и отчётность

### 2.1 `ОтчетКассоваяСмена` (форма отчёта, +348)
🟢 Единственный изменённый отчёт. `ManagerModule` отчётов не менялся; отчёт строится вручную через `ТабличныйДокумент` (без СКД). «+348» — в значительной мере **дублирование** старого тела + вынос в функции, плюс одна новая фича.

- `&НаСервере Функция ТабДокКасса()` — действующая версия. Запрос по `Документ.КассовыйДокумент` (фильтр `НомерСменыККМ`, период, `ВключатьПроизвольныеЧеки`), области макета `МакетКасса`; итоги `ИтогоПоКарте/Наличные/Возврат/Отель/Коворкинг`. **Новое:** обработка групповых счетов `ТипЗнч(...) = Тип("ДокументСсылка.ГрупповыеСчета")` — по `ДокументДолг.ДокументыДолги` собирается сводная `ТЗ_Данные(УслугаКорень, СуммаОплаты)`, сворачивается и выводится разбивкой по группам доп. услуг через `ПрисоединитьГруппа`; групповая сумма добавляется к `ИтогоОтель`. 🟢
- `&НаСервере Функция ТЗ_Заявка(ДокументДолг, ДокументОплаты)` — **новая**. Запрос `Документ.ЗаявкаНаБронирование.РаспределениеОплатДолги ⟕ …ДопУслуги` (по `ДолгиГУИД = ГУИД`), группировка по услуге; колонка `УслугаКорень` (для услуги без значения — «Проживание», иначе подъём к корню иерархии через `КореньУслуга`). 🟢
- `&НаСервере Процедура ПрисоединитьГруппа(ТабДок, Макет, ТЗ_ГруппыДопУслуги, ТЗЗаявка)` — **новая**. Выводит область `Строка|Группа`: сумма по «Проживание», затем по группам доп. услуг. 🟢
- `&НаСервере Функция ТабДокКасса_1()` — **мёртвый клон** старого тела `ТабДокКасса` (inline-запрос заявки, без `ГрупповыеСчета`); не вызывается. 🟡 (полнотекстовый поиск вызовов по всей конфигурации не делался). Кандидат на удаление при следующей чистке.
- `КореньУслуга` (рекурсивный подъём), `Флажок` (`&НаСервереБезКонтекста`) — без изменений. 🟢

### 2.2 `ПечатьСервер` (+11/−9) — текстовые формулировки
🟢 Логика не тронута; только наименования услуг в печатных формах: «Проживание …» / «Услуги гостиницы» → **«Услуги по предоставлению мест для временного проживания в гостинице»** (юр. формулировка для фискальных документов), плюс перенос точки-разделителя в конкатенации. Затронуто ~7 мест (стр. ≈73, 161, 205, 281, 1584, 1648, 1930, 1994). 🟢

### 2.3 `ДокументыСервер` (+6/−3) — фикс комиссии
🟢 Блок `// + Аудит` (≈325–343), расчёт комиссии по услугам:
- Отбор строк: `Новый Структура("ГУИД", Истина, …ДолгиГУИД)` (ошибочный 3-параметр) → `Новый Структура("ГУИД", …ДолгиГУИД)` — корректный отбор `НайтиСтроки` по `ГУИД`.
- База суммы: `СуммаУслуга = СтрокаУслуга.Сумма` → **`СтрокаУслуга.Цена * СтрокаУслуга.Количество`**; далее `СуммаКомиссииУслуги += Окр(СуммаУслуга * ПроцентКомиссии/100, 2)`. 🟢

## 3. Интеграции и обмен

### 3.1 `TelegramСервер` (+4/−4) и `MAXСервер` (+10/−10) — контракт ответа
🟢 В функциях отправки переименовано поле структуры-результата `ОписаниеОшибки` → `Описание`, чтобы совпасть с консьюмером `МесенджерСервер` (`Ответ.Описание`). Логика HTTP-отправки (GREEN-API) не менялась.
- Telegram: `ОтправитьТекстGreenTelegram`. MAX: `ОтправитьТекстGreenMAX`, `ОтправитьФайлИТекстGreenMAX`.
- `MAXСервер` — отправка в мессенджер **MAX** через GREEN-API (токен `Константы.GREENApiToken_MAX`), симметричен Telegram/WhatsApp. 🟢
- 🟡 **Несимметрия:** функции `ПроверитьНаличие…` сохранили старое поле `ОписаниеОшибки` — контракт результата внутри модулей стал неоднородным (потенциальный источник путаницы, но в текущем потоке ошибок не вносит).

### 3.2 `РассылкаWhatsApp` (+28/−20) — правила и текст рассылки ДР
🟢 Процедура `РассылкаWhatsApp_ДеньРождения(ДатаРассылки) Экспорт` и `ТекстРассылки_ДеньРождения(Клиент)`:
1. Закомментированы фильтры площадок `ИЛИ НастройкиСервер.ЭтоЧехов()` и `ИЛИ НастройкиСервер.ЭтоЛайв()` в условии раннего `Возврат` — рассылка ДР больше не блокируется для «Чехов»/«Лайв».
2. Снят порог отбора `И КоличествоЗаявок.Количество >= 3` (SDBL); удалён мёртвый блок `МесенджерСервер.ПроверитьWhatsAppGreen(...)`.
3. Новый текст поздравления (Екатеринбург, «Art de vivre», скидка 10% в ДР и 10 дней после) вместо старого (скидка 20%). 🟢

**Запуск:** `ManagedApplicationModule` (+9): при `ИмяПользователя() = "РассылкаДеньРождения"` вызывается `РассылкаWhatsApp.РассылкаWhatsApp_ДеньРождения(НачалоДня(ТекущаяДата))` с авто-`ЗавершитьРаботуСистемы(Ложь)`. 🟢 (Это пакетный запуск по расписанию под спец-пользователем — не относится к PassportBox.)

### 3.3 `ОбменБухгалтерияНДС` (+16/−8) — фикс ставки НДС
🟢 Функция `ЗаписатьЗаявки(ИмяФайла, ДатаС, ДатаПо, ТипыСчетов)` (выгрузка в бухгалтерию через файл/FTP): в 8 местах `ДокументыСервер.СтавкаНДСЧисло(СтавкаНДСЧислоТекущий)` → `…СтавкаНДСЧисло(СтавкаНДСТекущий)`. Прежде в функцию подавался уже-числовой результат (двойное преобразование), что давало некорректную числовую ставку. Формат файла и набор `ТипыСчетов` не менялись. 🟡 семантика `СтавкаНДСЧисло`/тип `СтавкаНДСТекущий` в `ДокументыСервер` не верифицированы; само изменение однозначно. 🟢

## 7. Подключаемое оборудование (БПО) — PassportBox

🟢 **Чистый рефакторинг без изменения поведения.** Настройки сканера паспортов вынесены из `НастройкиСервер` в новый выделенный общий модуль.

- Новый серверный ОМ **`PassportBox_Настройки`** (зарегистрирован в `Configuration.mdo`). Перенесены дословно (−37 в `НастройкиСервер` / +37):
  - `PassportBoxНастройки() Экспорт` — читает константы `PassportBoxIP/Порт/Таймаут/Активность`, дефолты (Порт=80, Таймаут=30), возвращает `Структуру("IP,Порт,Таймаут,Активность")`. Только чтение констант. 🟢
  - `PassportBoxПроверитьСвязь() Экспорт` — Snapshot-проверка связи через `PassportBoxВызовСервера.СоздатьСоединение/ПолучитьКартинку`, возвращает `Структуру("Успех,Описание")`. 🟢
- `PassportBoxВызовСервера/Module.bsl` (стр. 238): единственная правка — квалификатор вызова `НастройкиСервер.PassportBoxНастройки()` → `PassportBox_Настройки.PassportBoxНастройки()`. Логика обращения к устройству не тронута. 🟢
- Константы `PassportBoxIP/Порт/Таймаут/Активность`: тип/длина/точность **не менялись**, изменены только UUID (регенерация EDT). 🟢
- Форма `DataProcessor.НастройкиPassportBox` — косметика (удалён namespace, схлопнуты дефолтные свойства). 🟢
- Интеграция работает по **HTTP** (Snapshot, порт 80), не COM. 🟢
