**Класс:** транзакция без `ОтменитьТранзакцию` и без `Попытка`
**Метка:** 🟢 ПОДТВЕРЖДЕНО
**Связь:** уточняет `H6` старого аудита (A1 `:343`) — счёт из A1 (85 / 84 / 30) подтверждён,

**Сценарий повреждения** (на `ВыпискаСвязьУдалитьНаСервере`, `2234–2270`):

1. Оператор отмечает три связи «оплата ↔ счёт» и жмёт «Удалить связь».
2. Цикл `2238–2263` идёт по отмеченным строкам. Для каждой он **сначала** правит

3. На третьей итерации документ долга заблокирован другим сеансом → исключение.
4. Отката нет. Платформа откатывает транзакцию сама на границе серверного вызова, но
   **реквизиты формы в памяти не откатываются**: остатки по первым двум связям уже
   увеличены, а в базе связи остались.
5. Оператор видит согласованную на вид форму с завышенными остатками и продолжает
   разносить оплаты от этих чисел. Каждая следующая операция пишет в базу суммы,
   выведенные из несуществующего состояния.

`Documents\СписаниеДопУслуг\Forms\ФормаДокумента\Module.bsl:429` при живых транзакциях
`331–349` и второй в модуле.

**Почему CRITICAL, а не HIGH.** Повреждение молчаливое: пользователю не показывается ни
ошибки состояния, ни расхождения. Затронут контур разнесения безналичных платежей —
то есть деньги. И граница «есть защита / нет защиты» точно совпадает с границей
«библиотека / наш код», что означает системную причину, а не отдельный пропуск.


Обходится массив, полученный из `НайтиСтроки` (`:15`), а удаление идёт из самой
табличной части. Строки табличной части адресуются по индексу: после первого `Удалить`
оставшиеся элементы массива указывают на сместившиеся позиции. При **одной** оплате
цикл делает ровно одну итерацию и дефект не проявляется; при **двух и более** вторая
итерация работает с чужой или уже удалённой строкой.

**(в) Сброс остатка вместо вычитания — `:39`.**

```
:39  ОстатокСуммаВозврата = СуммаВозврата - СтрокаРаспределениеОплат.СуммаОплаты;
```

Должно быть `ОстатокСуммаВозврата - …`. Что это именно ошибка, доказывает соседняя
ветка: на `:31–:33` тот же самый паттерн уже помечен как правка аудита —
`//ОстатокСуммаВозврата = СуммаВозврата - …` закомментировано и заменено на
`ОстатокСуммаВозврата = ОстатокСуммаВозврата - …`. Во второй ветке правку не сделали.

**Сценарий повреждения.** Счёт коворкинга, две строки распределения по 300 ₽ от одной
оплаты. Возврат 500 ₽. Ветка `Иначе` (`:34`): первая итерация удаляет строку 300 ₽,
остаток становится `500 − 300 = 200`; вторая итерация вместо `200 − 300` считает снова
`500 − 300 = 200` и уходит в ветку `:41`, уменьшая `СуммаОплаты` второй строки на 200
вместо 0. Затем `:48` вычитает **полную** `СуммаВозврата` из `СтрокаДокументыОплаты.СуммаРаспределено`.
Итог `:51–:54` пересчитывается по испорченной таблице, `:56`
`ДокументДолгОбъект.Записать(РежимЗаписиДокумента.Проведение)` фиксирует расхождение
между `ДокументыОплаты.СуммаРаспределено` и суммой `РаспределениеОплатКоворкинг`.
Фиксация на `:58` — безусловная.

Арифметическая часть (в) смежна с `24-H30` из B5 (потеря хвоста оплаты коворкинга), но
это другой модуль и другой оператор; лечится отдельно.

### 🟡 MEDIUM

#### `24-M60` — Журнал СМС в регистре сведений мёртв целиком, а его ключ спроектирован так, что защита от дубля в нём невозможна

**Уровень:** MEDIUM
**Метка:** 🟢 ПОДТВЕРЖДЕНО
**Связь:** тот же класс, что «антидубль в рассылках не срабатывает» из B1 — здесь на
другом объекте (регистр `СМС` заявки, а не контур рассылок).

`РегистрСведений.СМС` — независимый непериодический (в
`InformationRegisters\СМС\СМС.mdo` нет ни `informationRegisterPeriodicity`, ни `writeMode`).
Измерения: `Бронь` (`:69`), **`ДатаОтправки`** (`:86`), `Телефон` (`:104`),
`ОтметкаОтменаБронирования` (`:124`). Ресурс один — `Текст` (`:51`).

**(а) Ключ включает значение со временем.** Пишущая функция
`ЗаписатьОтправкуСМС_Регистр` `2670–2681` заполняет `НН.ДатаОтправки=ТекущаяДата()`
(`:2674`). `ДатаОтправки` — измерение, то есть часть ключа. Две отправки, разошедшиеся
на секунду, дают две разные записи; платформенная уникальность ключа не сработает
никогда, потому что ключ никогда не совпадает.

**(б) Запись без замещения.** `:2678` — `НашНабор.Записать(Ложь)`, то есть добавление
без замещения, и без установки `НашНабор.Отбор`. По всей конфигурации таких мест пять:
`ОборудованиеПлатежныеСистемы:316`, `ОперацииПроверкиКМ:446` и `:640`,
`ОперацииСПодключаемымОборудованием:190` и это. Четыре первых — контур БПО, там набор
предварительно отобран; здесь отбора нет.

**(в) Проверка на дубль по регистру существует и не вызывается.**
`Функция НетОтправленныхСМС_Регистр` `2458–2470` (обе границы проверены) делает ровно
правильный запрос — `СМС.Бронь = &Бронь И СМС.ОтметкаОтменаБронирования = &ОтметкаОтменаБронирования`,
без `ДатаОтправки`. Сплошной поиск по имени `НетОтправленныхСМС_Регистр` по всему `src` —
**одно попадание, строка её собственного объявления**. Ни одного вызова.
То же для `ЗаписатьОтправкуСМС_Регистр` (`2670`) — одно попадание, объявление.
Сплошной поиск по `РегистрыСведений\.СМС|РегистрСведений\.СМС` по всему `src` даёт
ровно две строки — `:2462` (внутри мёртвой проверки) и `:2671` (внутри мёртвой записи).

**Что работает вместо этого.** Живая защита — `Функция НетОтправленныхСМС` `2450–2455`,
она читает табличную часть документа `Объект.СМС` с отбором
`("ОтметкаОтменаБронирования, КодОшибки", …, 0)`. Ноль в `КодОшибки` действительно
означает успех: `Функция ОтправитьСМС` `2601–2651` инициализирует
`Результат.КодВозврата = 0` (`:2602`) и поднимает его до 1 или 2 только на ошибке
(`:2630`, `:2646`). То есть **сегодня дубли не идут** — но защита держится на табличной
части документа, а параллельный регистровый путь оставлен в коде в нерабочем виде.

**Сценарий повреждения (отложенный).** Кто-то включает регистровый журнал — вызывает
`ЗаписатьОтправкуСМС_Регистр` из `ЗавершениеВопросаОтправитьСМС` (`2406–2447`) и
`НетОтправленныхСМС_Регистр` вместо `НетОтправленныхСМС`. Проверка (в) ищет запись по
`Бронь + ОтметкаОтменаБронирования`, а запись (а) кладёт её с новым `ДатаОтправки`
каждый раз. Первая же повторная отправка запишется рядом, а не поверх; `Записать(Ложь)`
(б) её не заместит. Гость получает СМС столько раз, сколько раз нажали кнопку, и
`РегистрСведений.СМС` растёт без ограничения.

### 🔵 LOW

#### `24-L52` — Одна транзакция на 228 строк удерживает блокировки на всё формирование счетов заявки

**Уровень:** LOW
**Файл:** `Documents\ЗаявкаНаБронирование\Forms\ФормаДокумента\Module.bsl`,
`Функция ДобавитьСчетаНаСервере(ТолькоПроживаниеПараметр, ТолькоУслугиПараметр)` `:5826`
… `КонецФункции` `:6060` (обе границы проверены), транзакция `5829–6057`.
**Метка:** 🟡 ВЫВЕДЕНО

Самая длинная транзакция конфигурации: 228 строк между `НачатьТранзакцию()` и
`ЗафиксироватьТранзакцию()`, без `Попытка` и без `ОтменитьТранзакцию` (входит в 54 из
`24-C22`). Для сравнения, вторая по длине в том же модуле — `6730–6759`, 29 строк.

Внешних вызовов внутри нет (раздел 2), поэтому уровень LOW, а не выше: сетевого
таймаута, который подвесил бы транзакцию, здесь взяться неоткуда. Риск — конкурентный:
всё время формирования счетов заявки удерживаются блокировки на документе и на всех
затронутых счетах, а формирование идёт по табличным частям `Проживание`, `ДопУслуги`
и `СчетаДетальноДолги` целиком. На заявке с длинным проживанием второй администратор,
открывший ту же заявку, ждёт до конца.

**Сценарий.** Групповая заявка на 30 дней, два администратора работают с ней
одновременно. Первый жмёт «Добавить счета» → транзакция `5829` держится всё время
разбора; второй в этот момент сохраняет свою правку → ожидание блокировки, при
превышении таймажа — исключение, и дальше по сценарию `24-C22`, потому что отката нет.
