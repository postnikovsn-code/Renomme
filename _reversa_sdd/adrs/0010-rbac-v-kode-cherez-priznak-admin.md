# ADR 0010 — Доменный RBAC в коде через реквизит `Пользователи.Админ` вместо ролей платформы

- **Статус:** Принято (исторически) · 🟢 ПОДТВЕРЖДЕНО кодом
- **Дата:** неизвестна
- **Модуль:** сквозной (Бронирование, Ценообразование, Горничные, Размещение)

## Контекст

Нужно разграничить операторов стойки (ресепшн) и администраторов отеля: первые ведут брони/оплаты, вторые дополнительно удаляют документы, правят цены и тарифы. Стандартный путь 1С — роли платформы с правами на объекты.

Свидетельства:
- Доменная роль `Роль.Администратор` ПУСТА (`Rights.rights` — только глобальные флаги по умолчанию, ни одного `<object>`). 🟢
- Разграничение реализовано в КОДЕ через `ПараметрыСеанса.ТекущийПользователь.Админ` / `.Администратор` и фасады `НастройкиСервер.ЭтоАдмин():73-76` / `ЭтоАдминистратор():78-84` (проверка флага ИЛИ `Код="Администратор"`). 🟢
- Примеры: запрет удаления брони не-админу (BR-07); режим «только просмотр» цен (`КалендарьЦен`), тарифов, спец-форм при `НЕ Админ`. 🟢
- Роли в `.rights` — преимущественно инфраструктурные (БПО/БСП), доменные документы они по отдельности не ограничивают. 🟢

## Решение

Реализовать бизнес-разграничение ресепшн-vs-админ булевыми реквизитами `Catalog.Пользователи.Админ`/`.Администратор`, проверяемыми в коде через фасады `НастройкиСервер.*`; роли платформы оставить для инфраструктуры (полный доступ + БПО), доменную роль `Администратор` не наполнять.

## Рассмотренные альтернативы

- **Полноценные роли платформы** (`Администратор` с правами на объекты, отдельная роль «Оператор»). Отклонено фактически: доменная роль оставлена пустой, контроль перенесён в код — вероятно, ради гибкости (флаг на пользователе проще включить, чем перенастраивать роли) и из-за наследия.
- **Ограничения доступа на уровне записей (RLS).** Не применено для этого разграничения.
- **Гибрид (роли + флаг).** Не реализован; контроль почти целиком в коде.

## Последствия

- ➕ Простое включение прав «администратора» галочкой в карточке пользователя; гибкость без перенастройки ролей.
- ➖ 🔴 Нет централизованной, аудируемой матрицы прав — разрешения размазаны по десяткам форм/модулей в виде `Если ... Админ`.
- ➖ 🔴 Часть проверок `Если ... Админ` ЗАКОММЕНТИРОВАНА (напр. в `Интерфейс`/шахматке) — защита местами фактически снята, незаметно для администратора ИБ.
- ➖ Обход возможен: пользователь с `ПолныеПрава` и `Админ=Ложь` ограничен лишь кодом, не платформой.
- ⚠ При миграции права нужно собрать из кода (`Админ`-проверки) в явную модель ролей/политик целевой системы.
