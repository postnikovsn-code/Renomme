### 2.2 Откуда берутся суммы (гостиничная ветка)

Все три гостиничные обработки построены по одной схеме
(`СформироватьОтчетНаСервере` = основной отчёт; `СформироватьОтчетОплатыНаСервере` = отчёт
по оплатам; `СформироватьОтчетРаспределениеОплатНаСервере` = распределение;
`КомиссияРаспределение`/`ПлатежиКонтрагентуРаспределение` = агентские платежи):

1. **Начисление.** Запрос к `Документ.ЗаявкаНаБронирование` + подчинённым табличным частям
   `.Проживание`, `.Счета`, `.ДопУслуги`, `.СчетаДетальноДолги`
   (`ФинансовыйРезультатОтель:139-235`). Отбор: `ПометкаУдаления = ЛОЖЬ`,
   `ТипБронирования <> &ТипБронирования`, диапазон дат проживания и
   `Статус ∈ {Выехал, Проживает, Неустойка}`.
2. **Разнесение по дням.** Внешний цикл — календарный день `Дата_П` от `ДатаОтчетаС`
   до `ДатаОтчетаПо`; внутренний — заявки, попавшие в день по
   `ДеньПроживанияМинимум/Максимум` (`:287, 306-308`). Сумма проживания за день берётся
   из строки `Проживание` этого дня, не делится и не округляется — **накопления ошибки
   округления при разнесении по дням в гостиничной ветке нет**.
3. **Комиссия агента.** `ДокументыСервер.ПроцентКомиссииКлиента(Бронирует, РезервС)`
   (`ФинансовыйРезультатОтель:412`) → `ДокументыСервер.ПроцентКомиссии:819-841` — запрос
   к табличной части `Справочник.Клиенты.ПроцентыКомиссии` с отбором по дате начала действия,
   fallback на реквизит `Клиент.ПроцентКомиссии`. Сумма — `ДокументыСервер.СуммаКомиссии:314-356`.
4. **Раскладка комиссии на «информационно» / «к выплате»** — `:423-457`, по
   `Бронирует.ТипОплатыСчета`.
5. **Фактически выплаченная комиссия** — `КомиссияРаспределение(ДатаОтчетаС, ДатаОтчетаПо)`
   (`ФинансовыйРезультатОтель:2495-2695`), результат подтягивается по
   `Структура("Заявка, Дата")` на `:470-486`.
6. **Оплаты.** `ТЗ_Оплаты` сопоставляется с долгами по `ДолгиГУИД` через
   `ОбщийФункционалСервер.ВСписке` (`:500-517`).
7. **Итоги.** `ИтогиДень` (обнуляется на `:258-284`) ← строка заявки-дня (`:827-859`);
   `Итоги` ← `ИтогиДень` (`:928-958`); вывод периода — `:966-993`.

### 2.3 Откуда берутся суммы (коворкинговая ветка)

1. **Счета.** `Документ.КоворкингСчета` через `Справочник.КоворкингНомера`
   (`ФинансовыйРезультатКоворкинг:98-126`). Отбор: `ПометкаУдаления = ЛОЖЬ`
   **и `Проведен = ИСТИНА`** — в отличие от гостиничной ветки.
2. **Оплаты.** Табличная часть `Документ.КоворкингСчета.РаспределениеОплатКоворкинг`
   с `ЛЕВОЕ СОЕДИНЕНИЕ Документ.КоворкингСчета.ДопУслугиКоворкинг` по
   `Ссылка + ГУИДДолги = ГУИД` (`:228-234`).
3. **Разнесение аренды по дням** — `:273-300`: `СуммаЗаДень = Окр(СуммаСчета / КоличествоЕдиниц, 2)`,
   последний день добирает `ОстатокСуммаСчета`. Остаточная техника — **ошибка округления
   не накапливается**.
4. **Разнесение оплат по дням аренды** — `:302-354` (и `_Расширенный:471-521`). Здесь и был
   пункт C4.
5. **Себестоимость** в коворкинговой ветке отсутствует как понятие.

### 2.4 Себестоимость

Сплошной поиск `Себестоимост` по всем 10 модулям среза — **0 совпадений**. Затраты
представлены только в `ФинансовыйРезультатОтель` в блоке
`СформироватьОтчетРаспределениеОплатНаСервере` (`:2045-2421`): «затратами» там называются
**начисления заявки/услуги/коворкинга**, против которых распределён конкретный документ
оплаты (`:2244-2394`, поля `СуммаЗатрат`, `ТипЗатрат`, `ДокументЗатраты`). Это сверка
«оплата ↔ на что она легла», а не себестоимость. Настоящая себестоимость
(партии, `МинибарПартии`, `ОстаткиПродукции`) в финансовый результат **не попадает вообще**.

## 3. Какая версия контура живая

Критерий — достижимость, проверенная сплошным поиском, а не суффикс имени.

| Обработка | Кнопка в `Интерфейс` | Ночная выгрузка | Вердикт |
|-----------|---------------------|-----------------|---------|

| `ФинансовыйРезультатОтель` | да, `visible=true` | нет | **живая** (только интерактивно) |
| `ФинансовыйРезультат_Расширенный` | да, `visible=true` | да → `_ФинРезультат_Расширенный.xls` | **живая** |
| `ФинансовыйРезультатКоворкинг` | да, `visible=true` | да → `_ФинРезультатКоворкинг.xls` | **живая** |
| `ФинансовыйРезультатКоворкинг_Расширенный` | да, `visible=true` | да → `_ФинРезультатКоворкинг_Расширенный.xls` | **живая** |

**Мёртвых версий в контуре нет.** Ни одна кнопка не скрывается кодом: сплошной поиск
`ФинансовыйРезультат` по `Интерфейс/Forms/Форма/Module.bsl` даёт только пять обработчиков
команд `:2507-2668`, ни одного присваивания `.Видимость`.

Это и есть главный системный факт среза: **пять параллельных денежных отчётов сосуществуют,
все пять доступны, четыре из пяти ежедневно уезжают на FTP, и их логика разошлась** —
см. `24-C13` и `24-H31`.

Направление наследования установлено диффом:
`ФинансовыйРезультат` → `ФинансовыйРезультатОтель` — 720 строк расхождения, `Отель` —
надмножество (добавлены `СуммаВ2В`, `СуммаНомераБезЗавтрака`, `СуммаОплатыПроживание`,
разделение услуг на `Долг`/`Оплата`, константа `СуммаЗаЗавтрак`).
`ФинансовыйРезультат_Расширенный` — отдельная ветка с 21 функцией против 6 у базовой.

#### `24-H30` — Отчёт «Оплаты» коворкинга: одна и та же сумма аренды гасится каждой оплатой заново, хвост оплаты теряется

**Уровень:** HIGH
**Файлы:**
- `src/DataProcessors/ФинансовыйРезультатКоворкинг/ManagerModule.bsl:1052-1078`,
  внутри `Функция СформироватьОтчетОплатыНаСервере` (`:760`–`:1220`)
- `src/DataProcessors/ФинансовыйРезультатКоворкинг_Расширенный/ManagerModule.bsl:2762-2788`,

Обе границы проверены по `^Функция`/`^КонецФункции`.
**Метка:** 🟢 ПОДТВЕРЖДЕНО

**Что не так.** Это второй алгоритм разнесения оплат по дням аренды — тот, который правка
по C4 не затронула. Здесь циклы вложены наоборот (внешний — оплата, внутренний — дни
аренды), поэтому одна оплата дважды не считается. Но остаток **аренды** не хранится
между оплатами:

```
1059  Для Каждого СтрокаОплата Из ОплатыСчет Цикл
1060      ОстатокСуммаОплаты = СтрокаОплата.СуммаОплаты;
1062      Для Каждого СтрокаАренда Из АрендаСчет Цикл
1063          НоваяСтрока = ТЗ_ВсеОплатыАренда.Добавить();
...
1068          Если ОстатокСуммаОплаты > СтрокаАренда.СуммаАренды Тогда
1069              НоваяСтрока.СуммаОплаты = СтрокаАренда.СуммаАренды;
1070              ОстатокСуммаОплаты = ОстатокСуммаОплаты - СтрокаАренда.СуммаАренды;
1071          Иначе
1072              НоваяСтрока.СуммаОплаты = ОстатокСуммаОплаты;
1074              Прервать;
1075          КонецЕсли;
1076      КонецЦикла;
1077  КонецЦикла;
```

`СтрокаАренда.СуммаАренды` не уменьшается — каждая следующая оплата начинает гасить те же
дни с начала. Плюс: если оплата исчерпала все дни аренды и осталась с остатком, внутренний
цикл просто заканчивается — **остаток нигде не выводится**.

**Сценарий A (перекос по дням).** Счёт коворкинга: 4 дня × 500 ₽ = 2 000 ₽. Две оплаты
по 1 000 ₽.
- Оплата №1: день 1 → 500 ₽, день 2 → 500 ₽ (`Прервать`).
- Оплата №2: **снова** день 1 → 500 ₽, день 2 → 500 ₽.
- Отчёт «Оплаты»: 01-е — 1 000 ₽, 02-е — 1 000 ₽, 03-е и 04-е — **0 ₽**.
  Фактически аренда 3-го и 4-го дней тоже оплачена. Итог за период сходится (2 000 ₽),
  распределение по дням неверно — а отчёт строится именно по дням.

**Сценарий B (потеря денег).** Счёт: 3 дня × 100 ₽ = 300 ₽. Одна оплата 500 ₽ (предоплата
с запасом).
- День 1 → 100 ₽ (остаток 400), день 2 → 100 ₽ (остаток 300), день 3 → 100 ₽ (остаток 200).
- Цикл заканчивается. **200 ₽ не выводятся ни одной строкой.**
- Итог `СуммаОплаты` по `ТЗ_ВсеОплатыАренда` (`:1080-1081`, `_Расширенный:2790-2791`) —
  **300 ₽ вместо 500 ₽**. Отчёт «Оплаты» занижает поступления на всю переплату.

**Почему это не тот же дефект, что C4.** C4 (`СформироватьОплатыДни`) завышал: одна оплата
разносилась на каждый день полностью. Здесь наоборот — занижение и перекос. Правка C4
(`Если ОстатокСуммаОплаты = 0 Тогда Продолжить` + сохранение остатка в `СтрокаОплата`) в этот
блок не внесена ни в одной из двух обработок: маркеров `// + Аудит` в диапазоне `1052-1078` /
`2762-2788` нет.

  `..._Расширенный:442-469`. `СуммаЗаДень = Окр(СуммаСчета / КоличествоЕдиниц, 2)` (`:281`/`:450`),
  но последний день получает не расчётную сумму, а **остаток**:
  `Если Дата_П = ДатаПо Тогда НоваяСтрока.СуммаАренды = ОстатокСуммаСчета` (`:291-292`/`:460-461`).
  Классическая остаточная техника — сумма дней всегда равна сумме счёта до копейки,
  ошибка округления не накапливается. Дефекта округления нет — но у этого же цикла нет
  верхней границы по периоду отчёта, см. `24-M42`.
- **Гостиница, проживание по дням** — деления нет вовсе: строка `Проживание` документа
  уже хранится по дням (`ЗаявкаНаБронированиеПроживание.ДеньПроживания`), отчёт берёт
  готовую сумму дня (`ФинансовыйРезультатОтель:385, 645`). Дефекта нет.

Разбиение оплаты по карте/наличным (`..._Расширенный:645-648`,
`Окр(СуммаОплаты × СуммаДокументаОплатыКарта / СуммаДокументаОплаты, 2)`) округляет
каждое слагаемое независимо, поэтому `СуммаОплаты_кк + СуммаОплаты_нал` может разойтись
с `СуммаОплаты` на копейки при большом числе строк. Это косметика колонок расшифровки,
в итог `СуммаОплаты` не входит — до уровня находки не дотягивает.

### 6.3 Источник процента комиссии

Все 14 точек расчёта комиссии в трёх гостиничных обработках
(`ФинансовыйРезультат:398, 2459, 2514, 2565`;
`ФинансовыйРезультатОтель:412, 2564, 2619, 2670`;
`ФинансовыйРезультат_Расширенный:557, 3387, 4399, 4542, 4597, 4648`) идут через
`ДокументыСервер.ПроцентКомиссииКлиента` → `ДокументыСервер.ПроцентКомиссии:819-841`,
то есть через периодическую табличную часть `Справочник.Клиенты.ПроцентыКомиссии`.
Прямых обращений к реквизиту `Клиент.ПроцентКомиссии` в срезе нет — они закомментированы
(`ФинансовыйРезультатОтель:2563, 2618, 2669` и аналоги). Обращений к
`ПроцентАгент_OLD` в срезе нет ни одного. Единственный источник истины по проценту
комиссии в контуре ФинРезультата — корректный.

**Разночтение, оставленное как наблюдение (не находка):** дата, на которую берётся процент,
в двух соседних функциях разная. `ФинансовыйРезультатОтель:2619` передаёт

в `Функция КомиссияРаспределение` (`:2495`–`:2695`). Если поле `РезервС` строки запроса
всегда заполняется из `Заявка.РезервС`, разницы нет; доказать это чтением одного модуля
нельзя — запрос выбирает `РезервС` из разных источников в двух подзапросах.
