## EC-01. Списание при нулевом остатке партий («торговля в минус»)

**Контекст.** Горничные регистрируют фактическое потребление минибара постфактум, нередко раньше, чем оформлен приход товара. На момент проведения расхода доступных FIFO-партий по номенклатуре может не быть вовсе или не хватать на всё количество строки (`РасходОстаток > 0` после прохода по всем партиям).

**Текущее поведение легаси.** FIFO-цикл списывает с партий от старейшей `Мин(РасходОстаток, КоличествоОстаток)`. Если после исчерпания всех партий `РасходОстаток > 0`, добавляется движение `МинибарПартии` Расход **БЕЗ `ДокументПрихода`** (пустая партия) на остаток. Это уводит остаток партий в минус по «безпартионной» позиции, а себестоимость этого количества = 0 (`ЦенаПриход` пустая). Расход НЕ блокируется, `Отказ` не выставляется. 🔴

**Ожидаемое.** Учёт следует за фактом потребления — продажа не теряется при запоздалом приходе. НО: нулевая себестоимость недостающего количества занижает себестоимость расхода и завышает прибыль в отчёте «Прибыль»; остаток партий становится отрицательным. Корректность учёта не гарантирована — нужна явная бизнес-политика (оставлять 0 / дооценивать по средней / блокировать). 🔴

**Легаси.** `ПСН_РЕНОМЕ__АУДИТ/src/Documents/МинибарРасход/ObjectModule.bsl:16-62` (ветка без партии 54-61); flowchart `Минибар-РасходПроведение.md`; ADR 0012; `questions.md` Q-01.

**Доверие:** 🟢 (механика подтверждена) / 🔴 (корректность/политика — открытый вопрос).

## EC-02. Пересчёт цепочки месяцев при вводе данных задним числом

**Контекст.** Себестоимость `МинибарСебестоимость` ведётся помесячно (period=Месяц), результат месяца переносится на начало следующего (`Период = КонецМесяца + 1`). Приход или расход могут регистрироваться «задним числом» (по фактической `ДатаДокументаПрихода`/`ДатаРасхода`), создавая движение в уже рассчитанном или пропущенном месяце — возникает разрыв в помесячной непрерывности срезов.

**Текущее поведение легаси.** `ДатыОбновления()` ищет **первый разрыв** в помесячной цепочке `МинибарСебестоимость` и формирует диапазон пересчёта от него до даты расчёта; `БудущиеДаты()` добавляет месяцы с движениями после даты расчёта. Затем для каждого месяца диапазона `ОбновитьСебестоимостьМиниБараНаСервере` пересчитывает срез: начало = срез последних на начало месяца, средневзвешенная цена, перенос на `КонецМесяца+1`. Команда предварительно спрашивает подтверждение диапазона (`ВопросАсинх`). 🟢

**Ожидаемое.** После ввода движения задним числом весь «хвост» цепочки от затронутого месяца пересчитывается без пропусков; переходящие остатки согласованы между смежными месяцами; пользователь видит и подтверждает охватываемый диапазон. 🟢

**Легаси.** `ПСН_РЕНОМЕ__АУДИТ/src/DataProcessors/Минибар/Forms/Форма/Module.bsl` — `ДатыОбновления` (839-888), `БудущиеДаты` (891-966), `ОбновитьСебестоимостьМиниБараНаСервере` (968-1081); flowchart `Минибар-Себестоимость.md`.

**Доверие:** 🟢.

## EC-03. Идемпотентный повторный сбор расхода из уборок

**Контекст.** Документ `МинибарРасход` за месяц формируется автоматически из ТЧ `Минибар` уборок горничных. Сбор может запускаться многократно за один и тот же месяц (после дозагрузки новых фактов, после ручной правки уборок, при повторном открытии обработки).

**Текущее поведение легаси.** `СоздатьДокументРасходНаСервере` ищет существующий `МинибарРасход` с `Программно=Истина` и `ДатаДокументаРасхода=КонецМесяца`. Если найден — ТЧ `Расход` очищается и перезаполняется (комментарий «Обновлён программно»); если нет — создаётся новый («Создан программно»). Документ записывается с проведением. Таким образом за месяц всегда ровно один программный документ расхода, а не накопление дублей. Если за месяц нет фактов потребления — выводится сообщение, документ не создаётся/не изменяется. 🟢

**Ожидаемое.** Повторный сбор за месяц перезаписывает тот же документ (без дублей и без задвоения движений в регистрах); ручные документы расхода (`Программно=Ложь`) не затрагиваются; пустой месяц не создаёт пустого документа. 🟢

**Легаси.** `ПСН_РЕНОМЕ__АУДИТ/src/DataProcessors/Минибар/Forms/Форма/Module.bsl:17-94`; flowchart `Минибар-СборРасходаИзУборок.md`.

**Доверие:** 🟢.

## EC-04. Партия без `ДокументПрихода` в остатках FIFO

**Контекст.** Как следствие EC-01 («торговля в минус»), в `МинибарПартии` могут существовать отрицательные движения с пустым `ДокументПрихода`. При последующем приходе/расходе той же номенклатуры функция `ПартииОстатки` вернёт набор партий, среди которых есть «безпартионная» (пустая) позиция.

**Текущее поведение легаси.** `ПартииОстатки` упорядочивает партии по `ДокументПрихода.ДатаДокументаПрихода`. У пустой партии `ДокументПрихода` не заполнен → его `ДатаДокументаПрихода` неопределена/пустая, что влияет на её позицию в FIFO-порядке (вероятно, всплывает в начало как «самая ранняя»). Дальнейшее списание/коррекция работают по тем же правилам, но себестоимость пустой партии = 0. Явной обработки «схлопывания» отрицательной позиции при поступлении реального прихода в коде не обнаружено. 🟡

**Ожидаемое.** Поступление реального прихода должно гасить ранее образовавшийся отрицательный «безпартионный» остаток (или хотя бы не искажать FIFO-порядок реальных партий). Текущее поведение по гашению/упорядочиванию пустой партии требует подтверждения — потенциальный источник искажения себестоимости. 🔴

**Легаси.** `ПСН_РЕНОМЕ__АУДИТ/src/Documents/МинибарРасход/ObjectModule.bsl:54-98` (создание пустой партии и `ПартииОстатки`); `data-dictionary.md` → `МинибарПартии`.

**Доверие:** 🟡 (механика выведена) / 🔴 (гашение отрицательной позиции — пробел).

## EC-05. Деление на ноль при расчёте средневзвешенной цены

**Контекст.** Средневзвешенная цена списания считается как `(СуммаНачало + СуммаПриход) / (КоличествоНачало + КоличествоПриход)`. Для новой номенклатуры или после полного обнуления остатков знаменатель `(КоличествоНачало + КоличествоПриход)` может быть равен 0, хотя движение расхода в месяце есть (та же торговля в минус).

**Текущее поведение легаси.** При нулевом знаменателе применяется fallback: `СуммаНачало/КоличествоНачало` (если возможно) либо 0 — исключения деления на ноль не происходит. `ЦенаСписания = 0` означает нулевую себестоимость расхода за этот месяц. 🟢

**Ожидаемое.** Расчёт не падает с ошибкой деления на ноль; нулевая цена при отсутствии остатка/прихода — осознанное (но искажающее себестоимость) поведение, согласованное с EC-01. 🟡

**Легаси.** `ПСН_РЕНОМЕ__АУДИТ/src/DataProcessors/Минибар/Forms/Форма/Module.bsl:968-1081`; flowchart `Минибар-Себестоимость.md` (узел «fallback при делении на 0»).

**Доверие:** 🟢 (защита от деления на ноль) / 🟡 (последствия нулевой цены).

## EC-06. (Связанный контур) Инвентаризация бара при нулевом учётном остатке

**Контекст.** Документ `ИнвентарицацияБара` (контур «Бар»/`Товары`, НЕ минибар) заполняет ТЧ остатками `ОстаткиПродукции` и себестоимостью из `СебестоимостьТоваров.СрезПоследних`. Себестоимость за единицу = `Себестоимость / Остаток`; при нулевом остатке деление дало бы ошибку.

**Текущее поведение легаси.** Формула защищена тернарником: `Себестоимость / ?(Остаток=0, 1, Остаток)` — при нулевом остатке делитель = 1. Нулевые строки расхождения при проведении пропускаются (`Расхождение = 0` → нет движения). Заполнение ТЧ привязано к группе товаров через магическую строку `Справочники.Товары.НайтиПоНаименованию("Бар")`. 🟢/🔴

**Ожидаемое.** Заполнение не падает при нулевом учётном остатке; проведение корректирует `ОстаткиПродукции` только по ненулевым расхождениям (Факт − Учёт). Магическая строка имени группы — риск при переименовании. Контур независим от регистров минибара. 🔴

**Легаси.** `ПСН_РЕНОМЕ__АУДИТ/src/Documents/ИнвентарицацияБара/Forms/ФормаДокумента/Module.bsl:130-186` (магическая строка :154); `ПСН_РЕНОМЕ__АУДИТ/src/Documents/ИнвентарицацияБара/ObjectModule.bsl:2-30`; flowchart `Минибар-ИнвентаризацияБара.md`.

**Доверие:** 🟢 (защита деления, пропуск нулей) / 🔴 (магическая строка, разрыв контуров).
