# B2 — Эквайринг PayKeeper и HTTP-контур обмена с сайтом

> **Кусок:** B2 группы «Слепые зоны» аудита 2026-08-24.
> **Предмет:** платёжный шлюз PayKeeper целиком (кроме уже разобранного распределения оплат),
> обмен с сайтом бронирования (`ОбменСайт`, `ЗаявкаСайт`), HTTP-транспорты (`ОбменHTTP`,
> `HTTP_Модуль`) и внешний доступ к БД сайта (`ОбщийМодульСлужебныеСервер`).
> **Правило чтения:** каждый диапазон `X–Y` открыт и проверен по `^Функция`/`^Процедура` и
> `^КонецФункции`/`^КонецПроцедуры`. Отрицательные утверждения доказаны сплошным поиском по
> `ПСН_РЕНОМЕ__АУДИТ/src` (656 модулей).

содержит обработчиков HTTP-сервиса. Факт оплаты устанавливается **только опросом** API PayKeeper.

`PayKeeper.ВозвратДенег :295–354` → `POST /change/payment/reverse/`. Функция `Экспорт`

#### `24-C04` — Оплаченные платежи не попадают в учёт автоматически: импорт запущен только кнопкой в обработке `PayKeeper_ТЕСТ`

**Уровень:** CRITICAL — потеря/непопадание данных о деньгах в учёт.
**Метка:** 🟢 ПОДТВЕРЖДЕНО

**Координаты**

* `ПСН_РЕНОМЕ__АУДИТ/src/CommonModules/PayKeeperСервер/Module.bsl:56–91` — `Функция ПолучитьИОбработатьСписокПлатежей() Экспорт` (56) … `КонецФункции` (91). Единственная процедура, которая переносит факт оплаты из PayKeeper в базу: опрашивает шлюз, пишет `РегистрСведений.PayKeeperПлатежи` и вызывает `СвязатьPayKeeperПлатежи`, создающий `Документ.ВыпискаБанка`.
* `ПСН_РЕНОМЕ__АУДИТ/src/DataProcessors/PayKeeper_ТЕСТ/Forms/Форма/Module.bsl:90–97` — `&НаКлиенте Процедура ПолучитьСписокПлатежей(Команда)` (91) … `КонецПроцедуры` (97). Её единственный вызов.

**Доказательство отрицательного утверждения (сплошной поиск по `ПСН_РЕНОМЕ__АУДИТ/src`)**

```
ПолучитьИОбработатьСписокПлатежей → 2 вхождения:
  CommonModules/PayKeeperСервер/Module.bsl:56              (объявление)
  DataProcessors/PayKeeper_ТЕСТ/Forms/Форма/Module.bsl:92  (единственный вызов)
СвязатьPayKeeperПлатежи → 5 вхождений: :94 (объявление), :87 (из ПолучитьИОбработать…),
  PayKeeper_ТЕСТ/Форма:137 (кнопка «Связать оплаты-долги»),
  ЗаявкаНаБронирование/ФормаДокумента:7399   — ЗАКОММЕНТИРОВАН
  ГрупповыеСчета/ФормаДокумента:1857         — ЗАКОММЕНТИРОВАН
  КоворкингСчета/ФормаДокумента:1033         — ЗАКОММЕНТИРОВАН
```

В `src/ScheduledJobs/` шесть заданий, все с `methodName` вида
`CommonModule.ЛогированиеОперацийБПО.*` и `CommonModule.РассылкаЭлектронныхЧеков.*` —
ни одно не ссылается на `PayKeeper`. Регламентного задания опроса шлюза **нет**.

Обработка `PayKeeper_ТЕСТ` не входит ни в одну подсистему (`grep` по `src/Subsystems/` даёт
0 вхождений `PayKeeper_ТЕСТ`; в `Subsystems/ОсновнаяСистема/ОсновнаяСистема.mdo` из среза
присутствуют только `InformationRegister.PayKeeperПлатежи:68` и `Constant.PayKeeperВыводНаЭкран:82`).
То есть попасть в неё можно лишь через «Все функции».

**Сценарий воспроизведения**

1. Администратор отправляет гостю ссылку/QR на оплату счёта `Заявка/Счет: 000000123/1`.
2. Гость оплачивает. PayKeeper фиксирует платёж со статусом `success`.
3. В 1С **ничего не происходит**: `РегистрСведений.PayKeeperПлатежи` содержит запись, созданную
   при отправке (`PayKeeperСервер:942–949`) со `Статус = ""` и пустой `ДатаОплаты`;
   `Документ.ВыпискаБанка` не создан; долг по счёту не закрыт.
4. Кнопка «Проверить оплату PayKeepr» на форме заявки
   (`Documents/ЗаявкаНаБронирование/Forms/ФормаДокумента/Module.bsl:7352–7406`) показывает
   «Успешная оплата счета… на сумму…», но код регистрации в ней закомментирован (строки 7384–7399),
   поэтому в учёт факт оплаты она **не заносит**.
5. Пока никто вручную не откроет через «Все функции» обработку `PayKeeper_ТЕСТ` и не нажмёт
   «Получить список платежей», гость числится должником: счёт открыт, при выезде с него
   потребуют оплату повторно.

**Дополнительное окно потери.** `PayKeeperКлиентСервер.СписокПлатежейPayKeeper:102`
берёт `ДатаНач = НачалоМесяца(ТекущаяДата() - 15 суток)` и `СтрокМакс = 500` (`:105`).
Если ручной прогон не делали дольше ~45 дней или платежей за окно больше 500, часть оплат
не попадёт в выборку **никогда** — пагинации нет, `НачСтрока` жёстко 0 (`:104`).

#### `24-C05` — QR-код платежа пишется в файл с фиксированным именем: при двух одновременных отправках гость получает чужой QR

Разобрана и признана корректной — см. §4.2, строка 1. Отдельно проверено, что
`ОбновитьPayKeeperПлатежи:2–54` при повторном вызове по тому же `ИД_Платежа` сохраняет
исходный `ГУИД` (`:14`, `:26`) и исходную `ДатаСоздания` (`:38–42`), то есть не «перевыдаёт»
ключ дедупликации. Единственная слабость — `:45–49`: если шлюз перестал отдавать
`success_datetime`, `ДатаОплаты` восстанавливается из прежнего значения, а не обнуляется;
это защитное, а не дефектное поведение.

### 5.4 Проверка суффиксной «мёртвости» — опровергнута ещё раз

* `CommonForms/PayKeeperРаспределение_Тест` (4 911 строк) — **живой** рабочий интерфейс:
  сверка эквайринговых выписок, ручное распределение оплат по счетам, удаление связей.
  Открывается из `DataProcessors/PayKeeper_ТЕСТ/Forms/Форма/Module.bsl:101`.
* `DataProcessors/PayKeeper_ТЕСТ` — **живой и критически необходимый**: это единственная
  точка запуска импорта платежей (`24-C04`).
* `Documents/ЗаявкаСайт` — живой документ, есть форма списка с кнопкой загрузки и форма
  документа с порождением `ЗаявкаНаБронирование`; ссылается `Catalogs/Клиенты/Forms/ФормаЭлемента`,
  `Documents/ЗаявкаНаБронирование/Forms/ФормаДокумента`, `DataProcessors/Интерфейс/Forms/Форма`.
* Напротив, `ОбменHTTP` и SQL-функции `ОбщийМодульСлужебныеСервер` — мертвы, и **ни у одного
  из них нет «мёртвого» суффикса**. Критерий по имени опровергнут в обе стороны.

### 5.5 Что смотрел и дефекта не нашёл

* **TLS.** `Новый ЗащищенноеСоединениеOpenSSL` (`PayKeeper:713, 747`; `ОбменСайт:560`) без
  аргументов означает проверку сертификата сервера по штатному списку УЦ платформы —
  отключения верификации в срезе нет.
* **SQL-инъекция в запросах 1С.** Все `Новый Запрос` в срезе используют
  `Запрос.УстановитьПараметр` (проверено в `PayKeeperСервер:116,151,152,187,218,258`,
  `ЗаявкаСайт/ФормаСписка:83,156`, `ОтправкаPayKeeperФорма:50`,
  `ЗаявкаСайт/ФормаДокумента:59`). Конкатенации значений в текст запроса нет ни одной.
* **Дедупликация записей регистра `PayKeeperПлатежи`.** Ключ — `ИД_Платежа`
  (`ОбновитьPayKeeperПлатежи:5`), набор перечитывается перед записью (`:7`), очищается (`:19`)
  и пересоздаётся — дублей в регистре появиться не может.
* **Разбор `orderid`.** Проверены длины префиксов в
  `PayKeeperКлиентСервер:124–129` («Заявка/Счет: », 13), `:131–136` («Коворкинг счет: », 16),
  `:138–143` («Групповой счет: », 16) — все совпадают с фактической длиной строк.
  Обратный разбор в `СвязатьPayKeeperПлатежи:126, 163, 198` использует те же значения.
* **Дополнение номера нулями.** `СтрСоединить(Новый Массив(К + 1), "0")`
  (`PayKeeperСервер:145, 183, 214`) даёт ровно `К` нулей — арифметика верна.
  Отрицательный `К` возможен только при номере длиннее `ДлинаНомера`, что платформа не допускает.
* **`Позиции` против `Позиция`** в `PayKeeperСервер:717`
  (`Для Каждого Строка Из Позиции Цикл`) — проверено побайтово: используется массив `Позиции`,
  объявленный на `:562`, а не структура `Позиция`. Подозрение на обход структуры вместо массива
  **не подтвердилось**.
* **Расчёт `СуммаПлатежа`** (`PayKeeperСервер:716–719`) как сумма `sum` позиций совпадает
  с суммой, отправленной в шлюз: `ПолучитьQRКод:129–133` при заданных позициях присваивает
  `СуммаПлатежа = _Сумма`, а вызов на `:681–682` передаёт `Неопределено` пятым параметром,
  то есть сумма формируется исключительно из позиций. Расхождения нет.
* **Ставка НДС.** `СтавкаНДСPayKeeper:953–967` покрывает `НДС0/vat0` и остальные значения
  перечисления; допустимые значения `tax` проверяются в `ПолучитьQRКод:121–126`
  списком `none|vat0|vat5|vat20|vat22` — согласовано.
* **Возврат средств.** `ВозвратДенег:295–354` содержит корректные проверки статуса
  (`:306–313`), суммы (`:315–319`), уже возвращённой части (`:321–334`) и правильно
  вычисляет флаг `partial` (`:336`, `:341`). Логика возврата ошибок не содержит —
  проблема лишь в отсутствии контроля прав на вызов (`24-H11`).
