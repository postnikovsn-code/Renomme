# ADR 0001 — Двойной контур учёта долгов: ТЧ заявки vs регистры накопления

- **Статус:** Принято (исторически, реконструировано) · 🟡 ВЫВЕДЕНО (Git-история недоступна)
- **Дата:** неизвестна (до текущей версии 3.2.7.38)
- **Модуль:** Финансы и касса / Бронирование

## Контекст

В системе одновременно присутствуют два механизма учёта задолженности гостей:

1. **Регистры накопления** `Долги`, `Деньги`, `Взаиморасчеты` (классический «учётный» контур 1С).
2. **Табличные части документа** `ЗаявкаНаБронирование`: `СчетаДетальноДолги`, `СчетаДетальноСтроки`, `РаспределениеОплатДолги` (внутридокументный контур долгов с FIFO-гашением).

Свидетельства решения (вместо git-истории):
- В `КассовыйДокумент/ВыпискаБанка/ПрочиеОплаты ObjectModule.bsl` после единственного движения `Взаиморасчеты` стоит **безусловный `Возврат`**; весь последующий ~90-строчный блок построения движений `Деньги`/`Долги` и начисления бонусов — мёртвый код (FN-01). 🟢
- Регистр `Деньги` фактически НЕ наполняется; регистр `Долги` пишется только заявкой (Приход) и устаревшим `ГашениеДолгов_Старая` (суффикс `_Старая`, Расход) → его баланс недостоверен (FN-02). 🟢
- Реальное гашение долга идёт через `ЗаявкаОбщееКлиентСервер.РаспределитьОплатаСтрокаДолгСтрока` по ТЧ заявки (FN-04). 🟢

Вывод: контур долгов был перенесён из регистров в табличные части документа, но старый регистровый контур не удалён (отключён `Возврат`-ом и суффиксом `_Старая`).

## Решение

Вести долги и распределение оплат во внутридокументных ТЧ `ЗаявкаНаБронирование` (нормализация «много счетов на одну бронь» через `СчетГУИД`/`ДолгиГУИД`), оставив из регистрового контура фактически живым только `Взаиморасчеты` (оборот по контрагенту).

## Рассмотренные альтернативы

- **Чистый регистровый учёт** (только `Долги`/`Деньги`/`Взаиморасчеты`). Отклонено фактически: сложно моделировать множественные счета и детальное распределение оплат внутри одной брони; регистры дают баланс, но не структуру «счёт → строки долга → распределение».
- **Полный переход на ТЧ с удалением регистров.** Не завершено: регистры и `ГашениеДолгов_Старая` оставлены в конфигурации (риск регресса, опора отчётов на старые движения).
- **Гибрид с синхронным наполнением обоих контуров.** Отклонено: дублирование и риск рассинхронизации; вместо этого старый контур просто «обрезан» `Возврат`-ом.

## Последствия

- ➕ Гибкая модель множественных счетов и детального FIFO-распределения оплат.
- ➖ Регистры `Деньги`/`Долги` недостоверны → отчёты на их основе требуют осторожности; «единого источника правды» для бухгалтерских движений нет.
- ➖ Мёртвый код проведения (~90 строк × 3 документа) усложняет сопровождение и скрывает захардкоженное подключение к бонусной базе (ADR 0005).
- ➖ 🔴 Невозможно получить балансовый отчёт по долгам стандартными средствами регистра — только запросом по ТЧ документов.
- ⚠ При миграции на новую систему контур долгов нужно брать из ТЧ заявки, а не из регистров.
