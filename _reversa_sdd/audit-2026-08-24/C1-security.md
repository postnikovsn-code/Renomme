# C1 — Сквозная линза «безопасность»

> **Кусок:** C1 из плана `README.md` (группа C — сквозные линзы).
> **Предмет:** секреты в исходниках, права и роли, персональные данные.
> **Объект:** `ПСН_РЕНОМЕ__АУДИТ/src` — конфигурация «ОТЕЛЬ» 3.2.7.38 (1C:EDT).
> **Метод:** сплошной поиск по всем `.bsl`, `.mdo`, `.form`, `.rights` в `src/`;
> каждая координата открыта и проверена по обеим границам.
> **Режим:** только чтение. Секреты приведены **как есть**, без маскирования —
> это условие задачи: маскированный реестр не позволяет владельцу опознать,
> какой именно аккаунт нужно ротировать.

Два вывода, определяющих характер всего куска:

1. **Секреты не «просочились» — они являются штатным способом конфигурирования.**
   Ни одного обращения к `ХранилищеОбщихНастроек`, `БезопасноеХранилищеДанных`,
   константе с паролем или внешнему конфигу для аутентификационных данных
   не найдено (сплошной поиск, §1.9). Пароль, вписанный в текст модуля, —
   единственный применяемый механизм. Следовательно, точечная зачистка
   не решает задачу: нужен механизм хранения, которого в конфигурации нет.

2. **Роли не разграничивают ничего в гостиничном домене.**
   Все семь `Rights.rights` упоминают **только** объекты библиотеки подключаемого

   `Report.*` гостиничной части конфигурации нет ни в одной роли (§3).
   Разграничение доступа целиком вынесено в код — в сравнения строк и флаг
   `Админ` (§3.4).

## 1. Реестр секретов

Обозначения колонки «путь»:
**ЖИВОЙ** — код исполняется в достижимом сценарии;
**МЁРТВЫЙ** — объект/ветка недостижимы;
**КОММЕНТАРИЙ** — строка закомментирована, но секрет читается из исходника.

Важно: для колонки «что даёт злоупотребление» «КОММЕНТАРИЙ» **не смягчает** оценку —
исходник конфигурации доступен любому, кто может открыть её в конфигураторе или
получить `.cf`/выгрузку в файлы, а значение пароля одинаково пригодно к употреблению
независимо от того, вызывается ли строка.

### 1.2 SMS-шлюз Bytehand — ключ в URL, открытый HTTP

`CommonModules/СлужебныеСервер/Module.bsl:65-69` (функция `ОтправитьBytehand`, `:54-102`)

```
Адрес = "http://bytehand.com:3800/send?id=27944"
+ "&key=0FE91DD358FF29D2"
+ "&to=" + НомерТелефона
+ "&from=" + НаименованиеСМС
+ "&text=" + ПодготовитьТекст(Текст);
```

Путь ЖИВОЙ (экспортная функция, гейт `ЭтоТестоваяПрограмма` на `:56-57` — только
на тестовой базе). Секрет: `id=27944`, `key=0FE91DD358FF29D2`.

**Три дефекта в пяти строках:**
1. Схема `http://`, а не `https://` — ключ и **номер телефона гостя** идут открытым текстом.
2. Ключ в query-string, а не в теле/заголовке — попадает в логи прокси и шлюза.
3. Транспорт — COM `WinHttp.WinHttpRequest.5.1` (`:75`) с `Option(4, 13056)`.
   `13056 = 0x3300` — это комбинация флагов игнорирования ошибок сертификата
   (`SslErrorIgnoreFlags`: неизвестный ЦС + неверное имя + неверная дата + неверное
   использование). То есть проверка TLS отключена **на случай, если адрес переведут на https**.

**Что даёт злоупотребление.** Рассылка SMS от имени отеля за его счёт;
перехват номеров телефонов гостей на любом узле между сервером 1С и bytehand.com.

### 1.7 GreenAPI — `idInstance` + `apiToken` (уточнено)

**Уточнение к унаследованной формулировке.** Утверждение «GreenAPI в 18 строках»
подтверждено численно: сплошной поиск литерала
`84a9441987a9415fb7f03365ffdea87b67027916c3e54405bb` и `3100530778` даёт ровно
**18 вхождений в 2 файлах** — `CommonModules/MAXСервер/Module.bsl` (10)
и `CommonModules/TelegramСервер/Module.bsl` (8). В `GREEN_WhatsApp` литерала нет.

Но механизм иной, чем следует из формулировки: **все 18 вхождений — хвостовые
комментарии**, а живой код читает значения из констант.

`CommonModules/TelegramСервер/Module.bsl:2-11` (`ПараметрыGREEN`, Экспорт):

```
idInstance = Константы.GREENIdInstanceTelegram.Получить(); // "3100530778";
ApiToken   = Константы.GREENApiToken_Telegram.Получить();  // "84a9441987a9415fb7f03365ffdea87b67027916c3e54405bb";
```

Строки-комментарии: `TelegramСервер` `:3,4,19,20,58,59,119,120`;
`MAXСервер` `:3,4,19,20,66,67,105,106,167,168`. Все проверены.

Практический вывод не смягчается: значение токена лежит в тексте конфигурации
и одинаково пригодно к употреблению. Дополнительно — **в комментариях Telegram и MAX
стоит один и тот же токен**, то есть либо это один инстанс на два канала,
либо один из комментариев устарел и вводит в заблуждение.

Константы, хранящие живые значения (`Constants/GREENApiToken_Telegram`,
`GREENApiToken_MAX`, `GREENApiToken_WhatsApp`, `GREENIdInstanceTelegram`,
`GREENIdInstance_MAX`, `GREENIdInstance_WhatsApp`) — обычные строковые константы
без пометки «пароль», доступные на чтение всем, кому доступна конфигурация (§3).

#### 1.7.1 Токен утекает в журнал регистрации (подтверждено)

`DataProcessors/GREEN_Telegram/ObjectModule.bsl:1761-1763`:

```
Функция URLМетодаСервиса(Инстанс, Токен, Метод)
	Возврат СтрШаблон("waInstance%1/%2/%3", Инстанс, Метод, Токен);
КонецФункции
```

Токен — **сегмент пути URL**. При любом ответе, отличном от 200, тот же модуль пишет
этот URL в журнал регистрации целиком —
`DataProcessors/GREEN_Telegram/ObjectModule.bsl:1541-1543`:

```
ЗаписьЖурналаРегистрации("GreenAPI.ОшибкаЗапроса",
	УровеньЖурналаРегистрации.Ошибка, , ,
	"Адрес: " + Адрес + Символы.ПС + ТекстОшибки);
```

Сплошной поиск подстроки `"Адрес: " + Адрес` по всей конфигурации даёт **ровно одно
вхождение** — это `GREEN_Telegram`. В `GREEN_MAX/ObjectModule.bsl:1686`,
`GreenAPI/ObjectModule.bsl:1628`, `GreenAPI/Forms/Форма/Module.bsl:518`
и `GREEN_WhatsApp/Module.bsl:286` та же `URLМетодаСервиса` есть, но в журнал URL
не пишется. То есть утечка в журнал локализована точно.

**Что даёт злоупотребление.** Любой, кто может открыть журнал регистрации
(в том числе через «Все функции» — §3.2), читает действующий `apiToken`
и получает управление аккаунтом GreenAPI: чтение всей переписки с гостями
и отправку сообщений от имени отеля.

### 2.5 `PassportBox` — сканер паспортов

Разобрано: `CommonModules/PassportBoxВызовСервера/Module.bsl` (612 строк),
`PassportBox_Настройки/Module.bsl` (37 строк),
`PassportBoxВызовСервера_Переопределяемый/Module.bsl` (26 строк),
`Catalogs/Клиенты/Forms/ФормаЭлемента/Module.bsl:2017-2100`.

**Что уходит наружу.** Ничего за пределы локальной сети. Адрес сканера берётся
из констант `PassportBoxIP`/`PassportBoxПорт` (`PassportBox_Настройки:12-18`),
обмен — HTTP GET к устройству (`PassportBoxВызовСервера:261-286`). Внешних сервисов,
облаков, отправки распознанных данных третьим лицам в модулях **нет**
(проверено сплошным просмотром всех 24 функций модуля).

**Что логируется.** Ничего. Сплошной поиск `ЗаписьЖурналаРегистрации`, `ВЛог`,
`Сообщить` с данными паспорта по трём модулям PassportBox — ноль вхождений.
Это единственный контур интеграции в конфигурации, который **не** пишет ПДн в лог.

**Транспорт.** `PassportBoxВызовСервера:263-269` — `Новый HTTPСоединение(Адрес, Порт, , , , Таймаут)`:
седьмой параметр `ЗащищенноеСоединение` не передан, значит **HTTP без TLS**.
По этому каналу идут распознанные поля паспорта и JPEG-развороты
(`ПолучитьФотографииПаспорта` `:507-536`, `ПолучитьФотографиюРегистрации` `:547-564`).
Смягчающее обстоятельство: таймаут задан явно (в отличие от `СерверККМ`, §1.9).

**Гейт.** `Catalogs/Клиенты/Forms/ФормаЭлемента/Module.bsl:22-29`:

```
Если НастройкиСервер.ЭтоРеноме() Тогда
    Видимость_П = Истина;
Иначе
	Видимость_П = Ложь;
КонецЕсли;
Элементы.ФормаСканироватьРазворотПаспорта.Видимость = Видимость_П;
Элементы.ФормаСканироватьРегистрациюПаспорта.Видимость = Видимость_П;
```

Это гейт **видимости**, а не доступа. Сами функции
`PassportBoxВызовСервера.ПолучитьРазворот23()` и `.ПолучитьРегистрацию()` объявлены
`Экспорт` в модуле с `serverCall=true` — их можно вызвать с клиента из любого
другого места, включая внешнюю обработку, вне зависимости от площадки.

**Оценка.** По качеству кода PassportBox — лучший интеграционный контур
конфигурации: документированные функции, обязательные поля проверяются
(`ПроверитьОбязательныеПоля` `:489-506`), таймаут задан, ПДн не логируются,
наружу ничего не уходит. Единственный дефект — отсутствие TLS внутри ЛВС.

### 3.3 Как читать `setForNewObjects=true` в этой конфигурации

Флаг `setForNewObjects=true` означает: право, не записанное явно, считается
**выданным**. Доказательство того, что здесь это именно так, — сама роль
`ПолныеПрава`: у неё `setForNewObjects=true` и ровно **40 записей, все со значением
`false`** (проверено подсчётом значений в файле). Роль с именем «Полные права»,
не содержащая ни одного `true`, имеет смысл только при чтении «всё разрешено,
кроме перечисленного».

Отсюда содержательный итог по трём «сильным» ролям:

| | `ПолныеПрава` | `АдминистраторСистемы` | `Администратор` |
|---|---|---|---|
| Данные (все 808 объектов) | **все права** | нет (флаг `false`, данные не выданы) | **все права** |
| `Administration` | **запрещено** (`:101-102`) | разрешено | **разрешено** |
| `DataAdministration` | не указано → разрешено | разрешено | **разрешено** |
| `UpdateDataBaseConfiguration` | **запрещено** (`:105-106`) | разрешено | **разрешено** |
| `ThickClient` | **запрещено** (`:109-110`) | разрешено | **разрешено** |
| `ExternalConnection` (COM) | **запрещено** (`:113-114`) | разрешено | **разрешено** |
| `Automation` | **запрещено** (`:117-118`) | разрешено | **разрешено** |
| `InteractiveOpenExtDataProcessors` | **запрещено** (`:149-150`) | не указано | **разрешено** |
| `InteractiveOpenExtReports` | **запрещено** (`:153-154`) | не указано | **разрешено** |
| `ConfigurationExtensionsAdministration` | **запрещено** (`:145-146`) | разрешено | **разрешено** |
| `EventLog`, `ActiveUsers`, `ExclusiveMode`, `TechnicalSpecialistMode` | не указано → разрешено | разрешено | **разрешено** |

`АдминистраторСистемы` даёт ровно 23 административных права на `Configuration.ОТЕЛЬ`
и `UpdateDataHistorySettings` на четыре объекта БПО — и **ничего** по данным
(`setForNewObjects=false`). Это корректно спроектированная роль.

`ПолныеПрава` — все данные, администрирование явно снято. Тоже осмысленно.

`Администратор` — **объединение обоих плюс всё остальное**, без единого исключения.
Пользователь с этой ролью может выгрузить конфигурацию, изменить её, подключиться
по COM, запустить произвольную внешнюю обработку и удалить любые данные.
Роль не входит в `defaultRoles`, то есть назначается вручную — но назначить её
может любой, у кого есть `Administration` (то есть носитель `АдминистраторСистемы`
или её самой).

### 3.4 Реальное разграничение — в коде, на клиенте, по флагу `Пользователи.Админ`

Поскольку правами не закрыто ничего, доступ разграничивается вручную в модулях.
Механизм — булев реквизит `Справочник.Пользователи.Админ` и три функции-обёртки
`CommonModules/НастройкиСервер/Module.bsl`:

| Функция | Строки | Критерий |
|---|---|---|
| `ЭтоАдмин()` | `:73-76` | `ПараметрыСеанса.ТекущийПользователь.Админ` |
| `ЭтоАдминистратор()` | `:78-84` | `ТекущийПользователь.Администратор` **ИЛИ** `СокрЛП(Код) = "Администратор"` |
| `ТекущийПользовательКодРавноАдминистратор()` | `:86-92` | `СокрЛП(Код) = "Администратор"` |

Сплошной поиск даёт **25 живых** мест применения и 13 закомментированных.
Все живые — управление видимостью/доступностью элементов формы, то есть
проверка выполняется **после** того, как данные уже получены, и почти всегда
в клиентском контексте.

Эталон, названный в брифе, проверен по обеим границам —
`DataProcessors/Интерфейс/Forms/Форма/Module.bsl:1944-1955`
(`:1943` — `&НаКлиенте`, `:1944` — `Процедура ФинансыКоманда(Команда)`,
`:1955` — `КонецПроцедуры`):

```
ТекПол = ОбщийФункционалСервер.ПолучитьЗначениеПараметраСеанса("ТекущийПользователь");
ТекПолАдмин = ОбщийФункционалСервер.ПолучитьЗначениеРеквизитаНаСервере(ТекПол,"Админ");
Если ТекПолАдмин тогда
	ОткрытьФорму("Обработка.Интерфейс.Форма.ФормаФинансы_Старая", …);
иначе
	ОткрытьФорму("Обработка.Интерфейс.Форма.ФормаФинансы", …);
конецесли;
```

Два независимых обхода:

1. **Обход выбором формы.** Проверка решает, *какую форму открыть*.
   `ФормаФинансы_Старая` собственной проверки не содержит, поэтому её открытие
   любым другим способом (другая команда, внешняя обработка, «Все функции»)
   даёт полный интерфейс администратора без всякой проверки.
2. **Обход изменением флага.** `Catalog.Пользователи` не закрыт ни одной ролью (§3.2),
   а реквизит `Админ` выведен на форму элемента
   (`Catalogs/Пользователи/Forms/ФормаЭлемента/Form.form:130`) и на форму списка
   (`Catalogs/Пользователи/Forms/ФормаСписка/Form.form:134`). Значит **любой
   пользователь может открыть свою карточку и поставить себе `Админ = Истина`.**
   Проверка `ЭтоАдмин()` после этого возвращает `Истина` в том же сеансе после
   переустановки параметра сеанса.

Третий вариант — `ЭтоАдминистратор()` (`:78-84`), где правом решает **строка кода
пользователя**: `СокрЛП(ТекущийПользователь.Код) = "Администратор"`. Код элемента
справочника — пользовательское поле; тот, кто может редактировать `Справочник.Пользователи`
(то есть все), может присвоить себе этот код.

### 3.5 Привилегированный режим

Сплошной поиск `УстановитьПривилегированныйРежим(` даёт **116 вхождений**
(100 `Истина`, 16 `Ложь`) в 26 файлах.

Существенный факт: **все 116 — в коде библиотеки подключаемого оборудования**
(`ЭлектронныеСертификатыНСПК`, `РассылкаЭлектронныхЧеков`, `РаспределеннаяФискализация`,
`МенеджерОборудования*`, `Оборудование*`, `КассовыеСмены`, `ОбщегоНазначенияБПО`,
`ИнтеграцияПодсистемБПО`, `ЛогированиеОперацийБПО`, менеджеры регистров фискализации,
`ПанельАдминистрированияБПО`, `Catalog.ДрайверыОборудования`,
`Catalog.ПодключаемоеОборудование`, `CommonForm.КодВидаНоменклатурнойКлассификации`).
**В гостиничном коде — ноль вхождений.**

Это не дефект библиотеки, а диагноз конфигурации: гостиничному коду привилегированный
режим не нужен, потому что у всех и так есть все права. Дисбаланс 100/16 сам по себе
дефектом не является — в 1С привилегированный режим автоматически снимается при выходе
из процедуры, в которой был установлен.

### CRITICAL

#### 24-C16 — роль `Администратор` не ограничивает ничего, включая администрирование БД

**Уровень:** CRITICAL
**Файл:** `Roles/Администратор/Rights.rights:1-6` (весь файл; `:1` — XML-декларация,
`:6` — `</Rights>`), `Roles/Администратор/Администратор.mdo:1-8`
**Метка:** 🟢 ПОДТВЕРЖДЕНО

Файл прав роли состоит из трёх флагов и не содержит ни одного элемента `<object>`:

```
<setForNewObjects>true</setForNewObjects>
<setForAttributesByDefault>true</setForAttributesByDefault>
<independentRightsOfChildObjects>true</independentRightsOfChildObjects>
```

При `setForNewObjects=true` отсутствие записи означает выданное право (доказательство —
§3.3). Следовательно, роль выдаёт **все права на все 808 объектов метаданных плюс все
права на `Configuration.ОТЕЛЬ`**, в том числе `Administration`,
`UpdateDataBaseConfiguration`, `ThickClient`, `ExternalConnection`, `Automation`,
`InteractiveOpenExtDataProcessors`, `InteractiveOpenExtReports`,
`ConfigurationExtensionsAdministration` — то есть ровно то, что роль `ПолныеПрава`
**явно запрещает** (`Roles/ПолныеПрава/Rights.rights:98-156`).

**Сценарий эксплуатации.** Сотруднику выдана роль «Администратор» — по названию
это выглядит как «администратор гостиницы». Фактически он получает право
`UpdateDataBaseConfiguration` (изменение конфигурации базы), `ThickClient` (запуск
толстого клиента), `InteractiveOpenExtDataProcessors` (запуск любой внешней обработки).
Достаточно открыть внешнюю обработку из трёх строк, чтобы прочитать все константы
GreenAPI (§1.7), выгрузить справочник `Клиенты` целиком или изменить проведённые
кассовые документы.

#### 24-C17 — разграничение доступа основано на флаге, который пользователь ставит себе сам

**Файлы:** `CommonModules/НастройкиСервер/Module.bsl:73-92`;
`DataProcessors/Интерфейс/Forms/Форма/Module.bsl:1944-1955`;
`Catalogs/Пользователи/Forms/ФормаЭлемента/Form.form:130`;

**Метка:** 🟢 ПОДТВЕРЖДЕНО
