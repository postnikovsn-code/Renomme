## 🔴 КРИТИЧНЫЕ — блокируют безопасную сборку или достоверность данных

### G-C01. Секреты в исходном коде (FTP / Telegram / COM-пароли / MS SQL / Admin-Admin)
- **Описание.** Боевые/предположительно боевые секреты захардкожены в исходниках: FTP-креды (`mnbvcxz*279`), Telegram Green API токен, COM-пароли `Pwd="123"` (минимум 5 точек), строка MS SQL `Password=bf02a805`, дефолты `Admin/Admin` Сервера ККМ, COM к базе `BONUS`.
- **Где.** `ФТПСервер/Module.bsl:199-202`; `TelegramСервер/Module.bsl:4,20,59,120`; `ОбменГорничныеСервер/Module.bsl:22`, `ОбменКартинкаСервер/Module.bsl:8,16`, `ЗагрузкаНомеров{Лайв,Реноме,Чехов}`; `ЗаявкаНаБронирование/ObjectModule.bsl:402-443`; `КассовыйДокумент/ObjectModule.bsl:140-143`; `СерверККМ/Module.bsl:8`.
- **Влияние.** Прямая утечка доступов к внешним системам и фискальному сервису; диагностики `UsingHardcodeSecretInformation`, `UsingHardcodeNetworkAddress`, `UsingHardcodePath`. Тиражирование секрета в новую систему и историю VCS.
- **Рекомендация.** Вынести все секреты/пути в защищённое хранилище (константы с правами / `ХранилищеЗначения` / параметры подключения). Ротировать пароли и токен, вычистить историю Git. НЕ воспроизводить хардкод при переподнятии. См. CR-01..CR-07, MB-01, CrossR-01.

### G-C02. Недостоверный финансовый учёт — двойной контур долгов и денег
- **Описание.** Регистр `Деньги` не наполняется (недостижим после `Возврат`); регистр `Долги` пишет приход (заявка), но расход — только устаревший `ГашениеДолгов_Старая`, тогда как реальное гашение идёт по ТЧ `СчетаДетальноДолги`. Баланс по регистрам не совпадает с ТЧ.
- **Где.** `КассовыйДокумент/ObjectModule.bsl:87,92-105`; `ВыпискаБанка`, `ПрочиеОплаты`; `ГашениеДолгов_Старая/ObjectModule.bsl:2-16`; `code-analysis.md:757,768`; ADR-0001.
- **Влияние.** Отчёты «оплаты по способам/картам» (на `Деньги`) пусты; остаток по `Долги` завышен. Перенос «как есть» удвоит контур или перенесёт неверный баланс.
- **Рекомендация.** Зафиксировать ТЧ `СчетаДетальноДолги.СуммаКЗакрытию` единственным достоверным источником долга; решить судьбу регистров `Деньги`/`Долги` (отказ/перестройка) и исторических данных. См. CR-08, CR-09, CR-10, CR-11.

### G-C03. Разрыв двух товарных контуров «Минибар» vs «Бар»
- **Описание.** Два независимых учёта товаров без синхронизации; инвентаризация работает только по контуру «Бар» (`ОстаткиПродукции`), фактические остатки самого минибара (`МинибарОстатки`/`МинибарПартии`) выровнять по факту нельзя.
- **Где.** `ИнвентарицацияБара/ObjectModule.bsl`; `AccumulationRegisters/{МинибарОстатки,ОстаткиПродукции}`; ADR-0012.
- **Влияние.** Достоверность складского учёта минибара под вопросом; нет инвентаризации минибара как такового.
- **Рекомендация.** Подтвердить с владельцем — раздельные склады или требуется синхронизация; ввести инвентаризацию минибара при необходимости. См. CR-12.

### G-C04. «Торговля в минус» в минибаре (FIFO без покрытия)
- **Описание.** При нехватке партий расход проводится без `ДокументПрихода` и с нулевой себестоимостью недостающего количества; остаток партий уходит в минус.
- **Где.** `МинибарРасход/ObjectModule.bsl:54-61`; ADR-0012.
- **Влияние.** Занижение себестоимости → завышение прибыли в отчёте «Прибыль»; типичный сценарий из-за постфактум-регистрации.
- **Рекомендация.** Решить политику себестоимости недостающего количества (0 / средневзвешенная / последняя цена / блокировка). См. CR-13.

### G-C05. Незавершённые миграции `_NEW`/`_OLD` (ФМС) и двойная база цен + magic-date
- **Описание.** В `Catalog.Клиенты` сосуществуют модели ФМС `_NEW`/`_OLD`; в ценообразовании — `ДокументыСервер`/`_Старый`, `КалендарьЦен`/`_Старый` с границей-хардкодом `'20240401'`.
- **Где.** `Catalog.Клиенты` (поля `*ФМС_NEW`, `*_OLD`); `ДокументыСервер.Module.bsl:369-371`; ADR-0003, ADR-0007.
- **Влияние.** Перенос неверной модели ФМС → потеря/искажение миграционных данных; пересчёт исторических броней новой моделью исказит закрытые периоды.
- **Рекомендация.** Подтвердить актуальную модель (`_NEW`), судьбу `_OLD`-данных; стратегию границы цен (не пересчитывать брони до `'20240401'`). Возможно вынести дату в настройку. См. CR-14, CR-15.

### G-C06. Магическая привязка `НайтиПоНаименованию("Бар")`
- **Описание.** Заполнение инвентаризации опирается на поиск группы товаров по человекочитаемому имени «Бар».
- **Где.** `ИнвентарицацияБара/Forms/ФормаДокумента/Module.bsl:154`.
- **Влияние.** Переименование/дубль/отсутствие группы молча ломают заполнение; `UnsafeFindByCode`.
- **Рекомендация.** Заменить на стабильный признак (предопределённый элемент / реквизит-флаг / константа-ссылка). См. CR-16.

### G-C07. БПО ред. 3.2 не разобрана вглубь (осознанная граница)
- **Описание.** ~255 объектов подсистемы `ПоддержкаОборудования`, ~98 общих модулей, 63 шаблона-драйвера описаны только на уровне фасадов/контрактов; фискализация (ФН), драйверы, ФЛК/маркировка/эквайринг — n/a.
- **Где.** `Subsystems/ПоддержкаОборудования/**`; ADR-0006; `code-spec-matrix.md` §непокрытые зоны.
- **Влияние.** Если граница неверна (требуется кастомизация внутри библиотеки) — объём и риски радикально меняются. ~40% «всей конфигурации» непокрыто.
- **Рекомендация.** Явно подтвердить, что библиотека переиспользуется как стабильная зависимость и не переписывается. См. EQ-02.

### G-C08. DCS-отчёты (СКД) не разобраны
- **Описание.** Ни для одного из 14 DCS-отчётов не извлечена схема компоновки (наборы данных, поля, ресурсы, связи, оформление).
- **Где.** `Reports/<Имя>/Templates/<Схема>/Template.dcs` + `.mdo` (`mainDataCompositionSchema`).
- **Влияние.** Реализация DCS-отчётов без схемы невозможна; ~33 отчёта вообще покрыты лишь по имени.
- **Рекомендация.** Извлечь схему каждого `Template.dcs` при детальной проработке отчётности. См. AU-01, AU-02.

### G-C09. Незаполняемая телеметрия датчиков — источник ТЧ не найден
- **Описание.** `Document.ПоказанияДатчиков` пишет РС по строкам ТЧ `Датчики`, но канал наполнения ТЧ (опрос/импорт/ручной ввод/HTTP/MQTT) не обнаружен.
- **Где.** `ПоказанияДатчиков/ObjectModule.bsl`; `Catalogs/Датчики`.
- **Влияние.** Сквозной сценарий телеметрии невоспроизводим (T-19 заблокирована).
- **Рекомендация.** Локализовать источник наполнения ТЧ. См. EQ-01.

### G-C10. Неразобранные финансовые формулы витрины аудита
- **Описание.** Формулы ресурсов `ЕжедневныйОтчетФакт` (агентское вознаграждение, B2B, ADR_НА, Процент_НА) не разобраны построчно.
- **Где.** `ЕжедневныйОтчетФакт/Module.bsl:2-407`.
- **Влияние.** Витрина соберётся, но финансовые показатели будут неверны. Граница с «Финансы»/«Ценообразование».
- **Рекомендация.** Разобрать формулы совместно с финансовым/ценовым модулями. См. AU-03.

### G-C11. XDTO-схемы обмена не разобраны
- **Описание.** `Cashbox_1_21_1/Package.xdto` и `ExchangeMessage/Package.xdto` не разобраны.
- **Где.** `XDTOPackages/*/Package.xdto`.
- **Влияние.** Сериализация/десериализация обмена и фискального контура невоспроизводима — блокер.
- **Рекомендация.** Получить актуальные XDTO-схемы у владельца. См. IN-01.

## 🟡 УМЕРЕННЫЕ — техдолг и риски, не блокируют ядро, но требуют решения

### G-M01. Незакрытые миграции / legacy-ветви (помимо критичных)
- **Описание.** Параллельные кодовые ветви и legacy-регистры: `ДокументыСервер_Старый`, `КалендарьЦен_Старый`, `ЦеныБазовыеПоДатам`/`ЦеныПоДатам` (legacy), `Тариф_НеИспользуется`, `КодыТарифов_КУдалению`.
- **Где.** Ценообразование (`CommonModules`, `InformationRegisters`); `code-spec-matrix.md` §3.
- **Влияние.** Риск переподнять устаревшую ветку расчёта цен.
- **Рекомендация.** Определить активные ветви по командам/обработчикам; legacy перенести как «исторический режим» или discard. См. CR-15, PR-05.

### G-M02. `CreateQueryInCycle` — запросы в циклах
- **Описание.** Запросы внутри циклов: ценообразование (N×5 запросов/бронь), печать акта списания (запрос по строкам ТЧ), потенциально шахматки.
- **Где.** `КалендарьЦен.ПолучитьТекущаяЦенаДня:161-224`; `СписаниеДопУслуг` печать; `Интерфейс`/`КоворкингШахматка`.
- **Влияние.** Деградация на длинных/групповых бронях и больших объёмах.
- **Рекомендация.** Предзагрузка среза одним запросом/единый запрос до цикла — ПОСЛЕ фиксации поведения тестами. См. PR-01, DK-05, RM-Q10.

### G-M03. Транзакции без `Попытка/Исключение`
- **Описание.** `НачатьТранзакцию/ЗафиксироватьТранзакцию` без `Попытка/ОтменитьТранзакцию`; запись в цикле без обёртки. Диагностика `BeginTransactionBeforeTryCatch`.
- **Где.** `КлиентыОбъединиение/Module.bsl:206-221`; `КоворкингСервер` (3 проц.) + форма `СписаниеДопУслуг` (2 проц.); `КалендарьЦен(форма).ИзменитьВыбранныеНаСервере:1565-1661`; `НомернойФонд/ObjectModule.bsl:29-55`.
- **Влияние.** Подвисшие транзакции и несогласованное состояние регистров при сбое.
- **Рекомендация.** Обернуть в канонический паттерн (Begin вне Try, Commit последним в Try, Rollback+журнал+Raise в Except). См. GU-02, DK-02, PR-02, RM-04.

### G-M04. Полный перебор без отбора + перепроведение
- **Описание.** `ЗаменаНомеровВЗаявках` перебирает ВСЕ заявки без отбора и перепроводит каждую с подавлением ошибки.
- **Где.** `ЗаменаНомеровВЗаявках/Forms/Форма/Module.bsl:11-29`.
- **Влияние.** Деградация на больших объёмах; молчаливые ошибки перепроведения.
- **Рекомендация.** Запрос с отбором + сбор/журналирование ошибок (T-18, EC-04). См. RM-Q08.

### G-M05. RBAC размазан по коду (`Админ`), местами закомментирован
- **Описание.** Доменный RBAC — проверки `ТекущийПользователь.Админ` в коде; в шахматке и др. закомментированы; роли платформы покрыты лишь 🟡.
- **Где.** Бронирование `ПередУдалением`, Ценообразование, Горничные; `Интерфейс` (снято); `permissions.md`; ADR-0010.
- **Влияние.** Неоднородная и местами отсутствующая модель доступа.
- **Рекомендация.** Перенести на роли платформы (Rights.rights) с явной матрицей; зафиксировать намеренно снятые ограничения. См. CrossR-04, RM-05.

### G-M06. Отчётность аудита — 33 отчёта по имени, дубли в форме
- **Описание.** Источники/колонки/агрегаты подтверждены только у 6 отчётов; в форме `ЕжедневныйАудит` несколько версий методов и закомментированный код.
- **Где.** `Reports/*`; `ЕжедневныйАудит/Forms/ФормаДокумента/Module.bsl`.
- **Влияние.** Возможны расхождения колонок/итогов; риск перенести мёртвую логику.
- **Рекомендация.** Подтвердить активные версии и состав каждого активного отчёта. См. AU-01, AU-05.

### G-M07. Мультиотельность как код (ADR-0008)
- **Описание.** Состав сети и параметры расчётного дня зашиты строковыми сравнениями имён отелей в нескольких модулях; единого справочника «Организация» нет.
- **Где.** Аудит (`Module.bsl:873-1006`, `ЕжедневныйОтчетФакт:436-851`), Персонал (`Module.bsl:347-376`), Горничные (`НастройкиСервер.Это*`).
- **Влияние.** Добавление/переименование отеля требует правки кода в нескольких местах.
- **Рекомендация.** Ввести единый справочник/настройку «Организация» с параметрами, либо явно сохранить хардкод 1:1. См. CrossR-02, AU-04, PE-06.

### G-M08. Дубль модели учёта рабочего времени персонала/горничных
- **Описание.** У администраторов РС `АдминистраторыТабель` (не используется), у горничных аналога нет (смены — на документах). Две модели.
- **Где.** `InformationRegisters/АдминистраторыТабель`; `Document.ГорничныеСмены`.
- **Влияние.** Единая точка отказа у горничных; рассогласование моделей.
- **Рекомендация.** Унифицировать модель учёта времени или явно сохранить две. См. CrossR-03, PE-04, HK-Q08.

### G-M09. Бизнес-логика на форме вместо `ObjectModule`
- **Описание.** `СписаниеДопУслуг` без `ObjectModule`/движений — вся логика, создание `ПрочиеОплаты`, транзакции на форме.
- **Где.** `СписаниеДопУслуг/Forms/ФормаДокумента/Module.bsl`; ManagerModule.
- **Влияние.** Слабая тестируемость и переносимость логики списания.
- **Рекомендация.** Вынести логику в серверный общий модуль, форму оставить тонкой. См. DK-01.

### G-M10. Запись РС в цикле без агрегации (коворкинг)
- **Описание.** `ОбработкаПроведения` коворкинга пишет слот на каждый час/день — десятки записей на документ месячной аренды.
- **Где.** `КоворкингСчета`/`ОбработкаПроведения`; РС `ЗанятостьНомеровКоворкинг`.
- **Влияние.** Нагрузка при длинных периодах аренды.
- **Рекомендация.** Сохранить слоты (нужны для шахматки) с оценкой нагрузки, либо интервальная модель. См. DK-03.

### G-M11. Дублирование клиент/сервер логики
- **Описание.** `КоворкингСервер` ↔ `КоворкингКлиент` (5 процедур, расхождение в `СчетДатаПо`); расчёт часов клиент (`*8`) vs сервер (`ДлинаСмены`) у горничных и персонала.
- **Где.** `КоворкингСервер`/`КоворкингКлиент`; `ГорничныеЗарплата/Forms/.../Module.bsl:846-853`; Персонал ADR-0011.
- **Влияние.** Клиент и сервер дают разные результаты; неоднозначный источник истины.
- **Рекомендация.** Единая серверная реализация; устранить расхождение часов. См. DK-04, HK-01, PE-08.

### G-M12. Молчаливое подавление ошибок (пустой `Исключение`, goto-ретраи)
- **Описание.** COM-выгрузка в `Попытка` с молчащим `Исключение` (загрузка «по нулю» без сигнала); `Перейти`(goto)-ретраи в интеграциях; нет `ЗаписьЖурналаРегистрации`. `MissingCodeTryCatchEx`.
- **Где.** `ОбменГорничныеСервер/Module.bsl:130-136`; `ОбменКартинкаСервер`; `HTTP_Модуль`.
- **Влияние.** Молчаливые сбои → недоначисление ЗП / потеря данных обмена без видимой причины.
- **Рекомендация.** Журналировать сбои, заменить goto на цикл попыток с алертингом. См. HK-Q09, IN-04.

### G-M13. Классификаторы ФМС `_NEW` не разобраны
- **Описание.** Структура справочников `*ФМС_NEW` (реквизиты `ID/CODE_ALPHA3/CODE_0/END_DATE`) не разобрана; зависит магическое `103008`.
- **Где.** `Catalogs/*ФМС_NEW`; `ВыгрузкаДляФМС`.
- **Влияние.** Выгрузка ФМС невоспроизводима без структуры классификаторов.
- **Рекомендация.** Получить источник/структуру классификаторов. См. GU-01, GU-03.
