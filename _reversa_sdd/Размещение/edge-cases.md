# Размещение и номерной фонд — Крайние случаи

> Файл `edge-cases.md`. Сценарии-границы, выведенные из легаси-кода.
> Доверие: 🟢 ПОДТВЕРЖДЕНО · 🟡 ВЫВЕДЕНО · 🔴 ПРОБЕЛ.

## EC-01 — Баг записи соседей в загрузчиках Лайв/Чехов 🔴

**Контекст.** `ЗагрузитьДанныеНомеровНаСервере` должен заполнять ТЧ `Соседи` импортируемого номера соседними комнатами из внешней базы.

**Дефект (Лайв/Чехов).** В цикле используется коллекция `ТЗ.Соседи` вместо `Строка.Соседи` (итерируется не та таблица), а присваивание `НоваяСтрокаСоседиСоседнийНомер = ...` написано БЕЗ точки — это не доступ к полю строки ТЧ, а отдельная переменная. В результате поле `СоседнийНомер` новой строки ТЧ остаётся пустым → **соседи не записываются**.

**Эталон (Реноме).** Исправлено: цикл по `Строка.Соседи`, присваивание `НоваяСтрокаСоседи.СоседнийНомер = ...`.

**Источник.** `DataProcessors/ЗагрузкаНомеровЛайв|Чехов/Forms/Форма/Module.bsl` (`ЗагрузитьДанныеНомеровНаСервере`); сравнение с `ЗагрузкаНомеровРеноме`. 🔴

**Ожидаемое поведение после исправления.** После импорта ТЧ `Соседи` каждого созданного номера содержит все соседние комнаты из источника. Регресс-тест: TT-07. Граф смежности (`Соседи` + `ОбщийКондиционер`) восстановлен.

**Влияние.** Сломан граф смежности → некорректная работа функционала, опирающегося на соседей/общий кондиционер; «тихая» потеря данных без ошибки.

## EC-02 — Раскраска ячейки шахматки при конфликте/множественности статусов 🟡

**Контекст.** На одну ячейку (Номер × ПериодРезерва) теоретически может приходиться несколько записей `ЗанятостьНомеров` (разный `Номер_пп` — сосуществование резервов в одном часе, ADR 0002), либо клиент без явного цвета.

**Поведение кода.**
1. Запрос шахматки заранее ИСКЛЮЧАЕТ статус `ОтказОтБронирования` (`статус ≠ ОтказОтБронирования`) — такие брони не красятся вовсе. 🟢
2. Приоритет цвета строго детерминирован (RM-04): `Проживает`→белый, `Выехал`→серо-бежевый, `ОтказОтБронирования`→лосось (в основном отфильтрован), иначе цвет регистратора → цвет клиента → `СлучайныйЦвет(ТЗКлиентов)`. 🟢
3. При отсутствии собственного цвета клиент получает случайный НЕКОНФЛИКТНЫЙ цвет (генерация против уже занятых в `ТЗКлиентов`). 🟡

**Источник.** `Интерфейс/Forms/Форма/Module.bsl:1077-1094, 1124-1140`. 🟢

**Ожидаемое поведение.** Каждая видимая бронь получает ровно один цвет по приоритету; при наложении резервов в одном часе закраска идёт по найденным строкам внутреннего цикла (`:1295-1432`, граница с Бронированием — детали не дочитаны 🟡). Регресс-тест: TT-03.

**Влияние.** Неоднозначность при множественных резервах в часе или конфликте цветов клиента/регистратора — визуальная путаница на главном экране размещения.

## EC-03 — Внешняя COM-база недоступна (импорт и зеркало горничных) 🟢

**Контекст.** И загрузчики номеров, и зеркалирование карточки в БД горничных используют синхронный `V83.COMConnector` к файловым базам по захардкоженным путям (`D:\DB`, `C:\_Base1C`).

**Поведение кода.**
1. **Импорт:** `Connect(строка)` неуспешен → `Сообщить(ошибка)` + выход; номера не создаются. 🟢
2. **Зеркало горничных:** соединение/вызов обёрнуты в `Попытка` → ошибка ПОДАВЛЯЕТСЯ через `Сообщить`; локальная запись номера проходит штатно. 🟢
3. Обмен с горничными вообще не запускается, если `ОбменСГорничными=Ложь` или нет `Папка_Горничные`. 🟢

**Источник.** `ЗагрузкаНомеров*/.../Module.bsl` (Connect-проверка); `НомернойФонд/ObjectModule.bsl:2-27` (Попытка/Сообщить); ADR 0005. 🟢

**Ожидаемое поведение.** Недоступность внешней базы НЕ блокирует локальную работу: импорт прерывается с сообщением, запись номера завершается успешно. Регресс-тесты: TT-04, TT-06.

**Влияние.** Подавление ошибки зеркала маскирует рассинхронизацию с БД горничных (расхождение без алерта). Хрупкость из-за жёстких путей и пароля в коде (🔴 questions.md).

## EC-04 — Замена номера в заявках: масштаб и перепроведение 🟢

**Контекст.** `ЗаменаНомеровВЗаявках` перебирает ВСЕ `ЗаявкаНаБронирование` без отбора и перепроводит каждую затронутую с подавлением ошибки.

**Поведение кода.** Для строк ТЧ с `НомерВРезерв=СтарыйНомер` — подмена и `Записать(РежимЗаписиДокумента.Проведение)` в `Попытка`. На больших объёмах — деградация; ошибка перепроведения отдельной заявки гасится (часть может остаться непроведённой). 🟢

**Источник.** `ЗаменаНомеровВЗаявках/Forms/Форма/Module.bsl:11-29`. 🟢

**Ожидаемое поведение после исправления.** Запрос с отбором по номеру; ошибки перепроведения собираются и сообщаются (а не молча гасятся). Регресс-тест: TT-08.

**Влияние.** Производительность + риск «тихо» непроведённых заявок после массовой замены.
